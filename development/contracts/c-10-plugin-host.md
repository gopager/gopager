## Implemented behavior (specified in docs)

The wire contract is [`api/plugin/v2/plugin.proto`](../../api/plugin/v2/plugin.proto) with the Go SDK [`pluginsdk`](../../pluginsdk/pluginsdk.go) (go-plugin over gRPC, protocol 2, UTF-8 JSON records). Everything else is in [Plugins](../../docs/plugins.md): the runtime model with one pooled process per instance revision, lazy start, `SecureConfig` digest check, idle timeout and stop rules ([§1](../../docs/plugins.md#1-runtime-model)); the invocation envelope with `instanceId` and the `mode` field `live` or `preview` ([§3](../../docs/plugins.md#3-invocation-request)); the response and the failure classification with automatic retry ([§4](../../docs/plugins.md#4-response)); all limits (call deadline, handshake, request and response size, executable size) ([§5](../../docs/plugins.md#5-limits)); the artifact directory, manifest, `configurationPolicy` with `admin` and `user` scope, digest and instance pins, `supportsPreview` ([§6](../../docs/plugins.md#6-packaging-and-installation)). Operator view: [Operations: Plugin Directory](../../docs/operations.md#plugin-directory). Typed code: [`internal/processing`](../../internal/processing/) (`installed.go`, `artifacts.go`, `plugin_runtime.go`, `instance*.go`). Management routes: [HTTP API: Processing instances](../../docs/http-api.md#processing-workflows-versions-candidates).

Decisions that remain binding:

- Operator-installed plugins are fully trusted separate executables run as application-managed child processes (D-130, D-131), one process per configured instance. The Core provides no sandbox and no memory limit; process separation isolates crashes and allows killing a hung plugin but is no security boundary. Plugins may have direct host, device and network access (GPIO, printers, MQTT, KNX and similar). In-process native loading (Go `plugin`, C-ABI libraries) is not supported. Only operators install or update code; web administrators configure permitted capabilities; users own allowed subscriptions. There is no marketplace and no native legacy ABI; any language with gRPC can implement the protocol, and only the Go SDK is supplied.
- A plugin failure cannot change another domain's data or grants or bypass attempt recording. The Core never downloads, compiles or installs plugins, and a missing artifact means capability or dependency unavailable, never a built-in stub.
- Workflow steps accept only modules that declare `pure`, require no Core fields or operations and no host capabilities; purity is the author's trusted declaration, not enforced. Preview never calls a plugin without `supportsPreview` and fails with `AUTHORITY_UNAVAILABLE` instead (no fallback), and it checks the current execution Principal, the source and the editor separately. Unresolved Secret references block activation and invocation.
- The manifest configuration contract is mandatory for the SDK and API, not optional UI metadata: every configurable property, including nested properties and collection elements, declares type, validation, required or default behavior, explicit Secret classification and a `configurationScope` (`admin` or `user`); omission, unknown scope, conflicting declarations or an unclassified open-ended property invalidate the manifest, and container replacement or merges preserve the classification so a personal write cannot bypass an administrative child. Configuration reads and writes enforce this server side, expose only permitted fields and redacted Secret status, and reject unknown or unauthorized fields atomically. Personal values never shadow administrative values, and a manifest update that changes a scope incompatibly is a visible configuration failure. C-09 owns the configuration-authority boundary. Planned cases: [F-45](reference-cases.md#ap-04-plugin-configuration-cases).
- Bytes use the canonical typed encoding of [Workflows: Typed values](../../docs/workflows.md#typed-values); an old or incompatible host, worker or module fails explicitly and never reinterprets or drops bytes. Bytes in configuration, personal and Secret schemas stay unsupported.

## Planned and not yet implemented (AP-11, AP-12)

- **Full manifest.** Offered Delivery and Domain-event capabilities, Secret field declarations, Extension field definitions (stored by Master data, see [C-04](c-04-master-data.md)), required Core SDK operations and data field sets, and informational resource expectations (not enforced by the Core). Unknown required capabilities and incompatible major versions block activation. Inspection never runs plugin initialization with active credentials. AP-12 T069 defines the generated schema and SDK configuration types.
- **Envelope additions.** SDK version, job and attempt reference, resolved Secret version, correlation reference (the triggering fact's `correlationId` and `causationId`) and the accepted, transient, permanent or uncertain result status belong to the Delivery attempt contract of AP-11 T066 and the mapping of AP-12 T069. A plugin may query other Units only through declared approved SDK operations under its explicit data Principal; reads go through the versioned HTTP API with an access key of its technical Principal, so they stay authorized and audited, and no second host-callback API is planned. Further capabilities (Delivery targets, event reactions under REQ-139, plugin-emitted Domain events) are new protocol methods or capability kinds.
- **Lifecycle.** installed, validated, configured, active, with incompatible, disabled and failed distinguishable; configuration is revisioned and checked before activation. Update validates a new artifact and configuration without mutating running invocations; existing invocations keep their digest, configuration and Secret version, and no new old-version start happens after the switch. Disable stops new starts, cancels outstanding work best-effort and records uncertain effects honestly. Rollback reactivates a still-compatible preserved artifact and configuration and never undoes external effects or silently downgrades incompatible state; a missing old artifact visibly blocks its pending work. Docker updates preserve mounted artifacts and configuration.
- **Helpers.** Standard HTTP and SMTP helpers and optional connection, stream and command capabilities let existing libraries own protocol logic, with deadline, cancellation and size limits on all mediated I/O; command execution needs its declared operator-approved capability. Required runtime dependencies are shipped with the distribution (D-63 managed-child boundary); this grants no capability by itself.
- **Secrets and external transport.** The Core Secret store encrypts local secrets with authenticated encryption under a separately provisioned master key and key ID, or resolves versioned external references (mounted files, environment, provider adapters); environment rotation needs a process or configuration refresh, mounted file or provider rotation creates a new resolved configuration revision. Manifest-declared per-instance Secrets reach only that trusted plugin invocation, pinned by version for the invocation and dropped afterwards; other plugins and views get neither values nor unauthorized references; logs and errors redact secrets, with no guarantee against a deliberately malicious trusted plugin. Core-owned HTTP, webhook and SMTP transport validates URL, host and port, the DNS results actually connected, TLS certificate and hostname, and redirects; by default it rejects loopback, private, link-local and cloud-metadata destinations and redirects, an authorized operator may explicitly permit intended internal infrastructure, deliberately enabled redirects revalidate and do not forward credentials to a different authority. A trusted plugin with broad network or command capability may apply its own policy; that is explicit trust, not a Core SSRF guarantee.
- **Email.** The deferred email plugin supports configured SMTP with TLS and authentication and controlled status mapping, rejects CR/LF injection in header and Address fields and never builds a shell command from Payload. Public transport requires TLS; private-infrastructure exceptions are explicit operator policy. Initial first-party targets are the separate Pushover and Webhook plugins (D-33); Telegram and email follow later, and the initial Webhook capabilities are owned by [C-09](c-09-delivery.md#initial-target-capabilities).
