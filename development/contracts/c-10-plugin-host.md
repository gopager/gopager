## Implemented behavior (specified in docs)

The wire contract is [`api/plugin/v2/plugin.proto`](../../api/plugin/v2/plugin.proto) with the Go SDK [`pluginsdk`](../../pluginsdk/pluginsdk.go) (go-plugin over gRPC, protocol 2, UTF-8 JSON records). Everything else is in [Plugins](../../docs/plugins.md): the runtime model with one pooled process per instance revision, lazy start, `SecureConfig` digest check, idle timeout and stop rules ([§1](../../docs/plugins.md#1-runtime-model)); the invocation envelope with `instanceId` and the `mode` field `live` or `preview` ([§3](../../docs/plugins.md#3-invocation-request)); the response and the failure classification with automatic retry ([§4](../../docs/plugins.md#4-response)); all limits (call deadline, handshake, request and response size, executable size) ([§5](../../docs/plugins.md#5-limits)); the artifact directory, manifest, `configurationPolicy` with `admin` and `user` scope, digest and instance pins, `supportsPreview` ([§6](../../docs/plugins.md#6-packaging-and-installation)). The `delivery` capability: the manifest members `capability`, `sdkMinor` 1, `delivery` and `resources`, the Delivery request and response and their mapping to attempt outcomes ([§3](../../docs/plugins.md#delivery-request), [§4](../../docs/plugins.md#delivery-response)), the capability rules, placement across nodes and plugin status ([§1](../../docs/plugins.md#capabilities)), the configuration policy with Secret and user-scope rules, Secret references and storage ([§6](../../docs/plugins.md#configuration-policy), [Secrets](../../docs/plugins.md#secrets)), the Go SDK, `safehttp` and `plugintest` ([§7](../../docs/plugins.md#delivery-plugins)), and the two first-party targets with their result classification and the receiver-side HMAC verification ([§9](../../docs/plugins.md#9-first-party-delivery-plugins)). Operator view: [Operations: Plugin Directory](../../docs/operations.md#plugin-directory) and [Operations: Secrets](../../docs/operations.md#secrets). Routes: [HTTP API: Processing plugin instances](../../docs/http-api.md#processing-plugin-instances). Development: [Development: Plugin modules](../../docs/development.md#plugin-modules-and-plugintest). Typed code: [`internal/processing`](../../internal/processing/) (`installed.go`, `artifacts.go`, `plugin_runtime.go`, `instance*.go`), [`pluginsdk`](../../pluginsdk/), [`plugins/`](../../plugins/).

Decisions that remain binding:

- Operator-installed plugins are fully trusted separate executables run as application-managed child processes (D-130, D-131), one process per configured instance. The Core provides no sandbox and no memory limit; process separation isolates crashes and allows killing a hung plugin but is no security boundary. Plugins may have direct host, device and network access (GPIO, printers, MQTT, KNX and similar). In-process native loading (Go `plugin`, C-ABI libraries) is not supported. Only operators install or update code; web administrators configure permitted capabilities; users own allowed subscriptions. There is no marketplace and no native legacy ABI; any language with gRPC can implement the protocol, and only the Go SDK is supplied.
- A plugin failure cannot change another domain's data or grants or bypass attempt recording. The Core never downloads, compiles or installs plugins, and a missing artifact means capability or dependency unavailable, never a built-in stub.
- Workflow steps accept only modules that declare `pure`, require no Core fields or operations and no host capabilities; purity is the author's trusted declaration, not enforced. Preview never calls a plugin without `supportsPreview` and fails with `AUTHORITY_UNAVAILABLE` instead (no fallback), and it checks the current execution Principal, the source and the editor separately. Unresolved Secret references block activation and invocation.
- The manifest configuration contract is mandatory for the SDK and API, not optional UI metadata: every configurable property, including nested properties and collection elements, declares type, validation, required or default behavior, explicit Secret classification and a `configurationScope` (`admin` or `user`); omission, unknown scope, conflicting declarations or an unclassified open-ended property invalidate the manifest, and container replacement or merges preserve the classification so a personal write cannot bypass an administrative child. Configuration reads and writes enforce this server side, expose only permitted fields and redacted Secret status, and reject unknown or unauthorized fields atomically. Personal values never shadow administrative values, and a manifest update that changes a scope incompatibly is a visible configuration failure. C-09 owns the configuration-authority boundary. Planned cases: [F-45](reference-cases.md#ap-04-plugin-configuration-cases).
- Bytes use the canonical typed encoding of [Workflows: Typed values](../../docs/workflows.md#typed-values); an old or incompatible host, worker or module fails explicitly and never reinterprets or drops bytes. Bytes in configuration, personal and Secret schemas stay unsupported.

## Not implemented yet

- **Email and Telegram.** The deferred email plugin supports configured SMTP with TLS and authentication and controlled status mapping, rejects CR/LF injection in header and Address fields and never builds a shell command from Payload. Public transport requires TLS; private-infrastructure exceptions are explicit operator policy. Initial first-party targets are the separate Pushover and Webhook plugins (D-33); Telegram and email follow later, and the initial Webhook capabilities are owned by [C-09](c-09-delivery.md#initial-target-capabilities).
- **Event reactions, Core reads and plugin-emitted Domain events** (REQ-139, later). Delivery plugins make no Core reads and there is no host-callback API; the Core read path would be the versioned HTTP API under a technical Principal.
- **Provider API adapters for Secrets** (Vault, cloud secret managers): not offered ([D-142](../decisions/09-process-and-documentation.md#d-142)); `file:` and `env:` references cover externally managed Secrets.
- **Master key rotation without re-entering Secrets.** The store has one active key and no re-encryption; see the decisions below.

## Core ports used by AP-11 and AP-12 (record)

AP-11 owns the Core target descriptor (`delivery.TargetDescriptor`, version 1) and the attempt port (`delivery.Targets`: `Describe`, `Attempt`; `AttemptInvocation`, `AttemptResult`), implemented in `internal/delivery` ([C-09](c-09-delivery.md#ap-11-core-binding-planning-before-coding)). AP-12 implements the port with the plugin host (`cmd/gopager/delivery_targets.go`, `processing.DeliveryHost`). The only descriptor change is `configurationAuthority`: `admin`, or `admin-and-personal` when the manifest has `user`-scoped properties. An error from `Attempt` after the request was sent is uncertain; without a plugin directory the plugin host answers `Describe` with `AUTHORITY_UNAVAILABLE`.

## AP-12 Host, Manifest, Configuration and Secrets (binding decisions)

Recorded 2026-11-12 by AP-12 before coding and implemented in AP-12 ([work package](../work-packages/ap-12-plugin-host.md)). The permanent documentation listed above specifies the behavior, wire formats, limits and error codes; this section keeps only the decisions that bind later work. Where it differs from the earlier planning of this contract, this section and the documentation win.

- **Manifest.** Schema 2 stays; `sdkMinor` 0 or 1 (1 adds the Delivery capability), anything else is `INCOMPATIBLE_VERSION`. `capability` defaults to `processing`. A `delivery` manifest declares no `inputSchema`/`resultSchema`, is not `pure` and has no preview; `requiredOperations` or `requiredCoreFields` on it is `CAPABILITY_UNDECLARED` (403) at inspection, instance save and load. `resources` is informational only. Delivery plugins make no Core reads: the only capability kind AP-12 adds is the Delivery target.
- **Configuration and Secrets declarations.** `secret: true` only on `string` properties outside lists; a `user`-scoped property is `optional`, and everything under a user container is personal; an `admin` list holds no `user`-scoped node at any depth and a `nullable` `admin` container holds no `user`-scoped descendant (both `INVALID_INPUT`); property names contain no `.`. Every property has exactly one scope, so a personal value never shadows an administrative one and the plugin receives one merged object.
- **Secret storage.** Reference strings `secret:<uuid>`, `file:<path>`, `env:GOPAGER_PLUGIN_SECRET_<NAME>`; writes carry them in a separate `secrets` map, never in `configuration`. AES-256-GCM with the row, instance and owner IDs as additional data; rows are immutable. The master key is `GOPAGER_SECRET_KEY_FILE` (wins) or `GOPAGER_SECRET_KEY`; file references live below `GOPAGER_SECRET_FILE_ROOT`. Rotation is by re-entering values (one active key, no re-encryption); `file:` and `env:` are the rotation path ([D-142](../decisions/09-process-and-documentation.md#d-142)).
- **Personal Secrets are stored values only.** `file:` and `env:` references are operator-placed Secrets for administrative configuration. A personal write offering one is `INVALID_INPUT`, and the resolver refuses them for owner-bound values at use, so a User cannot route an operator-placed Secret into their own recipient settings.
- **Personal values and account deletion.** `plugin_personal_configurations` (key `(instance_id, owner_id)`) and owner-bound `configuration_secrets` rows. Deleting a personal configuration keeps a tombstone row (null configuration, next revision) so revisions never reset; reads treat it as absent, `expectedRevision` `"0"` creates over it, and any other value must equal the live revision. A previous Secret reference is carried over on a write only when all its parent objects are present in the submitted configuration. `pluginconfigstore.Store.DeleteAccountData` deletes both (tombstones included) for one account in the caller's transaction; AP-14 T076 calls it ([D-160](../decisions/05-events-and-delivery.md#d-160)).
- **Target use ([D-149](../decisions/05-events-and-delivery.md#d-149), [D-160](../decisions/05-events-and-delivery.md#d-160)).** A `delivery` instance requires `targetUse` (`everyone` or at most 1000 Principal IDs; no groups). Refusal at Subscription save is indistinguishable from an unavailable target (`AUTHORITY_UNAVAILABLE`), fan-out creates no Delivery for it, and the start check cancels with `authority-revoked`.
- **Per-Unit values (REQ-129).** Typed values per Delivery input in `integration_unit_parameters`, managed under global `plugin.configure`.
- **Lifecycle and status.** `lifecycle` (`active | disabled | incompatible | failed`) is computed on read. Plugin `status` is node-local, kept in memory and reset by a restart; there is no cluster-wide status and no new backoff beyond the existing pool, lazy restart and idle timeout. An update or disable retires older revisions' processes on the node that handled the change; rollback is a new revision pinning an older, still present artifact.
- **Delivery wire (schemaVersion 2, `kind: "delivery"`).** Specified in the documentation. Host mapping beyond the AP-11 port: failures before the request was sent are `transient` (`plugin-unavailable`, `configuration-unavailable`), a request over 1 MiB is `permanent` `request-too-large`, an invalid code is `invalid-code`, and a receipt that is oversized, not JSON or contains a resolved Secret of the call is dropped with `receipt-redacted`. After the request was sent, transport failures, deadlines and malformed answers are errors, hence `uncertain`.
- **Placement (REQ-117, [D-160](../decisions/05-events-and-delivery.md#d-160)).** The runner claims at once the due Deliveries of instances that verify from the node's plugin directory (`DeliveryHost.Loadable`, cached 5 s, no process started). Fan-out on a node that cannot describe the target creates the Delivery due at once with outcome code `dependency-unavailable`, so a capable node claims it without delay. A Delivery still unclaimed 60 s after it became due may be claimed by any node, which, when it cannot load the artifact, defers it for 60 s keeping its state (`prepared` or `retry-pending`) with outcome code `dependency-unavailable` and consumes no attempt. Without a plugin directory the list is empty.
- **SDK transport.** `pluginsdk/safehttp` checks every resolved address and dials the checked one; besides loopback, private, link-local, CGNAT, unspecified, multicast and metadata addresses it denies `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4` and the IPv6 transition ranges `64:ff9b:1::/48`, `2002::/16`, `2001::/32` and `::/96`. `Policy.AllowPrivate` (the instance's `allowPrivateDestinations`) lifts the address rules including the metadata rule, and the port rule; the scheme rule then also admits `http`.
- **Packaging.** `plugins/pushover` and `plugins/webhook` are separate Go modules (`replace` to the repository root) with `manifest.template.json`; `plugins/build.sh` and `make plugins` produce the plugin directory layout; the default `make` goal is `lint` plus `plugins-test`. The compose image ships both plugins under `/usr/lib/gopager/plugins` and sets `GOPAGER_PROCESSING_ARTIFACT_ROOT`.
