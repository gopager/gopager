**Version/status:** 0.1-draft. **Owner:** Plugin host; DOM-07 owns Delivery/subscription semantics, integration owns SDK contract. **Producers/consumers:** Operator supplies artifacts; host checks/activates; modules produce/handle explicit Domain events or provide allowed targets.

Draft interfaces: `InspectModule(artifact) -> compatibility`; `ActivateModule(moduleRef, configurationRevision) -> lifecycleStatus`; `InvokeCapability(invocationContext, projectedInput) -> boundedResult`; `DisableModule(moduleRef) -> status`; `DeclareExtensionFields(manifest) -> validated definitions`. Manifest/SDK shape below is documentary, not an approved compiled ABI.

**Defined:** Separate Operator-provisioned plugin executables, run as application-managed child processes under [D-131](../authoritative-plan.md#managed-plugin-process-runtime); each configured instance has its own process. Only operators install/update code. Web administrators configure permitted capabilities; users own allowed subscriptions. Lifecycle, update/rollback and incompatible/disabled/active/failed states are specified below. No marketplace or native legacy ABI. Any language with gRPC can implement the published protocol; only the Go SDK is supplied. English documentation and stable machine codes do not prevent a language-neutral SDK.

**Trust clarification (D-130, 2026-11-05):** Operator-installed plugins are fully trusted. The target capability includes direct host, device and network access, for example GPIO, displays, printers, building automation, MQTT and KNX. D-67's pure WASI command is only the first implemented subset for installed Processing steps; it is not a trust boundary or a limit for other plugins. D-131 selects the runtime that provides this access (managed executables over `go-plugin`/gRPC).

**Trust boundary (D-24):** Operator-installed plugins are trusted code. Explicitly approved host capabilities may include general network/SMTP/MQTT, filesystem and host/container command execution; the Core provides no sandbox around a plugin process. All SDK operations on Core entities, including other Units, must be declared in the Plugin manifest and pass current C-06 authorization. Host-level access can technically bypass SDK isolation (for example by reading a mounted database); the trust contract prohibits undeclared Core access but cannot guarantee enforcement against malicious privileged code. Operators must not grant such access to code they do not trust.

**AP-04 delivery amendment (D-33):** The initial first-party targets are separate Pushover and Webhook plugins; Telegram and email are later under the [scope decision](../authoritative-plan.md#ap-04-scope-decision). Initial Webhook capabilities are owned by [C-09](c-09-delivery.md#initial-target-capabilities). The retained future email boundary below does not require an initial SMTP implementation: an HTTP-only host API would not automatically support later email, which needs controlled SMTP or an explicitly selected mail provider path. For configurable webhooks/hosts, internal-target protection, DNS/redirect/TLS behavior, and secret forwarding belong to the security contract, not a blanket Network grant.

**Configuration exposure (D-33 clarification, 2026-10-26):** The [manifest configuration-field contract](#manifest-configuration-fields) is mandatory for SDK/API configuration, not optional UI metadata. C-09 owns the [configuration-authority boundary](c-09-delivery.md#configuration-authority), Pushover split and before-attempt checks.

**Transaction/failures:** Plugin failures cannot change another domain's data/grants or bypass attempt recording. Process separation isolates crashes and allows killing a hung plugin; it is no security boundary. The lifecycle below and C-09 define disable/update during invocation and uncertain provider results.

## Installed Processing Invocation

**Version/status:** plugin-runtime 2.0 under [D-131](../authoritative-plan.md#managed-plugin-process-runtime) (2026-11-05). It replaces the runtime of installed-processing 1.0 (D-67 WASI command). The typed envelope, manifest semantics, authorization and preview rules of 1.0 are kept. **Owners:** plugin host/integration for invocation, DOM-08 for typed Workflow use. Core regex runs in process under D-129 and is not a plugin.

**Runtime and protocol.** The Operator provides a plugin executable and a manifest (schema version 2, SDK 2.0) below the configured artifact root. The artifact may be a native binary or a script with an interpreter line; any interpreter is the Operator's responsibility. The Core starts the executable as a child process through HashiCorp `go-plugin` (handshake cookie `GOPAGER_PLUGIN`, application protocol 2, gRPC only) and calls `gopager.plugin.v2.Plugin/Invoke`. Request and response are `google.protobuf.BytesValue` messages containing UTF-8 JSON: the invocation envelope and the response defined in [the command boundary](../../internal/processing/installed.go). The protocol is published as [`api/plugin/v2/plugin.proto`](../../api/plugin/v2/plugin.proto); the Go SDK is [`pluginsdk`](../../pluginsdk/pluginsdk.go). The process receives a minimal environment, without inherited Core configuration or secrets, and runs in its artifact directory. Its standard output and error are not forwarded to Core logs.

**Instances.** Each configured instance (REQ-084) is loaded separately and runs in its own process; two instances of the same plugin never share a process. Envelope schema version 2 adds `instanceId` next to `configurationRevision`, so a plugin can keep per-instance connections, devices or state apart. Processes currently live for one Workflow run and are stopped when the run closes; a pool across runs is AP-12 planning.

**Loading and inspection.** Loading reads the manifest, validates it, checks that the artifact is a regular executable file inside the root, and verifies its SHA-256 pin by streaming at most 256 MiB. It does not start the process, so inspection never runs plugin initialization with live data or Secrets. The process starts on the first invocation; an incompatible handshake is an explicit failure. Unknown required capabilities still block invocation.

**Invocation bounds and failures.** Each call is limited to 1 MiB encoded input, 256 KiB output and a 30 s deadline; installed time stays excluded from the Workflow compute budget. A deadline, cancellation or broken connection kills the process, and the next call starts a new one. Each of the following is an explicit failure: a malformed, non-UTF-8, oversized or mixed success/failure response; a reported failure reason; a crashed process. Private plugin text never becomes a public error. The Core enforces no plugin memory limit; Operators use container or OS limits.

The concrete manifest, artifact pin, configuration policy and loader forms are owned by [the installed artifact definitions](../../internal/processing/artifacts.go) and [the process runtime](../../internal/processing/plugin_runtime.go). [Workflow invocation ports](../../internal/processing/installed_workflow.go) require separate current instance/Principal/source authorization and reject input substitution. No grants, credential secrets, foreign tables or unrestricted source are passed. The host-only invocation context carries the actual [captured source reference](../../internal/processing/capture.go) and optional original body target independently of mapped field values.

**Processing-step semantics.** Workflow steps still accept only modules that declare `pure`, no required Core fields/operations and no host capabilities. Under D-130 this is a trusted declaration by the plugin author, not an enforced sandbox. Preview never executes effectful or undeclared-capability code. A separately declared pure-preview artifact may run with synthetic or authorized data under the same bounds; otherwise the result is `capability-unavailable`. Stored samples or input require fresh execution-Principal grants and source-owner projection, separately from the editor's action grant. A missing source, configuration, Secret or authority owner fails explicitly; unresolved Secret references block activation and invocation.

The Operator provisions artifact and manifest through the local persistent artifact directory. Administrative instance configuration is separately revisioned; Workflow activation validates the capability, configuration and Principal binding. Digest and configuration pins are immutable during invocation. Disabling or switching versions prevents new old-version starts and cancels current calls. A missing artifact means dependency or capability unavailable, not a builtin stub.

**AP-06 startup/read additions, D-100/D-101:** Redacted administrative instance reads and listing use the existing global `plugin.configure` action under [C-06's narrow binding](c-06-identity-authorization.md). The local artifact directory is selected through the optional `--processing-artifact-root` flag or `GOPAGER_PROCESSING_ARTIFACT_ROOT`, with no default path, downloads or runtime installation. An invalid configured root fails explicitly; omitting it leaves installed capabilities unavailable without disabling built-in processing. Configuration views preserve the manifest redaction rules below.

The narrow administrative revision representation is owned by:
- [Processing instance types](../../internal/processing/instance.go)
- the [bounded local inspector](../../internal/processing/instance_artifacts.go)
- the [current-proof command coordinator](../../internal/processing/management/instance.go)
- [native immutable snapshots/current pointer](../../internal/persistence/ent/processingstore/instance.go)
- the [additive schema migration](../../internal/persistence/migrations/00007_processing_instances.sql)

[The execution/lifetime adapter](../../internal/processing/instance_execution.go) owns per-run main/preview preparation, fresh checks of the enabled instance, execution Principal and global fields, required source-owner checks, committed-change cancellation and drained process cleanup. Callers must evaluate with the run context, join dependent work, close the run, then close the shared plugin host and root during shutdown.

### Bytes Compatibility Addendum

## Installed Artifact Load Bound

**Status:** revised under [D-131](../authoritative-plan.md#managed-plugin-process-runtime); the 32 MiB `.wasm` bound of D-73 no longer applies. **Owner:** plugin host/integration.

The pinned executable (main or preview) must be a regular file inside the configured artifact root with an executable permission bit. Its SHA-256 digest is computed by streaming at most **256 MiB**; a larger, missing, non-regular, non-executable or mismatched artifact is an explicit capability failure. Rooted path handling must not permit reading outside the artifact directory. The process is started from the same path after verification; replacing the file between verification and start is an Operator action inside the trusted boundary, not a protected case. Do not download replacements, compile source or silently select an old version.

## Manifest Configuration Fields

**Owner:** Plugin host/integration; AP-04 D-33 draft amendment, not a frozen machine-readable manifest/SDK artifact. Every configurable property must declare its type/validation, required/default behavior, explicit Secret classification, and `configurationScope`:

| `configurationScope` | Storage/configuration binding | Who may configure |
| --- | --- | --- |
| `admin` | Administrative plugin instance | Authorized administrator/Operator under C-06 `plugin.configure`; never ordinary personal Subscription authority. |
| `user` | Owning User within a configured plugin instance | That User, with current permission to use the instance and manage their personal configuration; never another User's configuration or an administrative override. |

The classification applies to every configurable value, including nested properties and collection elements. Container replacement, defaults and configuration merges must preserve it; mixed-scope containers cannot be replaced through a personal write to bypass an administrative child. Omission, unknown scope, conflicting declarations or an unclassified open-ended property invalidate the manifest at inspection/activation. There is no inferred user-editable default. Plugins without personal settings declare no `user` properties.

SDK/API reads and writes use the validated manifest version and enforce this classification server-side for all configuration paths. Configuration views expose only permitted fields and redacted Secret status. Requests containing unknown or unauthorized fields are rejected explicitly and atomically without persisting the permitted subset; hiding a field in the UI or silently ignoring a forbidden field is insufficient. Manifest declarations describe supported configuration, not new grants or permission to make C-09 administrative settings user-editable.

Invocation resolves the administrative configuration and only the applicable User's personal configuration under the existing invocation Principal/Secret rules. Identical field names or nested paths do not allow personal values to shadow administrative values. Manifest updates revalidate configuration and its scopes before activation; an incompatible scope change is a visible configuration failure, not silent promotion of personal input to administrative authority. Existing invocations retain their pinned version under the lifecycle rules.

[F-45](reference-cases.md#ap-04-plugin-configuration-cases) specifies planned positive/negative examples. AP-12 defines the generated manifest schema/SDK configuration types, authoritative paths and compatibility version before implementation.

## AP-02 Installation, Manifest and Invocation

- Operator provides a plugin executable plus manifest through a persistent directory/volume or image layer before start, and names the directory by flag or environment (D-130/D-131). No Core rebuild and no automatic remote code download. Interpreters for script plugins, and device access (for example Docker `--device`), are the Operator's responsibility; required first-party plugins ship with the distribution (REQ-115). Docker updates preserve mounted artifacts/configuration.
- Manifest requires plugin ID/version, artifact digest, manifest/SDK major/minor compatibility, offered Delivery/processing/Domain event capabilities, typed configuration/input/result schemas, Secret fields, Extension field definitions, required Core SDK operations/data Field sets, requested host capabilities and resource expectations. Unknown required capabilities or incompatible major versions block activation; additive optional fields may be ignored only as schema permits. Inspect never executes plugin initialization with active credentials.
- Lifecycle: installed -> validated -> configured -> active; incompatible/disabled/failed distinguishable. Configuration is revisioned and checked before activation. Install/update is Operator-only; web administrators can configure only delegated capabilities, Users only permitted targets/Subscriptions. Host/container execution is an explicit high-trust capability, not silently inferred from email support.
- Invocation envelope identifies plugin artifact digest, SDK version, capability, job/attempt, effective Principal, configuration and resolved Secret version, deadline/cancellation, typed input and correlation reference. Result is bounded typed output plus accepted/transient/permanent/uncertain status; no raw exception/SQL/credential details in public outcomes. Plugin may query other Units only through declared approved SDK operations under its explicit data Principal, not by inheriting the installer.
- The SDK is the versioned gRPC protocol of D-131 carrying UTF-8 JSON records; the earlier guest-memory/host-function draft is withdrawn. Further capabilities (Delivery targets, event reactions under REQ-139, plugin-emitted Domain events) are added as new protocol methods or capability kinds by AP-11/AP-12. Plugins read Core data through the versioned HTTP API with an access key of their technical Principal, so reads stay authorized and audited; no second host-callback API is planned.
- Standard HTTP/SMTP helpers and optional connection/stream/command capabilities let compatible existing libraries own protocol logic. Core need not implement Telegram/SMTP protocol engines twice. Every mediated I/O has deadline/cancellation and size limits; plugin command execution still requires its declared Operator-approved capability. [D-63's managed-child boundary](c-12-persistence-operations.md#managed-child-process-clarification) permits application-managed subprocesses without an exact Core process-count restriction. Required application/plugin-host runtime dependencies must be supplied, not installed separately by the Operator. This topology clarification does not grant a plugin command/network/filesystem or Core-data capability.
- Update validates a new artifact/configuration without mutating running invocations. Existing invocations keep their digest/configuration/Secret version; no new old-version starts after activation switch. Disable stops new starts, cancels outstanding work best-effort, records uncertain effects honestly. Rollback reactivates a still-compatible preserved artifact/configuration; never undo external effects or silently downgrade incompatible state. Missing old artifact blocks its pending work visibly.

## AP-02 Secrets and External Transport

Core Secret store either encrypts local secrets using authenticated encryption with a separately provisioned master key/key ID, or resolves versioned external references. Kubernetes-mounted Secret files/environment and external-provider adapters are valid delivery paths; environment rotation requires process/configuration refresh, mounted file/provider rotation creates a new resolved configuration revision. No requirement to copy external values to SQL or bake them into images.

Manifest-declared per-instance Secrets may be supplied in plaintext only to that trusted plugin invocation; opaque handles are optional convenience, not a mandatory second security system. Other plugins/normal views receive neither values nor unauthorized references. Rotation pins the resolved value/version for the invocation, then drops it when finished; missing/expired Secret produces a visible configuration failure. Standard logs/errors redact secrets; there is no guarantee against a deliberately malicious trusted plugin printing or exporting them.

Core-owned configurable HTTP/webhook/SMTP transport validates URL/host/port, DNS results actually connected, TLS certificate/hostname and redirects. Default core transports reject loopback/private/link-local/cloud-metadata destinations and redirects; an authorized Operator may explicitly permit intended internal SMTP/MQTT/webhook infrastructure and external endpoints. Redirects, if deliberately enabled, revalidate destination and do not forward credentials to a different authority. A trusted plugin granted broad network/command capability may implement its own policy; that is explicit trust, not a falsely advertised Core SSRF protection.

The deferred email plugin supports configured SMTP with TLS/authentication and controlled status mapping; header/Address fields reject CR/LF injection, no shell construction from Payload. Standard public transport requires TLS; intentionally configured private infrastructure exceptions are explicit Operator policy, not silent downgrade. Initial target timing follows [D-33](../authoritative-plan.md#ap-04-scope-decision), not these retained future email requirements. Libraries are allowed if compilable/compatible; feasibility must be demonstrated rather than installing a second runtime unasked.
