## Implemented behavior (specified in `docs/`)

- PostgreSQL is the only store. "Lite" and "Full" are deployment profiles of the same binary: Lite is the single-host compose deployment, Full uses an external PostgreSQL and any split of roles. Topologies, flags, roles, start-up, bootstrap, health endpoints, failure handling, exit status, database TLS, plugin directory, shutdown and security: [Operations](../../docs/operations.md) (profiles in [Topology](../../docs/operations.md#topology) and [Lite with Docker Compose](../../docs/operations.md#lite-with-docker-compose)).
- Transaction and repository participation (opaque transaction capability, `READ COMMITTED`, 30 s timeout, no nesting, no callback replay, `COMMIT_UNCERTAIN`), locking, clock, readiness and lifecycle: [Architecture: Cross-cutting mechanisms](../../docs/architecture.md#cross-cutting-mechanisms). Failure classification: [Architecture: Errors and failure codes](../../docs/architecture.md#errors-and-failure-codes).
- Migrations (Goose, ledger, `check` and `apply`, advisory lock, strict prefix rule, no down migrations, corrective migrations instead of editing applied ones, release-time generation only): [Operations: Database Migrations](../../docs/operations.md#database-migrations) and [Development: Database Schema and Migrations](../../docs/development.md#database-schema-and-migrations). Health probes and their response schemas: [HTTP API: Platform endpoints](../../docs/http-api.md#platform-endpoints) and the `Platform` tag of [OpenAPI v1](../../api/openapi/v1.yaml).
- Application HTTP transport: every function works over the configured HTTP listener, there is no TLS requirement, redirect or separate HTTP setting, a reverse proxy may terminate TLS, direct HTTP offers no confidentiality or server authentication, and the public Origin value is deployment configuration: [HTTP API: Basics](../../docs/http-api.md#basics), [Origin and CSRF policy](../../docs/http-api.md#origin-and-csrf-policy) and [Operations: Security](../../docs/operations.md#security).
- Backup and restore are the operator's: [Operations: Backup and restore responsibility](../../docs/operations.md#backup-and-restore-responsibility). Initial setup is local, one-time and without shipped credentials, and completing it disables the bootstrap path: [Operations: First Start and Bootstrap](../../docs/operations.md#first-start-and-bootstrap).

Decisions that remain binding: on a failed allocation, write or commit (including a full disk or read-only store) the server rolls back where known and returns `STORAGE_UNAVAILABLE`, a possible commit is `COMMIT_UNCERTAIN` with caller-owned receipt lookup and never a definite rejection; C-01 acknowledges only its recorded acceptance stage; unclear primary or lease authority is `AUTHORITY_UNAVAILABLE` and stops new acceptance writes, private output and Delivery starts while pending work is retained; data is never deleted and durability or permissions are never relaxed to recover capacity; an inability to persist a failure fact is exposed through status and logs, not claimed as committed; expired attempts and leases never become fresh unattempted work; no quantitative SLA, RPO, RTO or hardware promise exists; operator-facing text is English by default and operational codes are language independent. Child processes (plugins) may be launched and managed by the application provided everything they need ships with it; the application owns their lifecycle, bounded IPC, cancellation, termination and reaping and never silently falls back to unrestricted in-process execution (D-63).

## Planned and not yet implemented (AP-16)

- **Retention.** Messages and `audit_records` are deleted only under an operator limit, unlimited by default; the limits are a revisioned single-row installation setting (e.g. `retention_settings`) managed through `GET/PUT /operations/retention`, and `POST /operations/retention/runs` starts a manual run on the same path as the worker-role runner (`--retention-interval`, default 1h, greater than 0), all with `operations.manage` (scope all, no new read action) ([D-142](../decisions/09-process-and-documentation.md#d-142)). The retention unit is a whole Message, aged by stored Message time (the earliest Observation time); a count limit removes the oldest whole Messages by `(Message time, Message ID)`. The policy is installation wide and never depends on a user's filters. Deletion removes the Message's `message_units` rows, target resolutions, Transmission evidence and membership, derived Processing and search data and the linked Submission receipts consistently, without regrouping other Messages or leaving dangling references; lookups of deleted Message references return not found. A continuously extended old Message can be removed despite recent receptions and an older late member can move it past the cutoff; a new Unit appearance does not extend retention. Expose the policy clearly to the operator; no switch to last-reception retention or per-target deletion. The accepted C-01 exception stays: a Gateway retry after removal of its Submission receipt can create a new Transmission. Retention also prunes automatically, without operator limits: `domain_events` and `consumer_offsets` (below every consumer offset and older than the replay window, which is AP-10's SSE replay window, default 24 h), terminal receipts per the C-08 rule and `login_attempts` once older than the longest rate-limit window (D-135, D-142). Prepared self-contained Delivery input can finish after Message deletion under C-09's bounded lifetime; jobs needing deleted data end `dependency-unavailable`; minimal deduplication and uncertainty receipts follow C-08. Gateway diagnostics distinguish removed history from never received: retention that deletes `gateway_state_history` rows sets `gateways.history_removed_before` to its cutoff (exposed as `historyRemovedBefore`, [Gateway administration](../../docs/http-api.md#gateway-administration)) and never clears `last_contact_at`, `last_heartbeat_at` or `last_transmission_at`. Storage exhaustion stays visible and never triggers silent emergency deletion.
- **Operational status.** Beyond the boolean probes, authorized readiness detail (store role, write and access authority, migration state, pending or failed correction and Processing work, safe storage, Secret and plugin failure codes) through `GET /operations/status` (`operations.manage`, scope all). Liveness is not write readiness; a replica or cache never serves private responses during authority loss. No capacity thresholds or alerts; storage exhaustion is reported through `STORAGE_UNAVAILABLE`, the status route and logs.
- **Updates.** Preflight of schema and plugin compatibility and blocking of conflicting writes during an incompatible migration; failure leaves an explicit not-ready or maintenance state; no automatic rollback of intervening data. Plugin artifact rollback follows C-10 and does not roll back provider effects.
- **Full fault and topology evidence.** Fault injection for authority loss and recovery, lease fencing, disk, crash, restart and external-effect recovery boundaries, and Delivery and retention under the real producers; no failover, HA or crash guarantee is demonstrated. An application-managed PostgreSQL child is not planned ([D-135](../decisions/10-foundation-redesign.md#d-135)).
