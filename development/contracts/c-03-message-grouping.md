**Defined:** GoPager groups only exact canonical Payload matches across compatible Protocols, Gateways and Networks (D-30). Preserve every original and target, including partial receptions; different canonical values remain separate. The Gateway does not submit authoritative membership. Network/Gateway alone do not split a Message; Unit resolution is independent. One shared Grouping policy does not assert a common real-world incident.

Grouping always uses the normalized Observation instant defined by C-01; this time basis is fixed and is not operator-configurable. The timestamp must include an explicit UTC offset or UTC designator and is compared as an unambiguous instant, never replaced by server acceptance time. D-42's whole-second precision applies before the inclusive-window comparisons below. **Grouping rules (user decisions 2026-10-25; frozen for AP-07 as part of C-03 1.0, draft for other consumers):**

- **Window `W` (D-49/D-51; D-51 supersedes D-46):** operator-configurable in whole seconds only, default 30 seconds. `W` = 0 disables Grouping: every Transmission forms its own Message. The inclusive range is `0..9,007,199,254,740,991` seconds (`2^53−1`), represented as a JSON integer so common clients can retain exact values. Values outside that range or non-integer forms are invalid and are rejected, never clamped. For comparison, use whole-second UTC instants and a checked absolute difference; do not multiply `W` into nanoseconds or add/subtract it from an instant. The supported RFC 3339 Observation range has a pairwise whole-second difference that fits `int64`. This exact behavior remains draft until frozen for the consuming slice.
- **Boundary:** inclusive. Two Payload-identical Transmissions are linked if their reported instants differ by at most `W`.
- **Exact membership (chain rule):** Under an unchanged policy, Payload-identical Transmissions connected by consecutive gaps `<= W` form the same component, independent of acceptance order: 0/50 and then 25 seconds (`W=30s`) equals 0/25/50. Similar but canonically different originals do not establish connectivity.
- **No maximum Message age.** The previously recorded default of 180 seconds is withdrawn (user decision on 2026-10-25, choosing to drop it rather than apply it only at ingest). A limit applied only when joining would be bypassed by merges and would reintroduce order dependence. Consequence: continuously repeated identical Payload (for example a stuck transmitter) forms one Message of unbounded duration.
- **Late/out-of-order Transmissions:** linked by reported Observation time, not by arrival order. There is no lateness cut-off: a Transmission may link to any retained Message, however old. Messages or Transmissions removed by retention are no longer candidates. The 2-hour lateness tolerance recorded by the user is a fallback only if unbounded late linking proves disproportionately complex; AP-01 assessment is that a lookup by Payload identity and member instants within `[t-W, t+W]` does not require it.
- **Exact merge on gap closure:** A new exact member connecting multiple components merges their Messages. Which internal Message representation is retained or replaced is an implementation choice, not an enduring public identity guarantee. No alias, old-link forwarding or old/new ID mapping is required. Current references and affected read models must be reconciled consistently; originals remain unchanged. Heuristic attachment/split behavior is not implemented or required in current scope.
- **Configuration changes:** Each membership decision captures the active Grouping-policy revision as its transaction begins; a decision already using that revision may finish under it. A configuration change uses `expectedRevision`, commits the new value/revision and audit record atomically, and applies to decisions that capture the new revision afterwards. There is no per-Message policy pinning or Address-rule-version entity. Existing memberships are not automatically regrouped; subsequent exact input may join/merge under new `W`. Historical regrouping is an architectural possibility, not a required future capability; heuristic correction remains later work. Concrete fields/revisions remain owner-contract work.
- **Configuration permission:** changing the Grouping configuration requires the dedicated, grantable `grouping.configure` capability at `all` scope (not implied by other administrative rights); every change is audited with the old and new values and the resulting revision. Enforcement belongs to C-06.
- **Domain event changes:** the Grouping domain emits a Domain event for each Message membership change: Message created, Transmission joined an existing Message (including a late join to an old Message), and Messages merged (survivor and absorbed IDs). These are new facts, not corrections of earlier Domain events. How consumers react (for example the frontend showing an additional Unit, or a push integration updating or reissuing a Delivery according to subscription and provider capabilities) is defined by their own contracts (C-07, C-08, C-09).

The server performs all comparisons from submitted Transmissions; a Gateway may not deduplicate or merge Transmissions to extend a Message. Transport retries do not extend the window by inventing a Transmission or a new Observation time.

## Controlled Historical Regrouping Boundary

**D-39/D-40 clarification, 2026-10-26:** Recomputing Message grouping from retained original Transmissions under a selected comparison/grouping definition and window is an architectural possibility, not a product requirement, mandatory preparation task, or promised future operation. In particular, changing the Grouping configuration does not require regrouping. The user's latest clarification supersedes the earlier interpretation as an approved future capability. No split/rebuild machinery is authorized in AP-05/AP-06. This possibility remains separate from non-exact heuristics under D-30.

Recomputing with another policy can change memberships, merge or split Messages and assign different Message IDs; it need not reproduce historical membership decisions. Repairing derived data while preserving existing membership decisions is a different operation. Retention-deleted originals cannot be reconstructed. D-40 removes enduring Message identity requirements for both normal merging and future recomputation.

No old/new ID mapping or successor-lookup capability is required or reserved. Invalidated Message references may return not found and views may require resynchronization under C-07. Stable authorization-relevant identities remain governed by the shared conventions.

Before executable scope is approved, the owning contracts must define consistent replacement publication with concurrent ingest/corrections, revision/fencing checks, contribution/support reconstruction, safe query/live resynchronization, pending job references and whole-Message retention during and after recomputation. Existing C-08 historical reprocessing suppresses external reactions by default; regrouping is not a new reception or permission for duplicate Delivery. Required contracts, cases and affected not-yet-started work packages need their own approval before implementation. Initial F-07/F-07b behavior remains unchanged.

## Initial Grouping Consistency and Projection

**Transaction/concurrency:** Message membership, publication state and required Domain event remain consistent; concurrent inputs must not create duplicate exact Messages. Exact Grouping/merging is serialized per Payload identity. On merge, coalesce equivalent Message contributions, redirect Contribution supports and recompute first times/age anchors and representative preference. Membership/supports/summaries publish consistently; original target resolutions remain traceable. Concrete fields/revision placement belong to the owner contract; validate SQL strategy in AP-03. Rule Rematching, lifting suppression and Workflow changes do not change membership.

**Projection:** Global last-Transmission time, Message size, and Gateway list are not automatically visible. Query projects from permitted Transmissions; hidden Transmissions must not leak through counts, ordering, or change indicators.

**AP-02 Message-time clarification:** Store internal `messageTime` as the minimum Observation time across members, atomically corrected on older late join/merge. It supports origin/retention, not normal GUI sort or authorization age. C-07 computes `viewTime` only from permitted matching Unit appearances; the former hidden-member timestamp exception is withdrawn. C-12 still deletes a whole Message. AP-01 chain semantics remain unchanged.

**Representative selection:** No mandatory second original Payload copy. Among usable readable exact members prefer those not marked incomplete, then earliest Acceptance time and ascending Transmission reference in the retained input set. This tie-break is not an enduring public ID guarantee. Otherwise use the same tie-break and visibly qualify the fallback. Repeat selection within readable evidence if the stored preference is inaccessible. No longest-text assumption, concatenation or synthetic completion. A canonically different fuller text remains another Message, not a representative replacement. A better original representation within the same identity may update display without resetting Unit times.

The semantic reference name is `representativeTransmissionId`; this fixes spelling, not a physical column layout. Absence of an Incomplete marker is not evidence of reception correctness.

**Comparison extension boundary:** C-02 owns comparison; this contract consumes exact match results and owns temporal membership/merge and atomic publication. Retain original evidence and match kind `exact`; do not implement future fuzzy scans, scores, split/reference events or new heuristic jobs now. A future non-exact comparator requires explicit approval of candidate discovery, temporal constraints, re-evaluation, split/reference/Delivery semantics and concurrency; exact per-identity serialization alone would not validate that extension.

**Remaining gates:** Product-specific PostgreSQL duration/concurrency validation is mandatory under AP-06 T024 after implementation and remains open until passed; D-50 makes it a completion gate, not a contract-freeze blocker. AP-07's exact C-03 and C-02 slices are frozen under D-119; this does not reopen earlier decisions. D-42 selects whole-second Observation precision; FLEX facts were verified under D-34. AP-02 handover is documentary, not runtime validation. Heuristics and configuration-triggered historical regrouping are later scope, not freeze blockers. No fixed-span-window change is adopted.

## AP-07 Initial Grouping Binding

**Version/status:** initial-grouping 1.0, frozen for AP-07 under [D-119](../authoritative-plan.md#ap-07-contract-freeze-proposal). **Owner:** Grouping; integration owns acceptance transaction participation.

For each newly accepted Transmission, AP-07 applies the exact C-02 identity and C-03 initial-membership rules under the captured active Grouping-policy revision. `W=0` creates a distinct Message per independent Transmission; otherwise exact matches use the inclusive whole-second Observation-time window and chain connectivity. Membership and any merge, contribution reconciliation, representative selection and required facts commit atomically with the acceptance. Configuration changes do not regroup prior members; heuristic comparison and historical regrouping remain excluded.
