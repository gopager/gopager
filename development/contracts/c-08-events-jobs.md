## AP-05 Transaction Participation

**Version/status:** transaction-participation 1.0, frozen for AP-05 under D-35 on 2026-10-26; the event/job engine and its wire/schema details remain 0.1-draft. **Owner:** Delivery domain for mechanics, producing domain for meaning, integration for the commit boundary. **Producers/consumers:** domain repository and outbox repository adapters in one C-12 transaction; later worker/consumer implementation. Vocabulary: glossary G-1.0.

`AppendDomainEvent` accepts the caller's [opaque transaction capability](c-12-persistence-operations.md#transaction-and-repository-participation), not a second connection or independently committed transaction. State and required fact/work persist atomically; failure of either participant aborts the unit. Downstream dispatch/wakeup may occur only after a known committed result; a wakeup is optional and never replaces durable work. A callback is never silently replayed by the platform. Unknown commit outcome remains uncertain and uses operation-owned receipt/dedup lookup before new work.

The platform supplies cancellable primary-store operations and current-clock/CAS test seams, not a globally ordered job engine. Any later claim/renew/complete repository must atomically check matching positive Fencing token plus unexpired primary-clock deadline under the existing shared lease rules; a controllable test clock does not replace production primary authority. AP-05 demonstrates the primitive through synthetic rows and [F-46e](reference-cases.md#ap-05-foundation-cases), without creating production event/job tables, claiming Delivery correctness or transferring schema ownership.

**Permissions:** Recording a Domain event does not replace current consumer/Delivery authorization. Raw Payloads are not browser/plugin grants. Retain rematch/retention/Delivery receipts so ordinary replay/restart does not revive deleted or expired work. Manual restoration of older store state is the Operator's responsibility under C-12/D-31. Domain event type/schema codes are language-independent.

## PostgreSQL Fact Publication

**Version/status:** postgresql-fact-publication 1.0, frozen and implementation-approved on 2026-11-02 by [D-94](../authoritative-plan.md#watermill-postgresql-publication-integration-proposal). **Owners:** Delivery/integration for transport/transaction participation; producing domains retain fact meanings. **Producers:** identity/master-data/Processing appenders. This version implements publication, not production consumption; consuming APs own the latter.

The existing typed producer ports and canonical envelopes remain unchanged. Every successful append writes its canonical `domain_events` row and one Watermill transport reference in the same live caller transaction. Transport topic and reference serialization are owned by [the infrastructure reference definitions](../../internal/persistence/ent/eventstore/transport.go); reviewed physical storage is owned by [the central migration](../../internal/persistence/migrations/00008_fact_transport.sql). Transport UUID equals canonical fact ID. No classified envelope, source Payload or authorization snapshot is copied to transport metadata. Publication failure aborts the producing unit; no independent connection, post-commit relay, optional transport fallback or automatic callback replay is permitted.

The adapter accepts only the caller's validated store-owned capability and never owns its commit/pool. Schema initialization is migration-only. Existing migration-history checks reject an unapplied/unknown suffix; missing or incompatible physical transport storage must fail publication explicitly, not trigger runtime DDL or silently drop a fact. Unknown commit outcomes keep C-12's existing uncertainty and producer-owned receipt lookup; publication does not create another operation-level receipt.

Only newly appended facts receive references. No historical backfill, automatic reprocessing or record cleanup is included. Before a production consumer is enabled, its owner must bind canonical fact lookup, unknown-version/missing-reference failure, current authority/revision checks, receipt/result/required-work atomicity before transport Ack, start/catch-up policy, retention and lifecycle/error handling. Transport offsets alone are not domain idempotency, job status or proof of a downstream outcome. PostgreSQL transport is at-least-once at the application boundary; a consumer crash after effect commit and before durable Ack can redeliver. SQLite runtime delivery remains outside this subset under D-93.

**Producer domain values:** `producer.domain` is the lowercase domain identifier from [Domains and Data Ownership](../architecture.md#domains-and-data-ownership), never a numbered domain ID. The domain named in the `/ producer` column below is the domain with that identifier.

### AP-07 Intake Fact Binding

**Version/status:** intake-facts 1.0, frozen for AP-07 under [D-119](../authoritative-plan.md#ap-07-contract-freeze-proposal). **Owners:** producing domain for fact meaning, Delivery/integration for append and transaction mechanics.

AP-07 appends the applicable `operation.submission-rejected`, `operation.observation-time-implausible`, and `operation.network-ambiguous` facts without original Payload; `gateway.state-changed` only on effective state transitions under D-116; `message.created`, `message.transmission-joined`, and `message.merged` for initial membership changes; `assignment.changed` only for actual target-resolution/contribution transitions; and `processing.completed` only when publication completes. Each required fact and its originating state/work change commit atomically. Exact envelope and per-type data remain those defined above; this slice does not start a general subscriber or external reaction.

One exact bridge transaction records one `message.merged` fact with survivor and the sorted absorbed-reference list, plus one `message.transmission-joined` for the newly accepted member; no new `message.created` for the survivor. Facts from that atomic change may share the final aggregate revision and have no required order within it. Consumers deduplicate each fact and reconcile current authorized state rather than depend on merge-before-join delivery. Under D-40 no alias chain or enduring Message identity is required; an invalidated reference is not permission to guess another Message or silently report successful processing. Across revisions, detect stale/superseded state; a provider can still observe different completion order. No hidden global sequencing field or exactly-once provider order is required.

**Claim/fencing:** Short primary transaction selects available due work, checks role, increments Fencing token and sets lease deadline. Renew/complete/reschedule require matching job/token and nonexpired lease. A lost Worker cannot publish stale target resolutions/contributions or terminal results over a successor. Lease expiry before external start permits reclaim; expiry after a recorded external start produces `uncertain` unless a provider-supported idempotency/receipt proves safe recovery. Never hold SQL transactions across plugin/provider I/O. Store driver locking/isolation/wake-up mechanism is AP-03, not a second semantic job implementation.

**Retry/recovery:** Idempotent internal derivation gets at most 5 automatic attempts (30 s/2 min/10 min/30 min delays with bounded jitter), then visible failed work; an authorized retry targets the current revision.
