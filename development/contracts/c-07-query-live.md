## Implemented behavior (specified in `docs/` and OpenAPI)

Platform failure classification and the PostgreSQL SQLSTATE mapping: [Architecture: Errors and failure codes](../../docs/architecture.md#errors-and-failure-codes).

AP-10 Query, live and saved views (implemented 2026-11-08, [AP-10 record](../execution/ap-10.md#handover)): appearance eligibility, field groups, filters, PostgreSQL text search, order, HMAC keyset page token, snapshot cutoff `position`, projections (Representative Transmission, Unit summaries, encrypted label, correction and processing status, target resolutions, derived results, `networkUnresolved`) and filter options: [HTTP API: Messages: query and detail](../../docs/http-api.md#messages-query-and-detail); positions, frames, fact handling, bounds, replay window and resync: [Messages: live stream](../../docs/http-api.md#messages-live-stream); [Saved views](../../docs/http-api.md#saved-views); [Search rate limiting](../../docs/http-api.md#search-rate-limiting); keyset paging: [Pagination](../../docs/http-api.md#pagination); data flow: [Architecture: Query](../../docs/architecture.md#query-api-role); flags `--search-attempts-per-minute`, `--live-replay-window`: [Operations](../../docs/operations.md#configuration-reference). Cases: [AP-10 query and live cases](reference-cases.md#ap-10-query-and-live-cases).

Binding rules for every response: codes are stable and language independent; Product-generated outcomes carry `error.<CODE>` or `status.<status>` text keys with a redacted English fallback and structured parameters; no client parses prose; UI language and formatting locale change no ID, field name, enum, timestamp, token or authorization outcome; invisible, deleted or invalidated references share one `NOT_FOUND` shape and never expose a replacement ID.

## Planned and not yet implemented

**Selection predicate and attributes ([D-152](../decisions/07-query-and-live.md#d-152), [D-150](../decisions/04-processing-and-plugins.md#d-150), [AP-21](../work-packages/ap-21-attribute-schemas.md)):** Feed, live stream and saved views accept a `filter` holding the typed predicate of [C-09](c-09-delivery.md#typed-predicates-and-values-implemented) over field-registry fields, compiled to SQL; the simple filter parameters stay, the `derived` parameter is removed, and a saved-view `definition` stores the predicate. Message attributes are addressed as `attributes.<schemaKey>.<field>[.<property>…]` and match the effective value of any target position the caller may see; Unit attributes ([AP-22](../work-packages/ap-22-unit-attributes.md)) as `unit.attributes.<schemaKey>.<field>…` and match on the Message's eligible Unit appearances, correlated with the same appearance like the other Unit dimensions (REQ-029). Only paths to scalars and lists of scalars are filterable (any-element semantics). An unknown field or a non-filterable path is `INVALID_INPUT`, and a predicate needing an unreadable field group is rejected as the `derived` filter is today (REQ-017). Projections show the effective Message attributes with their provenance (`workflowId`, `definitionVersionId`, `resultId`) and the Unit attributes. A typed projection table of effective values is added only when AP-21's measurement shows the gain.

**AP-21 binding (planning before coding, 2026-11-11):**

Status: implemented by AP-21 on 2026-11-11 ([handover](../execution/ap-21.md#handover)); the permanent documentation ([HTTP API](../../docs/http-api.md), [Workflows](../../docs/workflows.md), [OpenAPI](../../api/openapi/v1.yaml)) owns the implemented fields, states and errors.

- **Encoding.** `GET /messages` and `/messages/stream` accept one `filter` query parameter holding the predicate as JSON (at most 32 KiB encoded, the predicate limits of [C-09](c-09-delivery.md#typed-predicates-and-values-implemented)); it combines with the simple parameters by AND. A saved-view `definition.filters.filter` stores the same predicate; `filters.derived`, the `derived` parameter and the `derived` value of `unavailableFilters` are removed (a predicate needing an unreadable group reports `filter`). The saved-view `schemaVersion` stays 1 (unreleased format). The canonical filter form gets `"v":2` and the canonical predicate JSON, so earlier page tokens are rejected as `INVALID_INPUT`.
- **Semantics.** Each field reference resolves to a set of candidate scalar values: absent values contribute nothing, a list field contributes its elements, an attribute contributes the effective value of every visible position. A comparison (`eq`, `in`, `lt`, `lte`, `gt`, `gte`, `contains`) holds when one candidate satisfies it; `present: true` holds when the set is not empty, `present: false` when it is empty; `and`, `or`, `not` are two-valued. `contains` is a case-sensitive substring test (the `text` parameter keeps its case-insensitive search). Delivery filters use the same Go evaluator (`fields.Match`), and the read store compiles the same rules to SQL; one parity test runs every operator through both.
- **Fields in scope `message`.** `message.id`, `message.time`, `message.processingStatus`, `message.correctionStatus` (no group); `message.protocol`, `message.form`, `message.text`, `message.numeric` (`payload`, from the representative Payload as in the projection); `message.unitIds`, `message.unitNames` (`unit`, the caller's eligible Unit appearances); `attributes.<schemaKey>.<field>[.<property>…]` (`derived`).
- **Effective values.** Candidates are the published results of the Message's supporting eligible Transmissions whose stored `field_groups` the caller may read. Per schema field and position — untargeted, or a target position whose target the caller may see under the existing target-visibility rule — the effective value is the present value of the latest result (`published_at`, then result ID). A property path descends into object values (`value->'<name>'`).
- **Projection.** `FeedItem.derived` is replaced by `attributes`: a list of `{schemaKey, field, targetPosition?, unitId?, value, workflowId, definitionVersionId, resultId, publishedAt}` sorted by key, field and position (`unitId` is the target's assigned Unit when the caller may see it). It appears only with `derived` readable, as before.
- **Measurement (T094).** Seed 100,000 Messages (one Transmission each, two Workflows writing two schemas, 20 % target-scoped results, 10 Units) in PostgreSQL 18 and record `EXPLAIN (ANALYZE, BUFFERS)` and the median of 20 runs for: a feed page without filter, with a string `eq` attribute filter, with an integer range, and the detail of one Message. A typed projection table of effective values is adopted when a filtered feed page takes more than 100 ms or more than three times the unfiltered page; otherwise it is recorded as not adopted with the numbers.
- **T094 result and projection (2026-11-11).** Measured on PostgreSQL 18.0 with 100,000 Messages (AP-21 record): unfiltered page 95 ms, string `eq` attribute filter 2.4 s, integer range 3.5 s (median of 20) — far above the threshold, because the effective-value check runs as a subquery for every Message before the page is cut. Adopted: the typed projection `message_attribute_values` (in `00014_attribute_schemas.sql`, owned by the Processing domain, written in the publication transaction): one row per published result, schema, scalar path (`field` or `field.property…`; list elements one row each) and position, with `transmission_id`, `result_id`, `target_position` and one typed column per scalar kind, indexed by schema, path and value. It holds every published value, not the effective one, because the effective value depends on what the caller may see. The SQL compiler derives from the predicate a necessary condition — `eq`, `in` and ordered comparisons on attribute fields become an indexed lookup of Message IDs through `transmissions`; `and` takes any operand's condition, `or` only when every operand has one; `not`, `present` and `contains` have none — and adds it before the unchanged exact effective-value check, so results stay identical to T093.

**AP-11 (planning before coding):** Delivery uses the read side under the subscriber's resolved authority inside the consumer or runner transaction (`readmodel.Service.ProjectForDelivery`), with the same eligibility, field groups and readable result versions as the feed, plus the per-Unit first observations needed for Delivery age anchors; it adds `DEPENDENCY_UNAVAILABLE` (redelivery after the original input ceiling) and `EXTERNAL_UNCERTAIN` (retry of an uncertain Delivery). `CAPABILITY_UNDECLARED` stays with AP-12.

**Error codes:** `DEPENDENCY_UNAVAILABLE` (parameter `dependency`) and `EXTERNAL_UNCERTAIN` (parameter `deliveryId`) are implemented by AP-11 ([HTTP API: Errors](../../docs/http-api.md#errors)). Not implemented yet: `CAPABILITY_UNDECLARED` (403, permitted capability name), added by AP-12 together with its English fallback text and parameters. Plugin handshake and transport failures are `DEPENDENCY_UNAVAILABLE` and a crash is `INTERNAL_ERROR` once the plugin host maps them. Outcome statuses map to `status.<status>`. C-11 owns the text-key registry. Resync is the live `resync-required` event, not an HTTP error code.
