## Implemented behavior (specified in `docs/` and OpenAPI)

Routes and schemas: [OpenAPI v1](../../api/openapi/v1.yaml) (`info.version` 1.7.0), tags `Workflows` and `Processing instances`; route table and rights: [HTTP API: Processing](../../docs/http-api.md#processing-workflows-versions-candidates) and [Processing: plugin instances](../../docs/http-api.md#processing-plugin-instances). Semantics, all in [Workflows](../../docs/workflows.md): definition format, selector, steps (map, Core RE2 extract, branch, installed), field schema and typed values ([Definition format](../../docs/workflows.md#definition-format)); predicates and bounds ([Predicates](../../docs/workflows.md#predicates)); result shape with `fields` or `targetResults`, one run per Transmission and Workflow, namespaces that never overwrite another Workflow's fields ([Result shape](../../docs/workflows.md#result-shape)); one classification per definition version, applied at projection ([Classification](../../docs/workflows.md#classification)); save-time validation against the author's readable field groups ([Validation](../../docs/workflows.md#validation)); lifecycle, versions, atomic activation and previous-version selection, no automatic historical sweep ([Lifecycle](../../docs/workflows.md#lifecycle)); preview without live writes, events or external effects ([Preview](../../docs/workflows.md#preview)); admission, dispatch, candidate states, retries, stale-work supersession, publication and `processing.completed` ([From transmission to candidate](../../docs/workflows.md#from-transmission-to-candidate) to [Events](../../docs/workflows.md#events)); status reads and the processing status `none | pending | completed | failed` without a publication barrier ([Status reads](../../docs/workflows.md#status-reads), [Architecture: Processing status](../../docs/architecture.md#processing-status)); limits ([Limits and defaults](../../docs/workflows.md#limits-and-defaults)). Typed code: [`internal/processing`](../../internal/processing/).

Decisions that remain binding: no arbitrary inline scripts, loops or expanded permissions; saving and taking effect are distinct without a mandated multistage approval; concurrent edits conflict instead of overwriting; original Payload is preserved and processing or presentation version changes create no Transmission and no regrouping; derived fields keep their classification and extraction does not make hidden text public; installed code receives only its declared authorized input under the configured execution Principal, never the editor's temporary rights, and a missing execution authority is an explicit failed or pending state; a failed Workflow leaves the status `failed` with authorized retry and never substitutes raw text; the Core regex is Go RE2 with deterministic admission bounds (D-129) and an inadmissible pattern is `RESOURCE_LIMIT`.

## Presentation and Configuration (planned)

- **Layout definition (REQ-094, D-135).** GUI cards and Delivery renderings share one declarative, versioned layout definition with the blocks `text`, `field`, `chip`, `link` (URL template), `section`, `conditional` (the C-09 typed predicate) and `fallback`, rendered by the frontend and by the Core, never as raw HTML and without a template engine ([D-135](../decisions/10-foundation-redesign.md#d-135)). A definition has ID, revision, immutable version, applicable permitted scope, typed field bindings and an output kind (GUI card or Delivery text or structured input). AP-11 implements the declarative block renderer, the validator, persisted `layout_definitions` with `presentation.manage` CRUD and the Subscription layout reference, AP-13 the GUI card adapter, the card model and editor metadata and AP-15 the editor; rendering is bounded by the shared output, nesting and collection limits and escapes interpolation for its output context.
- **AP-11 layout binding (planning before coding, 2026-11-09).** Layout 1.0: `{"schemaVersion": 1, "outputKind": "text" | "markdown" | "json", "blocks": [...]}`. Blocks: `text` (`text` literal), `field` (`field` reference, optional `label`), `chip` (`field`, optional `label`), `link` (`label`, `url` template with `{0}`..`{9}` placeholders and a `fields` list; values are percent-encoded except for RFC 3986 unreserved characters and `@` (so `&`, `=`, `+`, `/`, `?` and `#` in a value never change the URL structure), the expanded URL must be `https`, `http` or `mailto`, else the link is omitted), `section` (optional `title`, `blocks`), `conditional` (`when` typed predicate, `then`, optional `else`), `fallback` (`blocks`: the first alternative that renders non-empty; a present but empty or control-only, unlabelled value renders nothing in every output kind, and output without content of an alternative being tried counts against the output bound only once that alternative is chosen, while everything a render holds, rendered items and every looked-up value including those of discarded alternatives, is bounded to 1 MiB). Field references use the Delivery field catalog of [C-09](c-09-delivery.md#ap-11-core-binding-planning-before-coding); an absent field renders nothing. Bounds: 256 blocks, nesting 8, literal 4 KiB, output 64 KiB (`RESOURCE_LIMIT` at save, `render-limit` at materialization). Output: `text` writes plain lines with control characters other than newline removed; `markdown` escapes Markdown metacharacters (including `~`, `=` and `&`) in every interpolated value and backslash-escapes `&` in link destinations; `json` emits an ordered array of `{kind, label, value | text | url | items}` objects with typed values. Values format as: string verbatim, numbers in decimal, booleans `true`/`false`, timestamps RFC 3339 UTC, bytes canonical Base64, lists comma-separated, objects compact JSON. No HTML output, no template engine. Persistence: `layout_definitions` (ID, revision, name, output kind) with immutable `layout_definition_versions` (layout, version = revision, definition); routes `GET/POST /layouts`, `GET/PUT/DELETE /layouts/{id}`, `GET /layouts/{id}/versions/{version}` with `presentation.manage` (scope `all`) for writes, readable also for `subscription.manage-own` and `subscription.manage-global` holders; a referenced layout cannot be deleted (`409 REVISION_CONFLICT`). `processing.LayoutResolver` returns the Subscription's layout at its current version, otherwise the built-in default of the requested output kind (version 0); the Delivery records the layout ID and version it rendered. Saving a layout checks only structure; field rights are checked when a Subscription references it.
- **Safe output.** GUI card models support text, labeled structured sections, icons, links and buttons, and configured map references. Missing permitted location fields fall back to permitted original text under explicit conditions, never hidden alternate evidence. No browser script or untrusted HTML; icons are sanitized, unsafe URL schemes and event handlers are rejected. Administrator-defined external links and maps may deliberately transmit permitted parameters (D-25) and their external origin is visible. A preview makes no outbound request.
- **Precedence** ([D-151](../decisions/06-identity-and-authorization.md#d-151): an Organization or Unit default must be a Layout assigned to the Unit's Agency; an Organization default applies only to its Units in the Layout's Agencies) is fieldwise: installation default, then Organization, then Unit, then Subscription. AP-11's resolver knows the Subscription layout and a built-in default; AP-13 binds the installation default (in `installation_settings`) and the Organization and Unit assignments (table `layout_assignments`, no change to C-04) into it. Conflicting whole layouts from several Units are resolved by explicit choice or separately scoped sections, never by iteration order or by combining hidden Unit settings. Personal formatting preferences never widen field rights or alter source results.
- **Displayed source.** GUI rendering consumes the readable exact Representative Transmission of [C-03](c-03-message-grouping.md), never a global text or concatenated originals; a restricted view's fallback never inherits fields derived only from hidden evidence; presentation uses the Representative Transmission and shows that Transmission's completed results or its `processing_status`, never results derived from another member.
- **Installation banner ([D-135](../decisions/10-foundation-redesign.md#d-135) item 15).** Installation title and banner are one revisioned `installation_settings` row: title, optional plain-text banner, optional severity and the default layout reference. It is edited with `notice.manage` and `expectedRevision` through `GET/PUT /api/v1/installation` (read is public, including guests) and shown to everyone while set; there is no dismissal, no notice ID and no audience.
- **Preferences ([D-142](../decisions/09-process-and-documentation.md#d-142)).** Account preferences are the formatting locale, the IANA time zone and the time-gap threshold in minutes (0 turns it off, range 0..1440), with ordinary revision checks under the action `preference.manage-own`; there are no Delivery defaults here (Delivery configuration stays in C-09). Invalid locale or time zone input is explained, never silently replaced; the UI language is English initially. Text, touch and keyboard operation, states readable without color and context-preserving copy and details are frontend acceptance goals.

## Attribute Schemas and Agency Binding (planned)

Status: implemented by AP-21 on 2026-11-11 ([handover](../execution/ap-21.md#handover)); the permanent documentation ([HTTP API](../../docs/http-api.md), [Workflows](../../docs/workflows.md), [OpenAPI](../../api/openapi/v1.yaml)) owns the implemented fields, states and errors.

- **Attribute schemas ([D-150](../decisions/04-processing-and-plugins.md#d-150), [AP-21](../work-packages/ap-21-attribute-schemas.md)).** An Attribute schema has an immutable, installation-wide unique `key`, `label`, `description`, `subject` `message | unit`, `fields` (name → `FieldSchema` with `label`, `description` and optional `icon` at every level; display metadata is kept beside the type so that compatibility checks compare types only), `agencies`, `revision` and `deprecated`. Limits are those of `FieldSchema`. Allowed changes: add optional fields or properties, deprecate (hidden from new references, still readable), edit display metadata; anything else needs a new schema. A schema is deleted only when no active Workflow version, Layout, Subscription, saved view or Unit value references it. AP-21 records the key syntax here.
- **Workflow outputs ([D-150](../decisions/04-processing-and-plugins.md#d-150)).** `outputSchema` is removed; `outputs` maps `<schemaKey>` → `<field>` → Assignment into `message` schemas, typed from the schema. Top-level fields are optional for every producer; nested required and optional properties are unchanged. The result shape (`fields`, `targetResults`) is keyed by schema and field. Step outputs stay internal. Several Workflows may write the same field; the effective value per Message, field and target position is the latest published one (`published_at`, then result ID) and carries its provenance. Classification is unchanged ([D-148](../decisions/04-processing-and-plugins.md#d-148)), with the known limitation recorded in D-150.
- **Agency binding ([D-151](../decisions/06-identity-and-authorization.md#d-151)).** Workflow scope is `{"agencies": [...], "narrowing": null | {"kind": "network" | "unit", "references": [...]}}`; narrowing references must belong to the assigned Agencies. A Transmission is admitted when its resolved Network's Agency is assigned and the narrowing covers it. Layouts carry `agencies`. Management, lists and Agency deletion follow [C-06](c-06-identity-authorization.md#planned-and-not-yet-implemented) and [C-04](c-04-master-data.md#planned-and-not-yet-implemented).
- **Layout field defaults ([D-150](../decisions/04-processing-and-plugins.md#d-150)).** `field` and `chip` blocks take their label and icon from the registry field (Attribute schema or built-in field); a block `label` or the new optional block `icon` (Unit icon identifier rule) overrides them. Icons are presentation hints for GUI card output; `text` and `markdown` renderings ignore them and `json` may include the identifier. Display metadata resolves at render time, so editing it changes renderings without a new Layout version.

### AP-21 Binding (planning before coding)

Recorded 2026-11-11 by AP-21 T092 before coding. Where it refines a bullet above, this section wins.

- **Key and names.** A schema `key` is 1..64 bytes of `[a-z0-9-]` starting with a letter. Field and property names are 1..64 bytes of `[A-Za-z0-9_]` starting with a letter, so dotted references are unambiguous. `label` is required for the schema (1..256 characters) and optional for fields (the client falls back to the name); `description` has at most 2048 characters; `icon` follows the shared icon rule (`internal/icons`, moved from the Unit settings); a schema has 1..1000 fields and 1..256 distinct Agencies; types obey the `FieldSchema` limits (depth 32, 1000 properties per object).
- **Field JSON.** A field is a `FieldSchema` object (`kind`, `optional`, `nullable`, `properties`, `element`) with `label`, `description`, `icon` and `deprecated` in the same object. Top-level fields carry no `optional` (they are always optional); list elements cannot be deprecated. `attributes.CheckChange(current, next)` is the executable compatibility rule: key and subject unchanged; nothing removed; every existing field and property keeps `kind`, `nullable`, `optional` and element type; added top-level fields and added optional properties (at any depth, including inside list elements) are allowed; display metadata, deprecation and Agencies may change.
- **Deprecation.** A deprecated schema, field or ancestor property is not offered for new references: saving a Workflow version, activating it, saving a Layout, Subscription or saved view, and running a feed or live query that references it are `INVALID_INPUT`. Existing values stay in projections. The evaluation of an already active Workflow version still compiles against deprecated fields, so processing never stops on a deprecation; a Subscription whose filter or Layout references a deprecated field becomes `invalid` with `field-unavailable` at its next fan-out ([C-09](c-09-delivery.md#planned-attribute-references-and-subscription-health)).
- **Delete.** `DELETE` needs `attribute-schema.manage` in every assigned Agency and fails with `409 REVISION_CONFLICT` while a reference exists: an active Workflow version whose `outputs` names the key, a Layout's current version, a Subscription filter or a saved-view definition containing a field reference `{"namespace":"attributes","path":[key,…]}` (checked with `jsonb_path_exists`), and later Unit values (AP-22).
- **Tables.** New migration `00014_attribute_schemas.sql`: `attribute_catalog` (control row with the registry `revision`, incremented by every schema change), `attribute_schemas` (`key` primary key, `revision`, `label`, `description`, `subject`, `fields` jsonb, `deprecated`, `created_by`, `created_at`, `updated_at`) and `attribute_schema_agencies` (`schema_key`, `agency_id`, cascade on both). Edited in place: `00006_processing_kernel.sql` replaces `processing_workflows.scope_kind` by `narrowing_kind` (`network | unit | NULL`) and adds `processing_workflow_agencies` (`workflow_id`, `agency_id`, cascade on both); `00013_events_delivery.sql` adds `layout_definition_agencies` (`layout_id`, `agency_id`, cascade on both).
- **Workflow scope.** `agencies` holds 1..256 distinct Agencies; `narrowing.references` 1..1024 distinct Networks or Units, each belonging to an assigned Agency, and with a narrowing every assigned Agency must contain at least one reference. Admission and the candidate source owner select `enabled`, active, undeleted Workflows having an `agencies` row for the resolved Network's Agency and, when narrowed, a reference to that Network or to a Unit of the match; Unit narrowing keeps restricting the evaluated target positions to the referenced Units.
- **Workflow authorization.** Without narrowing, the action is checked against every assigned Agency (`authz.Target{AgencyID}`); with narrowing, against every reference (Network: its Agency; Unit: Agency, Unit and collections). Update checks the union of the stored and the new set, delete the stored set. A Workflow is readable and listed when the caller's `workflow.read` matches one assigned Agency (grant scope `all` or `agency`) or, for Unit narrowing, one referenced Unit (`unit`, `unitCollection`).
- **Layouts.** `agencies` (1..256) is required on create and update. Managing needs `presentation.manage` in every Agency involved (stored and new). Lists and reads return a Layout when the caller holds `presentation.manage` or `message.read` in one assigned Agency (scope `all`, `agency`, or a `unit`/`unitCollection` grant on a Unit of that Agency); the same right lets a subscriber choose the Layout ([C-09](c-09-delivery.md#planned-attribute-references-and-subscription-health)).
- **Workflow outputs and results.** `Definition.Outputs` is `map[schemaKey]map[field]Assignment`; `outputSchema` is removed and `schemaVersion` stays 1 (unreleased format, [D-128](../decisions/01-platform-and-storage.md#d-128)). Output keys must name `message` schemas. A result stores only present values (an explicit null counts as present) as `{"selected": true, "fields": {schemaKey: {field: FieldValue}}}` or `targetResults[].fields` of the same shape; an absent output writes nothing and therefore never replaces an earlier value. `ValidateEvaluation` checks results against the schemas current at publication.
- **Field registry.** `internal/fields` declares `Field{Ref, Type, Group, Filterable, Label, Description, Icon, Deprecated, Scopes}` with scopes `workflow` (source and target fields), `message` (search, live, saved views) and `delivery` (Subscription filters and Layouts). `Filterable` means a scalar other than bytes, or a list of such scalars. Providers: the built-in provider (the former Processing source declarations and Delivery catalog) and the attribute provider in `internal/attributes`, built from the schema catalog of one registry revision. `fields.Registry` implements `processing.Declarations` and `processing.FieldGroupDeclarations` for one scope; a strict mode rejects deprecated fields. Attribute fields belong to group `derived`; the result's stored groups apply on top as before.

## Historical Reprocess (planned)

`Reprocess` (action `workflow.reprocess`) with a scope of the Workflow selection scope (its assigned Agencies, optionally narrowed to Networks or Units, [D-151](../decisions/06-identity-and-authorization.md#d-151)) intersected with an explicit Message-time range and the chosen version is not implemented; `workflow.reprocess` is authorized over the Unit and Agency scopes of the affected Transmissions and the stable scan cutoff is the maximum accepted Transmission sequence at request time; the retry of a single failed candidate is. It uses current access and target state, preserves original Payload and membership, publishes replacement results atomically after success, and never keeps a result visible merely because it existed once if the source authority is invalidated. Reprocess publishes `processing.completed` with `replayMode` `reprocess`, which suppresses automatic Delivery fan-out (AP-11 owns the vocabulary in C-08); redelivery is C-09's separately confirmed operation. AP-13 owns it.

## Text-key Mapping and Remaining Technical Evidence

The implemented API error-code and fallback table is [HTTP API: Errors](../../docs/http-api.md#errors); [C-07](c-07-query-live.md) lists the codes still to be added. C-11 owns `status.<status>`, `validation.<constraint>`, `processing.<reason>` and component/action/accessibility keys. Registry entries require an English base string, typed named parameters and plural forms when count-dependent; CI in AP-15 checks every referenced built-in key/parameter against the catalog. Validation constraints reuse shared names (`required`, `type`, `range`, `maxLength`, `pattern`, `reference`, `cycle`); processing reasons include `no-match`, `conversion-failed`, `capability-unavailable`, `resource-limit` and `evaluation-failed`. Missing optional output is not displayed as failure.

A missing translation uses the English entry; a missing key/invalid parameter emits a redacted diagnostic and safe generic English text, never the confidential raw argument or an untranslated key. New built-in status/constraint/reason values require their English entry in the same change. Trusted operator templates and received data are not automatically translated. Exact component wording, the Vue i18n library and editor controls are AP-15 implementation artifacts, not a requirement for another locale.

| Text keys (one entry per listed suffix) | English base entries, in the same order |
| --- | --- |
| `status.pending`, `.running`, `.completed`, `.failed`, `.superseded` | Pending; Running; Completed; Failed; Superseded |
| `status.prepared`, `.started`, `.retry-pending`, `.accepted`, `.expired`, `.cancelled`, `.uncertain`, `.dependency-unavailable` | Prepared; Started; Retry pending; Accepted by provider; Expired; Cancelled; External outcome uncertain; Required data unavailable |

Validation parameters are typed `field`, `constraint`, `limit` as applicable. Count-dependent component keys declare an integer `count` and English singular/other forms (for example `{count} item` / `{count} items`), not concatenated fragments. Component/action labels are populated with their implementing UI, not a speculative catalog of screens.
