**Defined:** Subscriptions explicitly select Domain event types, correlated domain/Processing-result filters, one or more Delivery targets, and permitted template/input fields; multiple instances of one plugin remain separate. There is no global Unit-to-Delivery-target mapping. Per-Unit `integration_unit_parameters` values can parameterize a Subscription's filter/template/input, never introduce a destination implicitly. Pause/removal, Principal suspension/deletion, current grant revocation, and age limits prevent new unauthorized attempts.

Before every new attempt, authoritatively check current Principal, subscription, filters, assignments/suppression, and field permissions. A stored old ready-to-send Payload is not authorization. Preparation, execution, and recording are distinguishable; provider acceptance is neither reading nor recallability.

**Uncertainty:** A lost provider response may follow an already executed effect. Do not disguise it as definite failure/success or blindly repeat indefinitely. Bounded retries require failure classification and current permission; permanent/transient/uncertain outcomes remain separate. Deliberate redelivery names duplicate-effect risk. Use provider idempotency only when actually supported.

**Consistency boundary:** No SQL transaction around long external I/O. The attempt section below defines authoritative start/revocation and preparation races; an already started provider effect cannot be recalled.

## AP-02 Subscription and Plugin-input Contract

Subscription: ID/revision, owning Subscriber, personal/global kind, explicit nonempty Domain event type set, filter definition, permitted Delivery target references, template/input mapping version, active/paused state, creation/start time and optional additional maximum age. Global Subscription requires `subscription.manage-global` and an assigned technical Principal with explicit delegated data/target rights. Personal Subscription acts as its User. A creator's temporary admin status is never captured as unrestricted sending authority.

**Plugin reaction direction (REQ-139, D-130/D-131):** This is not frozen; AP-11 owns the binding. A Subscription's target is a typed reference, so a later plugin reaction capability of a configured plugin instance can be a target kind next to Delivery targets. Such reactions use global Subscriptions under a technical Principal and may select permitted event types of any domain, for example account lifecycle or Unit configuration. They reuse the attempt, retry, uncertainty and current-authorization rules of this contract. Reactions read further Core data through the versioned HTTP API as that Principal.

**Filters:** Reuse the C-07 dimension rules and typed predicates: equality, membership, presence, numeric/time comparison, literal substring, AND/OR/NOT with bounded nesting. Values are typed and namespaced; missing/hidden fields do not pass a positive predicate, and negation must not reveal hidden-field presence. Evaluate on an authorized projection, not original data. `processing.completed` with permitted `level >= 2` is a valid explicit selection. Workflow trigger selection uses the same predicate representation, not a second ad-hoc expression language. No arbitrary code in a filter.

Predicate evaluation is ordinary two-valued logic run as the system: there are no hidden operands and no indeterminate value, AND, OR and NOT are boolean, absent optional fields make comparisons false, and a human reader's rights are checked at save time against the fields a definition references, not during evaluation. Malformed typed comparisons are validation errors, not coerced strings or silent defaults.

### Typed predicates and values (implemented)

The structured predicate (`eq`, `in`, `present`, `lt`, `lte`, `gt`, `gte`, `contains`, `and`, `or`, `not`), the typed values including canonical Base64 `bytes`, the closed schemas, field references (namespace plus path segments, never an expression string), the restricted CEL-Go evaluation, the bounds and the per-definition classification are specified in [Workflows: Predicates](../../docs/workflows.md#predicates), [Typed values](../../docs/workflows.md#typed-values) and [Classification](../../docs/workflows.md#classification); typed code is in [`internal/processing`](../../internal/processing/). Subscriptions bind their own event and result namespaces to this same representation and add no second expression language. Target fields resolve on one correlated target context per predicate.

### Subscription Target and Input Selection

**Target selection:** A Subscription can select one or several configured target instances, including a provider-side channel or collection such as Telegram channel/chat or Pushover group key. Personal recipient selection follows the [configuration-authority boundary](#configuration-authority); subscription rights never create an integration. A dynamic selector may select from an explicitly delegated configured target pool using permitted structured data; it cannot turn untrusted Payload into an arbitrary undelegated URL/contact/Secret. An admin may explicitly configure a template-driven external destination under the SDK transport policy of C-10 (including `allowPrivateDestinations`) and delegated data rights; that is deliberate configuration, not an implicit global Unit mapping.

**Target instance identity (AP-11, D-131):** There is one instance concept. A Subscription target reference is `(instanceId, capability kind, revision)` where `instanceId` is `processing_instances(id)`; `integration_unit_parameters.instance_id` is a foreign key to the same table. AP-11 tests create instances through the existing instance store with a controlled-provider descriptor; AP-12 adds the Delivery capability kind, personal values and Secrets. A missing, disabled or unloadable target is rejected at Subscription create and update with `AUTHORITY_UNAVAILABLE` and status `unavailable`.

**Layout reference (AP-11):** A Subscription may reference a layout definition ([C-11](c-11-processing-presentation.md#presentation-and-configuration-planned)); a `LayoutResolver` returns the Subscription layout, otherwise the built-in default. AP-13 adds the installation, Organization and Unit layers.

**Sending admission (REQ-108, AP-11):** Delivery has its own bucket in `internal/delivery/`: 60 per minute per Subscriber ([C-06](c-06-identity-authorization.md#planned-and-not-yet-implemented)) plus a target-instance cap from the descriptor, with flags documented in Operations. HTTP create and redeliver return `RATE_LIMITED`; background sends are deferred as `retry-pending` with a safe delay and a deferral does not consume an attempt. Shared-IP fairness does not apply to background sending.

**Overrides:** Unit-specific values in `integration_unit_parameters(instance_id, unit_id, key, value)` have plugin-declared type/validation and explicit permission ([D-135](../decisions/10-foundation-redesign.md#d-135) item 15; there are no Extension fields). Mapping/precedence is declared by the Subscription: common target configuration, then Subscription mapping, then explicitly selected Unit values. Conflicting values from multiple relevant Units must be resolved by an explicit split-per-Unit or explicit configured selection, never map iteration order. Split Deliveries contain only the corresponding permitted data, with split identity in deduplication. Provider/channel/Secret changes remain separately authorized target configuration, not a Unit-field shortcut.

**V1 responsibility split:** `MaterializeDeliveryInput` is Core-owned. On the selected trigger (for result-dependent reactions `processing.completed`), Core reads the currently authorized projection, evaluates filters/target selection/templates, validates plugin-declared input fields, and stores bounded Delivery input plus minimal scope/field/access/Assignment/Suppression revision context. Input is not an unbounded object copy. Plugin receives this input and its instance-bound configuration/Secrets; it need not load the original Message. Delivery plugins receive no other Core reads: a manifest declaring `requiredOperations` or `requiredCoreFields` for a Delivery capability is rejected with `CAPABILITY_UNDECLARED` (Core-read capabilities are REQ-139, later).

| Future SDK/input decision | Required behavior now specified |
| --- | --- |
| Materialized declared fields (selected v1) | Prepared self-contained work may finish after Message retention, if current checks can be completed from its minimal authorization context. Remove Payload copy on terminal completion, at latest 24 h from original Delivery creation. |
| Reference-only capability | If the referred evidence/configuration no longer exists or is not permitted, stop with `dependency-unavailable`; no fabricated empty object or fallback to stale unprojected data. |
| Projected object snapshot | Bounded copy with explicit field classification, authorization context and independent expiry, never full private entity serialization; same revocation/deletion checks as materialized input. |
| Plugin asks for other Units/Core data | Not implemented for Delivery (REQ-139, later). Any such declaration is rejected with `CAPABILITY_UNDECLARED`. |

This matrix is binding. Only the materialized-fields variant is implemented. Message retention only cancels work whose actual dependencies disappeared; it does not cancel a self-contained Delivery just because the original Message was deleted.

## Configuration Authority

**AP-04 D-33 clarification, 2026-10-26; Delivery with plugin-host/integration ownership; draft, not frozen.** Every integration requires configuration by an authorized administrator or Operator before Users can use it. Administrative authority is checked through C-06 (`plugin.configure`, global scope; there is no instance scope, [D-100](../decisions/04-processing-and-plugins.md#d-100)); personal subscription rights do not grant it. Installing/updating plugin code remains Operator-only under C-10, by placing artifacts in the plugin directory. Personal recipient values are written by the owning User under `subscription.manage-own`, bound to (instance, owner).

Administrative configuration owns provider/application credentials, enabled capabilities, message format/templates, transport/authentication settings and security policy. The administrator/Operator is responsible for selecting appropriate settings and consciously accepting configured external-transport risks. This responsibility does not grant access to other Principals' data or disable Core authorization, Secret redaction or the existing transport rules.

Where an integration supports individually addressable recipients, its declared schema may expose personal recipient fields. Users can supply/change their own recipient identifier or credential and configure their own Subscriptions using that administratively configured integration, within current data/target permissions. Personal settings are bound to the owning User and target instance; they cannot change administrative settings, another User's recipient or provider/application Secrets. Subscription mappings and Unit-field overrides cannot promote a personal field into an administrative override. Integrations without individual recipient support expose no such personal-recipient configuration; permitted Subscriptions still use administratively configured targets.

Each property's administrative or personal configurability must be declared in the plugin manifest under [C-10's configuration-field contract](c-10-plugin-host.md#implemented-behavior-specified-in-docs), which also owns SDK/API enforcement and invalid-declaration handling.

**Pushover:** The administrator/Operator supplies the application API token and defines the message format. Each User may supply their own Pushover User key and select their own Subscriptions. The personal User key does not create another application configuration or reveal/replace its application token. Both credentials use C-10 Secret handling; ordinary views return redacted status, not stored Secret values.

Who may use an instance as a Subscription target is declared by its administrative configuration and enforced at save, fan-out and start ([D-149](../decisions/05-events-and-delivery.md#d-149), AP-12); until then every enabled instance with a Delivery descriptor is usable by every Subscription manager. Missing/inactive administrative configuration prevents use with a visible configuration failure; no personal credential creates a fallback integration. Personal-recipient changes are revisioned target configuration and participate in the existing current-authorization/configuration checks before each new attempt. Concrete field schemas and validation/error fixtures remain freeze requirements. This clarification does not select an additional persistent entity or physical SQL schema.

## Initial Target Capabilities

**AP-04 D-33 amendment; Delivery with plugin-host/integration ownership; draft, not frozen.** Pushover and Webhook are the initial target plugins. The capability set belongs to [REQ-090](../requirements-catalog.md#i-domain-events-extensions-and-deliveries), delivery timing to the [plan](../authoritative-plan.md#ap-04-scope-decision). Neither installed Gateway behavior nor existing provider fixtures define this API.

Webhook scope ([D-135](../decisions/10-foundation-redesign.md#d-135) item 15): POST with a JSON body, an optional Bearer header and an optional HMAC-SHA256 signature; other methods, encodings and authentication modes are later plugin-side additions. The configuration holds the destination, the Bearer and HMAC Secrets (versioned references, see [C-10 Secrets](c-10-plugin-host.md#planned-and-not-yet-implemented-ap-11-ap-12)) and the per-instance admin field `allowPrivateDestinations` (default false). The signature header is `X-GoPager-Signature: sha256=<hex>`, computed over the timestamp plus the raw body, with the timestamp in `X-GoPager-Timestamp`; the receiver applies and documents its own replay tolerance. All invocations use this contract's current authorized Delivery input and attempt/uncertainty rules plus the SDK-provided transport protections of C-10; none of the options relaxes them.

Pushover: the application token (admin, Secret) and the personal User key (user scope, Secret) as described under Configuration Authority; input mapping and request/receipt classification are recorded here by AP-12 T070. A failed or uncertain attempt never triggers a secret-bearing fallback; no query transport of credentials or input is offered.

## AP-11 Core Binding (planning before coding)

Recorded 2026-11-09 by AP-11 before coding and implemented on 2026-11-10 ([AP-11 handover](../execution/ap-11.md#handover)). The permanent documentation linked in the status line owns the implemented fields, states and errors; this section keeps the binding decisions. Where it refines an AP-02 draft rule above, this section wins.

- **Deliverable event types.** The versioned catalog (`events.Catalog`) lists every recorded type with its producer domain and schema version. Deliverable through Subscriptions: `message.created`, `message.transmission-joined`, `message.merged`, `assignment.changed`, `suppression.changed`, `processing.completed`, `gateway.state-changed` (REQ-049). Catalogued but not deliverable (kept for a later reaction target kind, REQ-139): `configuration.changed`, `principal.*`, `operation.*`, `correction.failed`. A Subscription selects 1..16 distinct deliverable types; there is no default selection.
- **Subscription.** ID, revision, `kind` `personal | global`, `subscriberId`, `state` `active | paused`, `eventTypes`, optional `filter` (the typed predicate), `targets` (1..8 distinct, each `{instanceId, capabilityKind: "delivery", revision, inputs}` with `inputs` a map of at most 64 typed constant values), optional `layoutId`, `splitByUnit` (default false), optional `maxAgeSeconds` (1..86400), `createdAt`, `updatedAt`. Personal: action `subscription.manage-own` on the caller's account, the subscriber is the caller. Global: `subscription.manage-global` on the subscriber's account, and the subscriber must be an active technical account. A personal Subscription is visible only to its owner, a global one only to `subscription.manage-global` holders; anything else is `NOT_FOUND`. Pause and resume are a `state` change of the update. Delete removes the Subscription and cancels its unstarted Deliveries; Delivery history keeps the Subscription ID.
- **Save-time checks.** Types deliverable; the filter and the layout compile against the field catalog below; the subscriber may read every field group the filter and the layout reference (`INVALID_INPUT` otherwise, as in Workflow validation); every target is the current revision of an existing, enabled instance with an available Delivery descriptor, else `AUTHORITY_UNAVAILABLE` with status `unavailable`; target inputs are declared by the descriptor and valid; the layout's output kind is supported by every target. Create takes one unit of the subscriber's sending admission (`RATE_LIMITED`).
- **Field catalog** (namespaces of filters and layouts; groups as in the Query field-group table): `event.type`, `event.occurredAt`, `event.lateJoin`, `event.reason` (no group); `message.id`, `message.time`, `message.processingStatus`, `message.correctionStatus` (no group), `message.protocol`, `message.form`, `message.text`, `message.numeric` (`payload`), `message.unitIds`, `message.unitNames` (`unit`); `unit.id`, `unit.name` (`unit`, present when the Delivery has exactly one relevant Unit); `result.<workflowId>.<output>` (`derived`; a result counts only when the subscriber may read all field groups stored with it; the kind comes from the Workflow's active version and a value of another kind is absent); `gateway.id`, `gateway.name`, `gateway.oldState`, `gateway.newState`, `gateway.contactTime` (`gateway`).
- **Authorized projection.** Message facts project the Message of `data.messageId` (or, once a merge absorbed it, the Message that `data.transmissionId` belongs to now) through the Query read side under the subscriber's current authority (`message.read` eligibility with ages, field groups, readable result versions). Not eligible means no Delivery. `processing.completed` additionally requires its published result to be visible in that projection. `gateway.state-changed` requires `gateway.read` on one of the Gateway's Agencies.
- **Split, parameters and identity.** Relevant Units are the projection's eligible Unit appearances. Without split: one Delivery with split key `""`. With `splitByUnit`: one Delivery per relevant Unit (split key = Unit ID) whose projection holds only that Unit, or one with key `""` when there is none. Input precedence: instance configuration (provider side), then the Subscription target `inputs`, then `integration_unit_parameters` of the Delivery's Unit for keys the descriptor declares. An unsplit Delivery whose Units supply different values for one key is created `failed` with `parameter-conflict` and sends nothing. Automatic identity is unique `(subscriptionId, domainEventId, targetInstanceId, splitKey)`; the consumer inserts with `ON CONFLICT DO NOTHING`, which is its deduplication by Domain event ID.
- **Materialization.** The consumer `delivery-fanout` runs on the AP-10 runner. It skips facts whose `replayMode` is not `normal`, facts recorded more than 24 h before the primary clock and Subscriptions created after the fact's `recordedAt` (no backfill). Per Subscription and target it evaluates the filter on the projection, renders the resolved layout and validates the input against the descriptor, then inserts a `prepared` Delivery with the input (`outputKind`, rendered `body` of at most 64 KiB, `inputs`) and its minimal context (Subscription revision, access revision, Message, Unit and Agency IDs, age anchor) in the batch transaction. A missing subscriber authority, an ineligible projection or a false filter create nothing; `parameter-conflict`, `input-invalid` and `render-limit` create a visible `failed` Delivery. Only infrastructure failures roll the batch back. Derived results count only when the subscriber may read all of their stored field groups (AP-10 D-148).
- **Age and expiry.** The age anchor is the earliest first observation of the Delivery's relevant Unit appearances (the Unit-less appearance or the Message time without Units), `occurredAt` for Gateway facts. `expiresAt` is the earlier of creation plus 24 h and anchor plus `maxAgeSeconds`; nothing is created when it has already passed. The input is removed on every terminal state and at expiry.
- **States.** `prepared` (input materialized; replaces the AP-02 `pending`, because fan-out materializes atomically) → `started` → `accepted | retry-pending | failed | uncertain`; `prepared | retry-pending` → `started | expired | cancelled`. Outcome codes: `accepted`, `transient`, `permanent`, `retry-exhausted`, `uncertain`, `lease-lost`, `expired`, `subscription-paused`, `subscription-changed`, `subscription-deleted`, `authority-revoked`, `no-longer-matching`, `parameter-conflict`, `input-invalid`, `render-limit`, and the deferral codes `rate-limited` and `dependency-unavailable`. Each attempt has its own row (number, state, start and finish time, instance revision, access revision, outcome code, bounded provider receipt).
- **Claims.** The Delivery runner (worker role) claims due `prepared | retry-pending` rows without a live claim with `FOR UPDATE SKIP LOCKED`, optionally restricted to a set of target instances (AP-12 placement). A claim increments the fencing token and sets a 60 s lease, renewed every 20 s during the provider call; every later write needs the current token and an unexpired lease on the primary clock. A `started` row whose lease expired (crash, lost lease) becomes `uncertain` with `lease-lost`; an unstarted row with an expired claim is simply claimable again.
- **Start check** (one transaction, immediately before the invocation): the Subscription still exists, is active and has the materialized revision (else `cancelled`), read under a shared row lock held until the start commits, so a pause or update either waits for this start or is seen by it; the subscriber authority resolves (else `cancelled` `authority-revoked`); the Message projection is re-read — eligibility and filter must still hold (else `cancelled`), and the input is re-materialized when the access revision changed; `expiresAt` not passed (else `expired`); the target instance is current, enabled and has a provider (else deferred 60 s with `dependency-unavailable`, no attempt consumed); sending admission (else `retry-pending` at the next admission window with `rate-limited`, no attempt consumed). Then the attempt is recorded `started` and committed; the provider is called outside SQL with a 30 s deadline. At each renewal the runner re-checks that the subscriber's account resolves and, when the access revision changed since the attempt started, that the subscriber may still see the Delivery's data; otherwise it cancels the call's context, and a call cancelled after start is `uncertain`. The renewal interval is a runner option (default 20 s, at least three renewals per lease) that tests shorten.
- **Outcome.** `accepted` is terminal. `transient` schedules the next attempt with `processing.NextAutomaticRetry` (at most 5 attempts; a later provider `retryAfter` wins) or ends `failed` `retry-exhausted`, or `expired` when the next time is not before `expiresAt`. `permanent` ends `failed`. `uncertain` and every invocation error after start end `uncertain`, with no automatic retry; providers declaring idempotency receive the stable key `deliveryId` but AP-11 still never retries uncertainty automatically.
- **Sending admission (REQ-108).** One-minute windows in `delivery_admissions`, keyed by a SHA-256 of the subscriber ID and of the target instance ID; flags `--delivery-sends-per-minute` (60, per subscriber) and `--delivery-target-sends-per-minute` (600, per instance, lowered by a smaller descriptor limit). HTTP create and redeliver return `RATE_LIMITED` with `Retry-After` and `retryAfterSeconds`; background starts defer as described.
- **Management.** `GET /deliveries` (filters `subscriptionId`, `state`) and `GET /deliveries/{id}` with attempts need `delivery.read` on the subscriber's account or on an Agency, Unit or Unit collection of the Delivery's context. `POST /deliveries/{id}/retry` (`delivery.retry`, `expectedRevision`) turns a `failed` `retry-exhausted` or `transient` Delivery before `expiresAt` into `retry-pending` due now; an `uncertain` Delivery is `409 EXTERNAL_UNCERTAIN`, other states `409 REVISION_CONFLICT`. `POST /deliveries/{id}/redeliver` (`delivery.redeliver`, `commandId`, `confirmDuplicateRisk: true`) on a terminal Delivery creates a new `prepared` Delivery (`redeliveryOf`, fresh ID) re-materialized from the original Domain event under current authority and Subscription state, before the original Delivery's creation plus 24 h (else `409 DEPENDENCY_UNAVAILABLE`).
- **Production without a provider.** The Core target port without AP-12 answers every descriptor request with `AUTHORITY_UNAVAILABLE`; Subscription create and update therefore reject every target with status `unavailable`, and no Delivery can start.
- **Personal data (AP-14, AP-16).** `subscriptions` (`subscriber_id`, `created_by`), `deliveries` and `delivery_attempts` (`subscriber_id`), `delivery_admissions` (hashed bucket, expired windows swept by later admitted sends, old windows deleted per bucket). `deliverystore.DeleteAccountData(ctx, tx, accountID)` deletes them for one account inside the caller's transaction.

## AP-02 Attempt State, Authorization and Retry

- Automatic identity: Subscription ID, selected Domain event ID, Delivery target ID and optional explicit split identity. Atomic unique creation prevents duplicate fan-out. Replacing Message/read-model IDs does not rename earlier Domain event IDs or implicitly resend earlier Deliveries; D-40 does not remove operation-specific deduplication.
- Normal state path: pending -> prepared -> started -> accepted / retry-pending / failed / uncertain. Pending/prepared may expire/cancel/dependency-fail; retry-pending returns to preparation. Terminal states are not reset by a worker restart. Creation/attempt IDs, revision, start/finish time, safe outcome code and provider receipt (where safe/useful) are inspectable only with `delivery.read`.
- Before each external attempt, check current Subscriber/account/Session or key validity where delegated, Subscription/target state, age, and access/Suppression revisions against primary authority. If unchanged, reuse the already materialized input; if changed, re-evaluate only relevant scope/fields. A stale target resolution or contribution may remain as historical context, not as proof of current Unit rights. Affected Rematching scopes wait/fail safely until current. No continuous full historical rematerialization or 100% distributed consistency promise.
- Atomically record `started` with current authorization revision/claim immediately before host invocation; provider I/O is outside SQL. Revocation committed before that authorization point blocks start. Revocation after authorized start requests cancellation where possible but cannot recall the external effect. Losing authority/lease prevents additional starts; an already started effect may remain uncertain.
- Default at most 5 attempts total, at 30 s/2 min/10 min/30 min backoff after each known transient failure; jitter within +/-20%, respecting provider Retry-After without exceeding expiry. Deadline 24 h from Delivery creation or an earlier configured Subscription/permission age deadline. Use the selected fact's relevant Unit appearances/Contribution age anchors for data age, not global Message time, provider-start time or a newly appearing unrelated Unit. A correction to relevant earlier evidence can expire an unsent prepared Delivery; a later reception cannot rejuvenate it. For explicitly subscribed Transmission facts retain their own Observation/Acceptance context, but current Unit-data age rights still apply. Operational facts without Message data use their own occurredAt/recordedAt. Permanent errors end immediately; success means provider acceptance, not User reading.
- Uncertain effects (lost response, crash after start, expired claim during I/O) receive no automatic blind retry. Retry is possible only with demonstrated provider idempotency using the same provider key or an explicit authorized duplicate-risk confirmation. Providers generally have no exactly-once receipt; a response lost after the request was sent is uncertain.
- `RequestExplicitRedelivery` requires current `delivery.redeliver`, target/data permissions and explicit duplicate-risk confirmation bound to original attempt plus fresh idempotency identity. Produces a new traceable Delivery; does not rewrite prior outcome. `delivery.retry` restarts eligible known-transient failure within original expiry, not an expired or uncertain effect under a misleading retry button.
- Pending/failed/uncertain work lives in the same store, with explicit authorized retry/cancel actions. Most jobs are expected to finish quickly, but upstream outages must remain correct under these finite limits. Receipts follow C-08; no mandatory separate DLQ service. Key/Subscription/target deletion removes their future authority, not historical fact.

## Planned: Attribute References and Subscription Health

- **Field references ([D-150](../decisions/04-processing-and-plugins.md#d-150), [D-152](../decisions/07-query-and-live.md#d-152), [AP-21](../work-packages/ap-21-attribute-schemas.md)).** The field catalog of the AP-11 binding becomes the shared field registry: `result.<workflowId>.<output>` is replaced by `attributes.<schemaKey>.<field>[.<property>…]` (effective Message attributes, including the per-target values of the Delivery's relevant Units) and `unit.attributes.<schemaKey>.<field>…` ([AP-22](../work-packages/ap-22-unit-attributes.md)). Kinds come from the Attribute schema, not from a Workflow version, and a reference stays valid when its schema loses an Agency. Compiled filters and Layouts are cached by Subscription revision and registry revision.
- **Subscription health ([D-152](../decisions/07-query-and-live.md#d-152)).** `health` `valid | invalid` with `healthReason` `filter-invalid | field-unavailable | layout-invalid | resource-limit`. The fan-out or start-check transaction sets `invalid` at the first compile failure instead of silently producing no Delivery; a successful save sets `valid`. Each change records the Domain event `subscription.health-changed` ([C-08](c-08-events-jobs.md) vocabulary). `state` `active | paused` is unchanged.
- **Layout choice ([D-151](../decisions/06-identity-and-authorization.md#d-151)).** Layouts are Agency-bound. A Subscription may reference a Layout assigned to an Agency where the subscriber holds `subscription.manage-own` (global Subscriptions: the author holds `subscription.manage-global`); rendering is not restricted by the Message's Agency, and built-in default Layouts stay global.
- **Shared projection ([D-152](../decisions/07-query-and-live.md#d-152), AP-21 T094).** Fan-out and start check build the authorized Message projection once per event and subscriber authority and reuse it while access and Message revisions are unchanged; adopted only with measured gain.
- **Unit attributes as target input ([D-150](../decisions/04-processing-and-plugins.md#d-150), [AP-22](../work-packages/ap-22-unit-attributes.md) T096).** A target input may bind to `unit.attributes.<schemaKey>.<field>…` of the Delivery's Unit; `integration_unit_parameters` stays for plugin-specific and secret values. AP-22 T096 records here the precedence against Unit parameters and Subscription values and the kind compatibility with the plugin-declared input.
- **AP-21 binding (planning before coding, 2026-11-11).**
  - *Fields.* Subscription filters and Layouts compile against the registry scope `delivery`: the `message` scope of [C-07](c-07-query-live.md#planned-and-not-yet-implemented) plus `event.*`, `unit.id`, `unit.name` and `gateway.*` as in the AP-11 catalog. Filters are evaluated with `fields.Match` (C-07 semantics); for `attributes.*` the candidates are the untargeted effective value and the effective values of target positions assigned to the Delivery's relevant Units. A Layout `field`, `chip` or `when` reads one value: the untargeted effective value, else the one of the lowest relevant target position.
  - *Health.* `subscriptions` gains `health` (`valid | invalid`, default `valid`), `health_reason` (`filter-invalid | field-unavailable | layout-invalid | resource-limit`, NULL exactly when valid) and `health_changed_at`. Fan-out and start check set `invalid` in their transaction when the filter or Layout does not compile against the current registry (unknown or deprecated field: `field-unavailable`; another compile error: `filter-invalid` or `layout-invalid`; a bound: `resource-limit`) or when the subscriber can no longer read a referenced field group (`field-unavailable`; this replaces the AP-11 rule that such fields render as absent). The start check then cancels the Delivery as before. An `invalid` Subscription creates no Deliveries until a save that compiles sets it `valid`; health changes never change `revision`. Each change appends the non-deliverable fact `subscription.health-changed` (producer `delivery`, aggregate `subscription`, data `health`, `reason`, `revision`). The Subscription response shows `health` and `healthReason`.
  - *Layout choice.* The subscriber (for a global Subscription, the author) must hold `presentation.manage` or `message.read` in one Agency the Layout is assigned to (scope `all`, `agency`, or a Unit grant in that Agency); `subscription.manage-own` has no Agency scope, so the planned wording above is replaced.
  - *Caches (T094).* A compiled filter and Layout are cached by Subscription ID and revision, Layout version and registry revision only if measured; same for the shared projection.
  - *Measurement (T094).* One `message.created` fact against 20 active Subscriptions of 5 subscribers (4 each) with attribute filters and Layouts: record statements and wall time per event in fan-out. The compiled filter/Layout cache is adopted when compilation takes more than 10 % of the fan-out time per event; the shared projection (one projection per subscriber authority and event) when it lowers the fan-out time per event by at least 30 %.
