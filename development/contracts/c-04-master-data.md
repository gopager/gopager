## Implemented behavior (specified in `docs/` and OpenAPI)

Routes and schemas: [OpenAPI v1](../../api/openapi/v1.yaml) (`info.version` 1.10.0), tags `Agencies`, `Organizations`, `Unit templates`, `Units` and `Unit collections`. Semantics: [HTTP API: Agencies, Organizations, Unit templates, Units, collections](../../docs/http-api.md#agencies-organizations-unit-templates-units-collections) and [Master data semantics](../../docs/http-api.md#master-data-semantics) (Unit identity, exactly one Agency, collection membership, `inherit`/`value`/`unset` settings, color, icon and Function-meaning rules, name limit, templates as copied snapshots, Organization deletion with materialized defaults and no Rematch, Unit deletion marker and pending correction, bulk operations with their 100-item limit, required rights). Authorization of these routes: [HTTP API: Authorization](../../docs/http-api.md#authorization). Correction after Unit deletion: [Architecture: Historical correction](../../docs/architecture.md#historical-correction-worker-role). Typed code: [`internal/units`](../../internal/units/).

Decisions that remain binding: formation membership alone is not evidence of co-alerting and there is no unrestricted multi-parent default graph; a Unit is not subordinate to a Network; no historical color or icon versioning is needed for general master data; conflict details never reveal hidden uses elsewhere; a concurrent Organization and Unit edit conflicts instead of losing a value.

## Planned and not yet implemented

- **Extension fields.** Dropped by [D-135](../decisions/10-foundation-redesign.md#d-135): per-Unit integration values use the per-integration parameter table owned by [C-09](c-09-delivery.md) (AP-11, AP-12). Administrator-defined Unit attributes (below) are a separate concept with no plugin namespace and no rights effect.
- **Unit attributes (REQ-142, [D-150](../decisions/04-processing-and-plugins.md#d-150), [AP-22](../work-packages/ap-22-unit-attributes.md)).** A Unit carries values of `unit` Attribute schemas ([C-11](c-11-processing-presentation.md#attribute-schemas-and-agency-binding-planned)) that are assigned to its Agency ([D-151](../decisions/06-identity-and-authorization.md#d-151)). Each value uses the setting modes `inherit | value | unset`: `inherit` resolves to the Organization's default, Organization deletion materializes still-inherited values, and templates copy effective values, exactly as for the settings in [HTTP API: Master data semantics](../../docs/http-api.md#master-data-semantics). Changing a Unit's Agency requires removing the values of schemas that are not assigned to the new Agency. Edits need `unit.update` (Organization defaults: `organization.update`); they never change rights, never reprocess Messages and are no correction work.
  AP-22 binding (planning before coding, 2026-11-12, T095): Implemented by AP-22 on 2026-11-12 ([handover](../execution/ap-22.md#handover)).
  - *Storage.* Values are the member `attributes` of the existing setting documents: `units.settings`, `unit_templates.settings` and `organizations.defaults`; no new column. Shape `{"<schemaKey>": {"<field>": {"mode": …, "value": <typed value>}}}` per top-level field (an object field is set as a whole), typed values as in [C-09](c-09-delivery.md#typed-predicates-and-values-implemented). On a Unit or template a missing field is `inherit`, and the canonical form drops `inherit` entries, so only `value` and `unset` are stored; an omitted `attributes` member means everything inherits, as for the other setting members. In Organization defaults a missing field is `unset`; only `value` entries are stored (an explicit `unset` is accepted and dropped). The 64 KiB request limit of master-data routes bounds a document.
  - *Validation.* Every Unit entry (`value` or `unset`) names an existing `unit` schema assigned to the Unit's Agency and a declared top-level field, and a value must decode against the field's type; Organization defaults and templates have no Agency and are checked against existence, subject and type only. Deprecated schemas and fields still accept values (deprecation only hides fields from new field references). A violation is `400 INVALID_INPUT`.
  - *Resolution.* Per field: Unit `value` is effective with source `unit`; `unset` has no value; `inherit` takes the Organization's `value` default with source `organization`, but only when the schema is assigned to the Unit's Agency, so a Unit never shows a value of a schema its Agency lacks. Templates resolve without the Agency condition. `effectiveSettings.attributes` lists only fields with an effective value as `{"<schemaKey>": {"<field>": {"value", "source"}}}`.
  - *Organization deletion* materializes, as for the settings, every still-inherited field that has an effective value into a `value` entry on the Unit or template; fields without one stay absent, which resolves to no value once detached.
  - *Template copy.* A Unit created from a template receives, for every field of every `unit` schema assigned to the new Unit's Agency, the template's effective value as `value`, else `unset`, so later template or Organization edits do not change it (as for the settings). Values of schemas not assigned to that Agency are not copied.
  - *Bulk update* carries the complete `settings` per item, `attributes` included, and validates each item against its Unit's Agency; preview reports such an item as `INVALID_INPUT`, execution stays all or nothing.
  - *Agency change.* The request carries the complete `attributes`; an entry of a schema not assigned to the new Agency is `400 INVALID_INPUT`. Inherited values follow the new Agency's assignments.
  - *Reference checks.* Deleting a schema is `409 REVISION_CONFLICT` while an undeleted Unit, template or Organization stores an entry of it (in addition to the AP-21 references, which also count `unit.attributes.<key>…` in Layouts, Subscription filters and saved views and `target.unit.attributes.<key>…` in active Workflow versions, and the Subscription target-input bindings of C-09); in the same transaction the entries of deleted Units, templates and Organizations are removed, so a later schema with the same key never meets them. Removing an Agency from a schema is `409 REVISION_CONFLICT` while an undeleted Unit of that Agency stores an entry of it; inherited values of such Units simply stop resolving. Schema changes take the catalog lock first; a Unit, template or Organization write with `attributes` entries holds the shared catalog lock (`attributes.CatalogSource.LockCatalog`) before it validates them.
  - *Effects.* Attribute edits are setting edits: same rights, same `configuration.changed` facts (`updated`, Organization `defaults-changed`), no grant change, no correction scope, no Processing re-admission.
- **Agency deletion and definitions ([D-151](../decisions/06-identity-and-authorization.md#d-151), [AP-21](../work-packages/ap-21-attribute-schemas.md)).** An Agency that is the last assigned Agency of a Workflow, Layout or Attribute schema cannot be deleted (`409 REVISION_CONFLICT`); otherwise its definition assignments are removed together with it.
  AP-21 binding (2026-11-11): Implemented by AP-21 ([handover](../execution/ap-21.md#handover)). `unitstore.DeleteAgency` checks, under the Agency's row lock, whether an undeleted Workflow, a Layout or an Attribute schema has this Agency as its only assigned Agency (`units.ErrAgencyInUse`, `409 REVISION_CONFLICT`); the assignment rows of other definitions and of soft-deleted Workflows cascade.
- **Icon catalog and renderer.** The server stores and copies an icon identifier only. [AP-15](../work-packages/ap-15-frontend.md) (T079/T080) defines the identifier set from a bundled open-licensed icon set chosen under [D-36](../decisions/01-platform-and-storage.md#d-36), the renderer, and the fallback for an unknown identifier (an accessible label, never color alone), and records the result here replacing this line. Unit and Organization color and icon render consistently in management and Message views (REQ-022).
- **Exchange and bulk (REQ-128, REQ-140).** Server-to-server exchange of Units with their Address rules, Suppressions and Unit collections, and bulk changes of collections, are planned and implemented by [AP-15 T089](../work-packages/ap-15-frontend.md#planning-before-coding) ([D-138](../decisions/09-process-and-documentation.md#d-138)); the exchange document and bulk rules are defined here and in [C-05](c-05-matching-correction.md) by that task.
