**Authoritative artifact (change rule 9):** The implemented HTTP routes and request/response schemas are defined by [OpenAPI v1](../../api/openapi/v1.yaml) (OpenAPI 3.0.3, `info.version` 1.0.0), tags `Organizations`, `Unit templates`, `Units` and `Unit collections` under `/api/v1`. Implemented behavior is described in [HTTP API: Organizations, Unit templates, Units, collections](../../docs/http-api.md#organizations-unit-templates-units-collections).

**Defined:** Units have their own identity, may belong to several Unit collections, belong to exactly one Agency (the operating authority of their alerting domain, under [D-135](../authoritative-plan.md#foundation-redesign-after-the-2026-11-06-re-evaluation)), and are not subordinate to a Network. Organization, color, icon, templates, and selective overrides remain recognizable; returning to organization defaults is possible. Formation membership alone is not evidence of co-alerting. No unrestricted multi-parent default graph.

**Deletion:** Unit deletion coordinates C-05 Rematching of every potentially affected historical target resolution; no new Transmission records/Messages. Organization deletion preserves/detaches Units and retains previously effective organization defaults; no Rematching. Current organization filters/rights follow the new reference. Deleted Units have a nonselectable deletion marker until correction/reference cleanup completes; no stale visible Unit or scope expansion.

**Authorization/failures:** Creating an organization within a Unit dialog separately requires organization permission. Bulk/deletion checks each target; conflict details do not reveal hidden uses elsewhere. No silent overwrite of concurrent edits. Color/icon-only changes do not rematch.

**Transaction/time:** Consistently capture inherited defaults before detachment; reliably coordinate reference/permission changes and required correction work. C-05 does not require historical color/icon versioning for general master data.

### AP-08 Unit Template Direction

**Owner:** Master data. **Status:** standalone ownership approved; [AP-08](../work-packages/ap-08-master-data-correction-after-intake.md) defines exact authorization in C-06 before implementation.

A Unit template is a standalone master-data resource, not owned by an Organization. It may carry an optional Organization reference and the supported Unit creation settings. Creating a Unit from a template copies its current settings; the Unit has no live template relationship, and later template edits do not change it. Any copied Organization reference becomes the Unit's ordinary Organization relationship and follows the inheritance rules above.

Template operations require explicit current C-06 authorization, not inferred `organization.*` or `unit.*` rights.

## AP-08 Master-data Management

**Version/status:** master-data-management 1.0, defined and frozen for AP-08 T060 before implementation. **Owner:** Master data; Identity owns the linked authorization slice and integration owns cross-domain transaction composition. **Consumers:** AP-10 current read projection and AP-15 management workflows consume the fixed APIs; neither is an AP-08 prerequisite.

### Values, inheritance, and snapshots

Organization defaults and Unit settings cover color, icon reference, and POCSAG Function meanings. A default is either `value` or `unset`; a Unit setting is `inherit`, `value`, or `unset`. Only `value` carries a value. `inherit` resolves to the current Organization default, or to `unset` when the Unit has no Organization. Effective DTO values carry source `unit`, `organization`, or `unset`; clearing an override explicitly restores `inherit`. Organization changes affect only Units that still inherit the changed setting. Color accepts six hexadecimal digits with a leading `#` and is stored uppercase. Icon references are nonempty, at most 128 ASCII letters/digits/period/underscore/hyphen; AP-08 stores and copies the identifier but does not implement a renderer or icon catalog. POCSAG Function meanings map only Function codes `0..3` to nonempty, at-most-256-Unicode-scalar labels; other Protocols have no Function-meaning entries in this slice.

A Unit template is a standalone resource with a name, optional Organization reference, and typed setting modes. It is not referenced by a Unit. `CreateUnitFromTemplate` requires an explicit Unit name and collection list, copies the template's current Organization reference and effective settings in the same transaction, and stores the resulting values on the Unit; later template or Organization changes do not mutate that Unit. Templates can inherit their referenced Organization's current defaults until copied. Deleting an Organization detaches referenced templates and materializes their inherited effective settings as values or unset, preserving their current creation behavior; because templates are standalone, reference removal does not delete or rewrite any Unit.

### Operations and transaction behavior

The versioned management surface under `/api/v1` comprises the OpenAPI v1 tags `Organizations`, `Unit templates`, `Units` (including `POST /units/from-template`, `POST /units/bulk` and `POST /units/bulk/preview`), `Unit collections` and `Address rules`. Collection and Address-rule behavior already defined by the early master-data/current-matcher slices remains unchanged. New read/list operations use the existing bounded page shape and return explicit DTOs only. Create and bulk operations use actor-bound `commandId` receipts; updates/deletes require `expectedRevision`. Every mutation resolves current authority and primary time in the same transaction as the read/check/write, safe audit, applicable access/configuration revision, fact, command receipt, and correction work. Unknown JSON fields and oversized requests fail explicitly.

Organization and template CRUD use typed complete replacement values. Unit creation may reference an existing Organization, or atomically create an Organization and Unit only when both `organization.create` and `unit.create` are authorized. Unit creation from a template additionally requires `unit-template.read`; the copied Organization reference must be currently readable and usable. Unit updates include the complete current supported fields and collection list; they do not erase fields owned by later extensions.

Organization deletion requires `expectedRevision`, detaches every referencing Unit and template, and materializes each inherited effective setting as `value` or `unset`. Explicit Unit/template overrides are unchanged. Units and templates receive their own revisions when changed; the Organization is deleted in the same transaction. The operation authorizes each affected Unit/template and returns only a generic forbidden/conflict result if any use is not manageable. A stale affected revision rolls back the complete deletion. It never schedules Address-rule or target correction.

Bulk Unit update/delete is limited to 100 distinct explicit Unit IDs with an `expectedRevision` for each and an actor-bound `commandId`. Preview validates the complete set and returns only caller-safe per-item results and expected revisions; no writes or durable work occur. Execution repeats all authority, existence, revision and input checks under ordered row locks and is all-or-nothing. One stale/unauthorized/invalid item aborts every item without revealing hidden shared uses. A successful command writes one compact receipt for the operation and returns its per-Unit resulting revisions; an identical retry returns that receipt and changed content with the same ID conflicts. Bulk updates change only explicitly supported shared settings; they do not change names, Organization, membership, templates, or Address rules. Bulk deletion follows ordinary Unit deletion and its C-05 correction contract. Cosmetic/default/collection changes do not rematch; deleting a Unit disables its current rules and creates correction work atomically.

The authoritative API schemas for these routes, including the earlier Unit-collection and Address-rule routes, are maintained in [OpenAPI v1](../../api/openapi/v1.yaml). No renderer, icon-catalog administration, historical presentation versioning, import, or browser workflow is part of this slice.

## AP-02 Concrete Master-data Contract

- Unit: stable ID/revision, required nonempty name (maximum 256 Unicode scalars), optional one Organization, optional color (`#RRGGBB`), icon reference from configured catalog, Function meanings per Protocol/code, zero or more Unit collection memberships, plugin-namespaced Extension fields. No implied Network ownership. Organization/Unit collection/template names use the same name limit; names are not identity keys.
- Color/icon/Function-meaning entries each use either an explicit value or inheritance. Clearing an override restores inheritance; a null effective value means unset, not a fabricated default. A template is a copied creation snapshot, not a live multi-parent inheritance graph.
- `DeleteOrganization` reads the effective defaults and revisions, materializes each still-inherited effective value on its Units, detaches them, deletes the Organization and invalidates affected rights/filters in one transaction. Overrides remain unchanged; no Address-rule/target-resolution mutation or Rematch job. Concurrent Organization/Unit edit conflicts rather than loses a value.
- `PreviewBulkChange` returns caller-visible per-item validation and the exact expected revisions. Execution rechecks each item and permission; all-or-nothing transaction, no partial writes. Hidden shared use produces a generic forbidden/conflict outcome, not foreign identifiers.
- `DeleteUnit` atomically marks the Unit deleted, disables/removes its rules from the current rule set, records affected correction scope/revision and durable Rematch work. Current grants on that ID become ineffective, not global. Physical cleanup follows successful reference correction. Cosmetic edits never schedule Rematching.
- `DeclareExtensionFields` is owned by C-10, storage by Master data: definition has plugin namespace/version, type, validation/default, sensitivity/read and write capability. Unknown/new fields are inaccessible by default. Schema incompatibility blocks activation rather than coercing saved values.

### Data and Operation Forms

The authoritative master-data-core 1.0 DTOs, internal context and validation are [the Unit owner types](../../internal/Units/model.go); [the service](../../internal/Units/service.go) defines the implemented operations. Persistence uses [the owned Ent schemas](../../internal/persistence/ent/schema/assignments.go), [Goose migration 00004](../../internal/persistence/migrations/00004_current_assignments.sql) and [the native-filtered adapter](../../internal/persistence/ent/unitstore/store.go). ID/revision/deletion are server-owned, not writable properties. Unit collection has no implied Network/Organization ownership; membership is the explicit Unit-to-collection relation.

Organization/defaults, color/icon/Function meanings, creation templates, extension-field registry and general bulk operations remain later T028 work. Their meanings and deletion/default-preservation obligations above are not removed or replaced with empty placeholders. Keep the early owner ports separate from presentation fields so their later additive implementation does not require replacing the matcher/authorization boundary or changing existing Unit IDs. The early update operation changes only the named supported fields; it must never erase future unrelated configuration via a whole-row replacement.

`CreateUnit` and `CreateUnitCollection` take authenticated proof, actor-bound `commandId` UUID and typed creation values. Read/list operations return only authorized typed DTOs and ordinary bounded pages. Update/delete operations take ID and `expectedRevision`; updates change supported typed fields, not arbitrary merge-patched JSON. The resulting revision or safe deletion/pending status is returned. Creation retries compare the complete validated command input and return the same nonsecret result; changed content with the same actor/command is `IDEMPOTENCY_CONFLICT` (409, not retryable; changed under [D-133](../authoritative-plan.md#command-id-reuse-conflict-code), formerly `REVISION_CONFLICT`). General command receipt retention/expiry follows shared conventions, not Submission retention.

`ChangeUnitCollectionMembership` takes Unit ID/revision plus the complete desired collection-ID set; it checks current permission/existence of all affected uses and increments the Unit revision atomically. Collection deletion updates affected Unit revisions and membership without changing original evidence. This operation is not a general bulk-edit engine.

The authoritative version-1 HTTP request/response shapes are [OpenAPI v1](../../api/openapi/v1.yaml) (tags `Units` and `Unit collections`); [the management adapter](../../cmd/gopager/management.go) implements route registration, bounded JSON decoding and page validation; [root composition](../../cmd/gopager/main.go) retains one primary store/listener and [owner scope dispatch](../../cmd/gopager/scopes.go). Unit replacement requires an explicit membership list, including an explicit empty list to clear it. Stored/internal entities are never serialized directly. No Organization/template/bulk API is promised by this early slice. Actual HTTP/PostgreSQL evidence belongs to [the AP-08 execution record](../execution/source-ap-08.md#e-03-postgresql-race-http-and-proxy-validation).

### Matcher and Authority Participation

The internal `ReadUnitContext(transaction, unitId)` returns current ID/revision/deletion marker and collection references; no original Payload or authority is returned. `ScopeExists(transaction, kind, id)` handles current Unit/Unit-collection references and returns false for deleted targets. Network existence/Protocol belongs to Intake and is supplied through a typed transaction-participating owner port, not a foreign table query or fabricated Network. A missing owner adapter fails explicitly with `AUTHORITY_UNAVAILABLE`; standalone tests may supply explicit fixture owners but cannot count as completed production Network composition.

All protected operations resolve current C-06 authority in the same live platform transaction, filter before count/page/mutation, and check every affected use before shared-resource mutation. Collection operations cannot infer authority over hidden members; errors do not list those uses. Read DTOs project only permitted fields; no Organization grant dimension or new permission catalog is introduced.

Domain changes, safe audit, applicable access/configuration revisions, command result and required [C-08 configuration facts](c-08-events-jobs.md#early-master-data-fact-candidate) commit together. Before historical owners exist, Unit deletion persists the nonselectable marker, current-rule invalidation and durable affected correction scope/revision atomically; it returns pending correction, never falsely reports historical cleanup completed. Historical scanning/publication belongs to later T029/T030 integration. Organization deletion remains deferred, with its distinct default-preservation/no-rematch semantics unchanged above.

Invalid shape/reference is `INVALID_INPUT`, denied mutation is `FORBIDDEN`, inaccessible/missing reads use indistinguishable `NOT_FOUND`, stale expected state is `REVISION_CONFLICT`, and a reused command ID with different input is `IDEMPOTENCY_CONFLICT`. Resource/storage/authority/uncertain-commit outcomes follow C-07/C-12, without silent empty/default fallback. Operation time comes from the primary clock; Unit revision is not Address-rule domain-validity time. Positive/negative validation is bound in the [AP-04 consumer proposal](../execution/ap-04.md#ap-08-prerequisite-consumer-binding-proposal).
