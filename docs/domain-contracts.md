# GoPager Contract Catalog

Date: 2026-10-24. All contract versions: **0.1-draft**. Owner roles and module dependencies: [architecture](architecture.md#domains-and-data-ownership). Open decisions and approval status: [plan](authoritative-plan.md#open-issues-and-risks).

This document records defined domain invariants and describes interfaces as **documentary drafts**. Operation/field names and result types are proposals, not compilable Go signatures, fixed HTTP endpoints, or an approved Wasm ABI. Their semantics must not weaken confirmed product rules. Freeze a versioned contract only after resolving its blockers.

## Shared Interface Conventions

- Each operation identifies context, calling Principal/Gateway, domain input, result, and possible errors. Go uses cancellable context; concrete deadlines and size limits remain to be specified, not assumed unlimited.
- IDs are opaque stable references. UUID/integer format, transport serialization, and schema/OpenAPI version are not dictated by this notation.
- Gateway-reported Observation time, server acceptance time, domain validity time, and projection revision are distinct concepts. Every Transmission has a timestamp with an explicit UTC offset or UTC designator; Grouping always uses that reported instant, never server acceptance time. Exact serialization, trust/plausibility limits, and age anchors remain to be specified. Never silently substitute one time for another.
- Mutable configuration needs a visible revision/expected state for conflicts. Immutable Transmission evidence is not 'corrected' by updating it; derived data is versioned separately.
- Authentication is not authorization. Administrative, guest, Gateway, API-key, worker, and plugin paths require explicit capabilities. A technical worker is not a global data reader for outbound Payloads.
- Draft error classes: invalid/incomplete, login required, forbidden/invisible, revision/idempotency conflict, temporarily unavailable, storage/authority problem, internal error, uncertain external effect. Define HTTP codes/envelopes, retry hints, and redaction before OpenAPI freeze. Other users' IDs, secrets, and internal SQL/plugin errors do not belong in public details.
- English is the authoritative interface/documentation language. Define stable machine-readable error/status codes and structured Localized text parameters independently of localized display text. Any human-readable fallback is English; clients do not parse it. UI language and formatting locale do not change IDs, field names, enum/Domain event values, wire formats, or authorization.
- Atomicity applies within the authoritative database, not to browser state or external providers. Commit data and required domain outbox work together. Intermediate derivation must not be reported as complete state.
- Idempotency is operation-specific; it replaces neither AuthZ nor distinguishing independent Transmissions. Retention/restore must not unintentionally regenerate old work.
- Subscribing to a Domain event type never grants a Domain event/plugin/SSE consumer unprojected original Payload. Field permissions remain bound to the domain data context.

## C-01 Transmission Acceptance

**Version/status:** 0.1-draft; not approved for implementation. **Owner:** DOM-01; integration owns the shared commit boundary. **Parties:** authorized Gateway/Gateway manager; downstream DOM-02/DOM-04/DOM-07.

| Draft interface | Input | Result / effect |
| --- | --- | --- |
| `SubmitTransmission` | Context, authorized Gateway identity, submission identity, completed C-02 Transmission, mandatory Observation timestamp with explicit UTC offset or UTC designator, optional Gateway Network identifier, Transmission targets/Addresses, and already-evaluated quality metrics | Acceptance receipt/Transmission reference and an honest acceptance/processing state |
| `ReportGatewayState` | Context, Gateway identity, heartbeat or explicit termination | Separate contact/Transmission/state evidence, state Domain event if appropriate |
| `ConfigureGatewayNetworks` | Administrative Principal, expected revision, allowed Network contexts | Authorized new revision without retroactive mutation of Transmission evidence |

**Defined:** A Network has one domain Protocol; a Gateway may submit for multiple allowed Networks. An authorized unambiguous declaration precedes inference; reject unauthorized declarations rather than silently redirecting. An absent declaration (resolved by inference or the default Network) and an unauthorized declaration (rejected) are different outcomes. Simple single-Network Gateways need no artificial frequency ranges.

**Network resolution (user decision 2026-10-25; draft until AP-04 freeze):** A Gateway is assigned to one or more Networks. A Submission may declare its Network by a Gateway Network identifier: a Gateway-local identifier that the Gateway's configuration maps to exactly one of its assigned Networks. Only Networks assigned to the Gateway are ever used; there is no global built-in fallback Network. A Gateway assigned to more than one Network of a Protocol must have exactly one of them configured as its **default Network** for that Protocol; `ConfigureGatewayNetworks` rejects a configuration without it. The server resolves the Network of each Transmission in this order (user decision 2026-10-25):

1. **Declared:** a mapped Gateway Network identifier determines the Network. An identifier that is not mapped for this Gateway, or maps to a Network the Gateway is not assigned to, rejects the Submission (see failures); it is never silently redirected.
2. **Inferred, single:** without a declaration, if the Gateway is assigned to exactly one Network of the submitted Protocol, that Network applies.
3. **Inferred, by Address:** otherwise, among the Gateway's Networks of that Protocol, the Network in which at least one reported Address has an Address rule valid at the Observation time applies, if exactly one such Network exists.
4. **Default Network:** otherwise (no Network or more than one Network has a matching Address rule) the Gateway's default Network for that Protocol applies. If more than one Network matched, an Operational log entry is written and an Operational Domain event (ambiguous Network, default applied) is emitted, so administrators can fix the configuration or let the Gateway declare its Network.

The submitted declaration is immutable Transmission evidence; the resolved Network and its resolution method (`declared`, `inferred-single`, `inferred-address`, `default`) are derived data. Candidate Networks are not stored; they are recomputed from the Gateway Network configuration revision valid at the Observation time. The derived values are recomputed through C-05 Rematching when Gateway Network mappings or relevant Address rules change.

Each Gateway owns its transport and technical Protocol handling: it evaluates received frames/signals, checks Protocol-level integrity, reassembles fragmented Emissions, and submits completed Transmissions. GoPager does not accept or interpret raw RF/audio frames, checksums, or fragments. SMTP or other non-radio adapters likewise submit completed Transmissions in the shared Gateway contract.

The Gateway adapter does not perform Payload interpretation, map Addresses to GoPager Units, or perform Grouping of independent Transmissions. It submits the completed original Payload and the Transmission targets available from that Transmission. A Group call is submitted as one Transmission with multiple Transmission targets; this does not permit an adapter to merge separate Transmissions or decide that their Payloads are equal. GoPager performs the Payload-based comparison, resolves Address targets against current logical assignments, and links Transmissions into Messages, including across Gateways and Networks. Quality metrics are optional: if supplied, they must already be evaluated and include enough context to be meaningful; raw technical measurements and quality interpretation are not required of GoPager. An optional compact reference/delta submission format is a possible later bandwidth optimization, not part of this contract.

The submission preserves completed original Payload, reported Transmission targets, and Transmission context unchanged. Every independent Transmission must include its Observation timestamp with an explicit UTC offset or UTC designator, identifying an unambiguous instant; the server stores/compares that instant independently of server acceptance time. Missing or timezone-ambiguous Observation time is invalid; server acceptance time is never a fallback.

**Observation time format and plausibility (user decision 2026-10-25; draft until AP-04 freeze):** The Observation time is an RFC 3339 date-time with a mandatory numeric UTC offset or `Z`. Precision is at least whole seconds; finer fractions are allowed and are compared as instants at their supplied precision (`12:00:00Z` equals `12:00:00.000+00:00`). The supplied offset is stored with the instant. The maximum stored sub-second precision is a technical choice for AP-03; comparison always uses the stored instant, so stored and compared values never differ. Observation times in the past are accepted without limit. An Observation time later than the server time plus a configurable clock-skew tolerance is accepted and processed normally, including Grouping; the Transmission is marked `observation-time-implausible`, an Operational log entry is written, and an Operational Domain event is emitted so that administrators can subscribe Deliveries to it. The default clock-skew tolerance is 15 minutes. This does not automatically require recording raw radio signals. The Gateway adapter supplies an operation identity for each independent Transmission. A transport retry of the same operation creates no new server Transmission; an independent Transmission does, even if its Payload is identical to another Transmission's. **Idempotency (user decision 2026-10-25; draft until AP-04 freeze):** Gateway plus Submission ID identifies an operation. A retry with identical submitted Transmission content (Protocol, Gateway Network identifier, Observation time, Payload, Transmission targets, Incomplete marker, Quality metrics) returns the existing receipt and Transmission. Different content under the same Submission ID is rejected as a conflict and never updates the accepted Transmission. Retries do not create new Observation times or advance a Grouping window. The server retains a Submission ID as long as the Transmission it created is retained. A retry that arrives after its Transmission was deleted by retention is accepted as a new Transmission; the user accepted this residual risk on 2026-10-25 because retries normally end long before retention deletes data (F-23).

**Time/transaction:** Acceptance point and crash contract must fit Lite/Full. An uncertain commit is not a definite failure. Queries/resubmissions must respect idempotency and current Gateway permissions. Acceptance status distinguishes original intake, Message/assignment derivation, and pending jobs; exact synchronous/asynchronous boundaries remain open. Do not acknowledge 'fully processed' when work has only been scheduled.

**Rejected Submissions (user decision 2026-10-25):** A Submission is rejected as a whole, with a stable error code and no partial acceptance, if it is malformed: missing Observation time or one without offset, unknown Protocol, Payload that is invalid for the Payload form declared by the Protocol definition, unmapped or unauthorized Gateway Network identifier, a Protocol for which the Gateway is assigned to no Network, or a Submission ID conflict. A rejected Submission creates no Transmission. Each rejection writes an Operational log entry and emits an Operational Domain event (Gateway, Submission ID, error code, time; no Payload content) so administrators can subscribe Deliveries to it.

**Failure/cancellation:** Invalid/incomplete submission shape, unauthorized Gateway/Network, conflicts, storage shortage/write failure, and uncertain write authority are visible without exposing other Gateways/Networks. Protocol-frame, checksum, signal-decoding, and fragment-reassembly errors belong to the Gateway adapter. No silent deletion to free space. Cancellation after a possible commit cannot guarantee absence.

**Gateway state:** Never seen, active, degraded, deliberately stopped, and contact lost remain distinguishable. Transmission and heartbeat have separate times. Missing contact proves no specific crash cause; removed history does not disprove previous Transmission.

**Open:** Handed over: wire format, size limits, and concrete Gateway/Network identifier types (AP-02); acceptance/derivation boundary (AP-03); Gateway contact timeouts (AP-02). Grouping always uses the mandatory reported Observation timestamp, normalized as an instant from its explicit UTC offset or UTC designator; server acceptance time must never substitute for a missing Observation timestamp. AP-01/AP-02 clarify; AP-03 provides technical evidence.

## C-02 Protocol Payload and Payload identity

**Version/status:** 0.1-draft. **Owner:** DOM-02; DOM-01 owns submitted Transmission evidence. **Parties:** Gateway submits completed Transmissions; the GoPager ingest, assignment, and Grouping domains consume them. **Failure:** A malformed or incomplete submission is not silently treated as an empty Transmission or a certain match.

The Gateway contract identifies the declared Protocol and carries the completed original Payload, zero or more reported Addresses and Transmission targets (including applicable Function/signal attributes), Transmission context, and optional contextualized quality metrics. These fields are data, not a claim that the Gateway has interpreted their domain meaning. For example, an EAS submission contains both header and actual Payload; a POCSAG/FLEX/SMTP submission may report multiple Transmission targets for one completed Transmission. The contract does not describe frames, checksums, radio/audio decoding, or fragment reassembly.

The Gateway does not determine Payload identity, infer or validate Unit assignments, merge independent Transmissions, or assign Message membership. GoPager owns Payload equality and Grouping, Address-to-Unit resolution using current assignments, and all cross-Gateway/cross-Network correlation. A Group call is preserved as one Transmission with multiple Transmission targets; this does not create a Message or authorize deduplication of other Transmissions. Canonical identity representation, comparison/versioning, and collision handling are server-owned; the rules below define the decided identity semantics. A Gateway may not provide an identity/Message reference that GoPager trusts as authoritative.

Original supplied Payload and reported Transmission targets remain distinguishable and preserved. Gateway/Network are Transmission context, not blanket Grouping keys. Transmissions with different Transmission targets may still be Payload-identical; Transmission targets remain per-Transmission evidence and are resolved independently by the server. Payload equality is not determined from display labels alone, and search normalization is not implicitly reused for Grouping. A later compact reference/delta representation (for example, a later Transmission referring to prior Payload plus changed Address/time) is optional future transport optimization; it does not change server ownership of identity, assignment, or Grouping.

**Payload identity rules (user decisions 2026-10-25; draft until AP-04 freeze):**

- **Protocol definitions own identity fields via Payload forms.** There is no fixed, closed class catalog. Each Protocol definition maps each of its Transmission types to a **Payload form** plus a normalized value and declares which completed-Transmission fields are identity versus Transmission attributes. Two Transmissions are Payload-identical only if form and normalized value are equal, regardless of Protocol. Initial forms: `text` (POCSAG and FLEX alphanumeric), `numeric` (POCSAG and FLEX numeric, normalized to a shared numeric character set), `tone-only` (POCSAG Address-only calls and FLEX tone-only types; no Payload), `zvei-signal` (ZVEI double tone or "no double tone"), `eas-header`, and `binary` (FLEX binary/transparent and secure types; opaque bytes). Numeric and text never match each other ("123" numeric is not "123" text). Forms without a counterpart in another Protocol simply never match it (ZVEI forms never form a Message with POCSAG). Adding a form or mapping is a versioned identity-rule change.
- **Character sets (user decision 2026-10-25):** decoding Protocol character sets, including national variants such as the German DIN 66003 POCSAG variant (`[` as `Ä`), is Protocol handling by the Gateway adapter according to its configuration. The `text` Payload is submitted as Unicode text; the server does not reinterpret characters per Network.
- **Numeric character set:** POCSAG and FLEX numeric types use 4-bit codes. Numeric identity is defined by the code sequence, not by decoder glyphs, because sources and decoders render codes 0xA–0xF differently (ITU-R M.584 as summarized by Wikipedia: 0xA reserved, 0xB `U`, 0xC space, 0xD `-`, 0xE `)`, 0xF `(`; multimon-ng POCSAG: 0xA `.`, 0xE `]`, 0xF `[`; multimon-ng FLEX: 0xA as space, 0xE `]`, 0xF `[`). The Gateway adapter submits the code sequence in the shared canonical glyphs (user-confirmed 2026-10-25), one per code: `0`–`9`, 0xA `.`, 0xB `U`, 0xC space, 0xD `-`, 0xE `)`, 0xF `(`. Equal code sequences therefore give equal strings. Trailing 0xC padding is removed by the adapter; other leading and trailing spaces are ignored for comparison as for `text`. An adapter whose decoder cannot distinguish codes (for example multimon-ng FLEX 0xA versus 0xC) must take the code from the decoder or document the limitation.
- **Binary (user decision 2026-10-25):** FLEX binary/transparent and secure types are accepted as form `binary`: the Payload is the unchanged byte sequence, the identity is the subtype (`transparent` or `secure`) plus exact byte equality, and it is never shown as text. No decryption or interpretation takes place.
- **Address and Function are never Payload identity.** Transmission target Address (RIC, CAP code, ZVEI sequence, EAS area) and Function/subaddress values are per-Transmission target Transmission attributes. This holds both when a POCSAG Function is used as a Function bit and when it is used as a subaddress; which mode applies is decided by the Address filter during Address-to-Unit resolution, not by Grouping. Example: Payload "abc" observed for Transmission target B with Function a, Transmission target C with Function b, and Transmission target D as subaddress is one Payload identity with three Transmission targets.
- **Empty Payload is still Payload.** POCSAG Address-only Transmissions and FLEX tone-only Transmissions share the form `tone-only` and are Payload-identical to each other; normal Grouping applies across Addresses and across POCSAG/FLEX. Consequence accepted by the user: unrelated tone-only Transmissions within the window form one Message; projection still shows only permitted Transmissions.
- **ZVEI:** the five-tone sequence is the Address reported as a Transmission target. Payload is the optional double tone, identified by its technical tone name, or the explicit value "no double tone". Sequences without a double tone are Payload-identical across Addresses; sequences with the same double tone are Payload-identical. Grouping by Unit-specific double-tone meaning was evaluated and rejected for now: one sequence may resolve to several Units with different meanings, so a Transmission would have ambiguous Payload identity and Grouping would depend on mutable Unit configuration. Unit-specific meaning remains a projection concern.
- **EAS:** audio/video Payload is not supported initially. Identity uses all remaining header fields except the station identifier (originator, event code, purge time/duration, issue time); location codes (areas) are Transmission target Addresses, so a header with five areas is one Transmission with five Transmission targets. The station identifier is a Transmission attribute, so a rebroadcast by another station may join the original Message. Storing audio/video in the filesystem or object storage and playing it back is planned for a later version and is outside this contract.
- **Text canonicalization for comparison:** Protocol terminators and padding (for example POCSAG EOT) are removed by the Gateway adapter as Protocol specifics. Control characters are treated semantically and are not displayed as literal text: line breaks are part of the Payload (CRLF/CR canonicalized to LF for comparison), leading/trailing whitespace is ignored for comparison, and other control characters (for example BEL) are compared as code points and replaced by suitable representations for display. original Payload is stored unchanged; canonicalization applies to comparison only and is versioned with the identity rule. Search normalization is not reused.
- **Incomplete Transmissions (v1: exact comparison only):** v1 Messages only exact canonical matches. The submission may carry an optional Incomplete marker, which is stored and projected but does not relax matching in v1. A similarity heuristic is drafted for a later version: normalized edit-distance similarity within one Payload form and the time window, configurable threshold, configurable minimum length (default: shorter Payload at least 50% of the longer), a Transmission joins only if exactly one candidate Message qualifies, otherwise it always starts a new Message (failsafe), and joined members are marked as incomplete/deviating with their similarity value. It was deferred because thresholds require a calibration corpus of real bit-error Transmissions, Messages would need a canonical member and per-membership match kind, transitive drift (A~B, B~C, A!~C) must be prevented, and a false merge could visually hide a different Payload. The v1 membership model reserves a match-kind field (`exact`) so the heuristic can be added without changing existing memberships.

**Permissions:** Protocol Payload and Transmission target/Address fields are not public metadata. All fields receive C-06 projection; unknown new fields receive no automatic grant. Project i18n never translates original Protocol Payload before comparison.

**Submitted fields per Protocol (draft until AP-04 freeze).** Checked on 2026-10-25 against Wikipedia (POCSAG: 21-bit address, 2 function bits, 4-bit numeric codes; EAS: SAME header layout, at most 31 location codes) and the multimon-ng sources (FLEX output has a capcode and a type but no function bits; numeric code tables). The FLEX type list and the short/long capcode details come from secondary sources and training knowledge and still need verification against the FLEX specification:

| Protocol | Transmission target (Address + Function) | Payload forms | Payload identity fields | Transmission attributes, not identity |
| --- | --- | --- | --- | --- |
| POCSAG | RIC (integer 0–2,097,151) plus Function 0–3 (often shown as A–D); bit/subaddress meaning is decided by the Address rule | `text` (alphanumeric), `numeric`, `tone-only` (Address only) | Form plus canonical value | Bit rate, Gateway Network identifier, Quality metrics, Incomplete marker |
| FLEX | Capcode (integer; short and long capcodes as one numeric space); no Function. A group message is resolved by the Gateway adapter into the member capcodes as several Transmission targets (multimon-ng tracks group assignments, group capcodes from 2,029,568); if the adapter does not know the members (missed assignment), the group capcode itself is the Transmission target | `text` (alphanumeric), `numeric` (standard, special, numbered), `tone-only`, `binary` (transparent, secure) | Form plus canonical value; for `binary` also the subtype | Message number of numbered types, fragment/continuation flags (reassembled by the adapter), phase/frame, Quality metrics, Incomplete marker |
| ZVEI | Five-tone sequence as a five-digit string `0`–`9`; the repeat tone is resolved by the Gateway adapter | `zvei-signal` | Technical double-tone name, or "no double tone" | Tone timing, Quality metrics |
| EAS (SAME) | Location code `PSSCCC` per area (up to 31 per header) | `eas-header` | Originator, event code, purge time, issue time (`JJJHHMM`) | Station identifier, header repetitions/EOM (handled by the adapter), audio/video (not supported) |

Each Transmission carries the Protocol, optional Gateway Network identifier, Observation time, Payload with its Payload form, zero or more Transmission targets, and optional Quality metrics and Incomplete marker. `tone-only` has an empty Payload; ZVEI and EAS Transmissions have at least one Transmission target. SMTP-based and other Protocols need their own Protocol definition before use; they are not part of the initial set. The identity-rule version increases with every change of this table's identity columns or canonicalization.

**Open/fixtures:** Concrete wire types of Network and Transmission target identifiers and safe query correlation across Transmissions (P-09, AP-02); the EAS-area-to-Unit boundary (Address rules for location codes, AP-02); verification of the Protocol facts above. The Gateway adapter supplies complete Transmissions and any reported Transmission targets, but does not interpret Payload meaning, assign Units, or perform Grouping of Transmissions. Fixtures must distinguish payload-identical Transmissions with changed Transmission targets from genuinely different Payload, Group calls from separate Transmissions, and same/different Payloads for each supported Protocol. Raw frame/checksum/reassembly behavior is outside the GoPager contract. Safe assignment/query correlation across Transmissions belongs to AP-02 and remains a P-09 blocker.

## C-03 Message Grouping

**Version/status:** 0.1-draft. **Owner:** DOM-02. **Producer:** stored Transmission evidence with C-02 identity. **Consumers:** DOM-06 and C-08 Domain events. **Draft interface:** `AssignTransmissionToMessage(context, transmissionRef, payloadIdentity, groupingPolicyRevision) -> membership, messageRef, changeKind (created | joined | merged, with absorbed Message refs)`.

**Defined:** GoPager determines Payload identity and Messages matching Transmissions of the same Payload form and value across Protocols, Gateways, and Networks; the Gateway neither compares independent Payload nor submits authoritative Message membership. Network/Gateway alone do not split a Message. Preserve each Transmission, Network, and observed Transmission target separately; a Message is not an operational incident. Resolve each reported Transmission target against the applicable current Address-to-Unit assignments independently of Message membership. The window slides along member Transmissions (see the rules below), and each independent Transmission is distinct from a transport retry. Per D-17/REQ-122, there is one shared configurable Grouping policy, not a claim that Transmissions grouped into Messages describe one operational Domain event.

Grouping always uses the reported Observation time from C-01; this time basis is fixed and is not operator-configurable. The timestamp must include an explicit UTC offset or UTC designator and is compared as an unambiguous instant, never replaced by server acceptance time. **Grouping rules (user decisions 2026-10-25; draft until AP-04 freeze):**

- **Window `W`:** operator-configurable, default 30 seconds. `W` = 0 disables Grouping: every Transmission forms its own Message. There is no upper limit other than the maximum value of the chosen duration data type.
- **Boundary:** inclusive. Two Payload-identical Transmissions are linked if their reported instants differ by at most `W`.
- **Message definition (chain rule):** a Message is the set of Payload-identical Transmissions connected by a chain of links (each consecutive gap `<= W`). The result is therefore independent of acceptance order: Transmissions at 0 s, 50 s, and later 25 s (`W` = 30 s) form one Message, exactly as acceptance order 0/25/50 would.
- **No maximum Message age.** The previously recorded default of 180 seconds is withdrawn (user decision on 2026-10-25, choosing to drop it rather than apply it only at ingest). A limit applied only when joining would be bypassed by merges and would reintroduce order dependence. Consequence: continuously repeated identical Payload (for example a stuck transmitter) forms one Message of unbounded duration.
- **Late/out-of-order Transmissions:** linked by reported Observation time, not by arrival order. There is no lateness cut-off: a Transmission may link to any retained Message, however old. Messages or Transmissions removed by retention are no longer candidates. The 2-hour lateness tolerance recorded by the user is a fallback only if unbounded late linking proves disproportionately complex; AP-01 assessment is that a lookup by Payload identity and member instants within `[t-W, t+W]` does not require it.
- **Merge on gap closure:** if a new Transmission links to more than one existing Message, those Messages are merged. The surviving Message is the one with the earliest first member instant (then earliest created). Each absorbed Message keeps its ID as a permanent alias that forwards to the survivor; forwarding resolves chains to the final survivor, so IDs already passed to other systems never dangle. Message memberships move to the survivor; Transmission evidence is unchanged. With merging, no candidate tie-break is needed.
- **Configuration changes:** each assignment records the policy revision active at assignment time (`groupingPolicyRevision`); there is no revision pinning per Message. A new revision applies to every assignment processed after the change takes effect, independent of the Observation time of the Transmission (user decision 2026-10-25); an assignment already in progress completes under the revision it started with, which the per-Payload-identity serialization makes unambiguous. In v1 a configuration change does not dissolve, split, merge, or recompute existing Messages; it applies to subsequent assignments, which may link or merge existing Messages under the new `W`. Regrouping existing Messages after a configuration change, reusing the merge/alias mechanism and a split equivalent, is recorded as an investigation item for a later phase.
- **Configuration permission:** changing the Grouping configuration requires a dedicated, grantable capability (not implied by other administrative rights); every change is audited with the old and new values and the resulting revision. Enforcement belongs to C-06.
- **Domain event changes:** the Grouping domain emits a Domain event for each Message membership change: Message created, Transmission joined an existing Message (including a late join to an old Message), and Messages merged (survivor and absorbed IDs). These are new facts, not corrections of earlier Domain events. How consumers react (for example the frontend showing an additional Unit, or a push integration updating or reissuing a Delivery according to subscription and provider capabilities) is defined by their own contracts (C-07, C-08, C-09).

The server performs all comparisons from submitted Transmissions; a Gateway may not deduplicate or merge Transmissions to extend a Message. Transport retries do not extend the window by inventing a Transmission or a new Observation time.

**Transaction/concurrency:** Message membership, Message revision, and required Domain event must remain consistent; simultaneous matching Transmissions must not accidentally create duplicate Messages; assignment and merging are serialized per Payload identity. Validate SQL serialization/claim strategy and C-01 derivation boundary on both backends. Rematching, lifting suppression, and workflow changes are not regrouping.

**Projection:** Global last-Transmission time, Message size, and Gateway list are not automatically visible. DOM-06 projects from permitted Transmissions; hidden Transmissions must not leak through counts, ordering, or change indicators.

**Open/blockers:** Handed over: the duration data type that bounds `W` (AP-03); Domain event names, Payload schemas, and the alias-resolution API for consumers (C-08, AP-02). Later phase: the regrouping investigation and the similarity heuristic. Decided but not frozen before AP-04: time basis and its format/plausibility (C-01), policy-revision activation, default and range of `W`, inclusive boundary, chain rule with merge and alias forwarding, absence of a maximum Message age, late linking without cut-off, configuration-change behavior, configuration capability, and Domain event changes. AP-01 records fixtures for these questions; no unresolved choice is treated as approved.

## C-04 Units, Organizations, and Unit Collections

## C-05 Assignments, Suppression, and Rematching

## C-07 REST, Search, Details, and Live Updates

**Version/status:** 0.1-draft. **Owner:** DOM-06; integration owns OpenAPI/Domain event boundary; C-06 exclusively owns permission semantics. **Parties:** Vue/API consumers receive authorized projections, not internal database objects.

Draft operations: `QueryMessages(Principal, filters, timeAnchor, cursor) -> page`; `GetMessageDetail(Principal, MessageRef) -> projection`; `ListFilterOptions(Principal, context) -> safeOptions`; `OpenLiveView(Principal, viewDefinition, resumeState) -> authorizedChangesOrResync`. Response envelopes, endpoints, error codes, and cursor format remain open until versioned OpenAPI freeze.

**Query semantics:** OR within a dimension, AND between dimensions. Gateway, Network, Unit, and Unit collection conditions must match the same permitted Transmission/assignment. A Message cannot fabricate a match from Network A of Transmission 1 and Unit B of Transmission 2. 'Without Unit' requires genuinely unassigned authorized evidence, not hidden assignments.

**Text search:** Literal substrings, case-insensitive, Unicode-consistent, accent-sensitive. Empty search text applies no text filter; `.*` or `%` are user text, not regex/SQL wildcards. **Projection before result formation:** Apply suppression, current grants, and field permissions before filtering/counting/pagination/details. Two hours is not mandatory. Resume does not prove unchanged permissions; safely resynchronize if resume state is insufficient.

**Revocation/failures:** No further private output under revoked sessions/stale permissions. Safe invalidation may Address IDs already known to that consumer without exposing other objects. Payload already sent to a browser is not promised recallable. Unknown/invisible objects must not become an existence oracle.

**Language/i18n boundary:** Product-generated status, error, and validation outcomes use stable machine-readable codes and structured parameters, documented in English; their user-facing wording is Localized text drawn from the frontend text catalog, with an English fallback and no reliance on parsing server prose. Keep Protocol data, operator names, field names, enum values, timestamps, cursor semantics, and search/authorization behavior independent of UI language. User formatting locale is not an API translation switch. Exact code/parameter catalog and fallback mapping belong to AP-02/AP-09/AP-13; no second translation catalog is required.

**Open:** Stable sorting/cursor/time anchor, age anchor for long-lived Messages, revocation linearization, live-age rules, resume/resync envelope, filter-option permissions, cost limits, concrete error/text code mapping. AP-02/AP-03; P-08..P-10/P-12/P-15.

## C-08 Domain events, Outbox, and Jobs

**Version/status:** 0.1-draft. **Owner:** DOM-07 for mechanics, producing domain for Domain event meaning, integration for commit boundary. **Producers/consumers:** Gateway/Message/assignment/configuration changes -> explicit live/rematch/Delivery work.

Draft interfaces: `AppendDomainEvent(transaction, producer, DomainEvent) -> domainEventRef`; `ClaimJob(context, role, workerRef) -> leasedWork`; `CompleteJob(leaseRef, result)`; `RescheduleJob(leaseRef, classifiedFailure)`. Proposed Domain event fields: Domain event ID, type/schema version, producer, domain reference/revision, domain/recorded times, causality/idempotency reference, access-classified Payload. Exact envelope/required fields are not frozen.

**Defined:** Domain state and required Domain event/work are atomic in the primary store. Outbox state is truth; wake-up/pubsub is optimization only. Do not deliver a Domain event as committed before commit. Domain event types at least distinguish Message creation, Transmission joined (including late join), Messages merged, assignment/correction, subscribable Gateway states, and subscribable Operational Domain events (at least rejected Submission, implausible Observation time, and ambiguous Network; C-01); no hidden once-per-Message default. Exact type names/order remain open.

**Permissions:** Recording a Domain event does not replace current consumer/Delivery authorization. Raw Payloads are not browser/plugin grants. **Open:** Domain event types/envelope, revision order/replay scope, claim/fencing form, TTL/heartbeats, cancellation/dead-letter/retention, backend wake-up. AP-02/AP-03; P-01/P-04/P-11/P-12.

## C-13 Account Deletion, Audit, and Future Identity

**Version/status:** 0.1-draft. **Owner:** DOM-05; integration coordinates deletion; DOM-07 owns Delivery fields. **Parties:** confirmed account owner/authorized security manager, all personal-data owners.
