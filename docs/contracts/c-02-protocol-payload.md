**Version/status:** 0.2-draft, AP-04 D-34 amendment to the 0.1-draft baseline; not frozen. **Owner:** DOM-02; DOM-01 owns submitted originals. **Parties:** Gateway submits finalized Transmission reports; ingest, Assignment and Grouping consume them. **Failure:** Missing required fields or invalid declared-form data are rejected, not treated as empty/certain. A valid report of partial reception is different and must be retained.

The Gateway contract carries declared Protocol, original reported Payload, zero or more targets with Function/signal attributes, context and optional quality metrics. Finalizing this report does not certify reception completeness. EAS submits supported header Payload with areas as targets; POCSAG/FLEX/SMTP may report multiple targets in one report. No decoder/frame/checksum/reassembly internals are added to the server contract.

The Gateway does not determine Payload identity, Unit resolution, merge independent reports or assign membership. GoPager owns comparison/Grouping and current Address-rule evaluation. One multi-target Transmission has exactly one current Message after derivation, including W=0; never split it by target or Unit. Each target retains its own original Address/Function and stored derived resolution; usable targets support shared Message contributions through Contribution supports (C-05). Neither target resolution nor contribution identity determines Payload identity. Comparison normalization/versioning/collision checks remain server-owned; Gateway supplies no authoritative Message ID.

Original supplied Payload and reported Transmission targets remain distinguishable and preserved. Gateway/Network are Transmission context, not blanket Grouping keys. Transmissions with different Transmission targets may still be Payload-identical; Transmission targets remain per-Transmission evidence and are resolved independently by the server. Payload equality is not determined from display labels alone, and search normalization is not implicitly reused for Grouping. A later compact reference/delta representation (for example, a later Transmission referring to prior Payload plus changed Address/time) is optional future transport optimization; it does not change server ownership of identity, assignment, or Grouping.

**Payload identity rules (user decisions 2026-10-25; draft until AP-04 freeze):**

- **Protocol definitions own identity fields via Payload forms.** There is no fixed, closed class catalog. Each Protocol definition maps each of its Transmission types to a **Payload form** plus a normalized value and declares which completed-Transmission fields are identity versus Transmission attributes. Two Transmissions are Payload-identical only if form and normalized value are equal, regardless of Protocol. Initial forms: `text` (POCSAG and FLEX alphanumeric), `numeric` (POCSAG and FLEX numeric, normalized to a shared numeric character set), `tone-only` (POCSAG Address-only calls and FLEX tone-only types; no Payload), `zvei-signal` (ZVEI double tone or "no double tone"), `eas-header`, `binary` (FLEX binary/transparent and secure types; opaque bytes), and the D-34 `flex-short-signal` mapping [below](#ap-04-flex-clarification). Numeric and text never match each other ("123" numeric is not "123" text). Forms without a counterpart in another Protocol simply never match it (ZVEI forms never form a Message with POCSAG). Adding a form or mapping is a versioned identity-rule change.
- **Character sets (user decision 2026-10-25):** decoding Protocol character sets, including national variants such as the German DIN 66003 POCSAG variant (`[` as `Ä`), is Protocol handling by the Gateway adapter according to its configuration. The `text` Payload is submitted as Unicode text; the server does not reinterpret characters per Network.
- **Numeric character set:** POCSAG and FLEX numeric types use 4-bit codes. Numeric identity is defined by the code sequence, not by decoder glyphs, because sources and decoders render codes 0xA–0xF differently (ITU-R M.584 as summarized by Wikipedia: 0xA reserved, 0xB `U`, 0xC space, 0xD `-`, 0xE `)`, 0xF `(`; multimon-ng POCSAG: 0xA `.`, 0xE `]`, 0xF `[`; multimon-ng FLEX: 0xA as space, 0xE `]`, 0xF `[`). The Gateway adapter submits the code sequence in the shared canonical glyphs (user-confirmed 2026-10-25), one per code: `0`–`9`, 0xA `.`, 0xB `U`, 0xC space, 0xD `-`, 0xE `)`, 0xF `(`. Equal code sequences therefore give equal strings. Trailing 0xC padding is removed by the adapter; other leading and trailing spaces are ignored for comparison as for `text`. An adapter whose decoder cannot distinguish codes (for example multimon-ng FLEX 0xA versus 0xC) must take the code from the decoder or document the limitation.
- **Binary (user decision 2026-10-25):** FLEX binary/transparent and secure types are accepted as form `binary`: the Payload is the unchanged byte sequence, the identity is the subtype (`transparent` or `secure`) plus exact byte equality, and it is never shown as text. No decryption or interpretation takes place.
- **Address and Function are never Payload identity.** Transmission target Address (RIC, capcode, ZVEI sequence, EAS area) and Function/subaddress values are original target attributes. POCSAG Function mode (function-bit or subaddress) is selected by the Address rule during resolution, not by Grouping. Payload "abc" with target B Function a, target C Function b, and target D as subaddress has one Payload identity and three technical targets.
- **Empty Payload is still Payload.** POCSAG Address-only Transmissions and FLEX tone-only Transmissions share the form `tone-only` and are Payload-identical to each other; normal Grouping applies across Addresses and across POCSAG/FLEX. Consequence accepted by the user: unrelated tone-only Transmissions within the window form one Message; projection still shows only permitted Transmissions.
- **ZVEI:** the five-tone sequence is the Address reported as a Transmission target. Payload is the optional double tone, identified by its technical tone name, or the explicit value "no double tone". Sequences without a double tone are Payload-identical across Addresses; sequences with the same double tone are Payload-identical. Grouping by Unit-specific double-tone meaning was evaluated and rejected for now: one sequence may resolve to several Units with different meanings, so a Transmission would have ambiguous Payload identity and Grouping would depend on mutable Unit configuration. Unit-specific meaning remains a projection concern.
- **EAS:** audio/video Payload is not supported initially. Identity uses all remaining header fields except the station identifier (originator, event code, purge time/duration, issue time); location codes (areas) are Transmission target Addresses, so a header with five areas is one Transmission with five Transmission targets. The station identifier is a Transmission attribute, so a rebroadcast by another station may join the original Message. Storing audio/video in the filesystem or object storage and playing it back is planned for a later version and is outside this contract.
- **Text canonicalization for comparison (D-44):** Protocol terminators and padding (for example POCSAG EOT) are removed by the Gateway adapter as Protocol specifics. Control characters are treated semantically and are not displayed as literal text: line breaks are part of the Payload (CRLF/CR canonicalized to LF for comparison), leading/trailing whitespace is ignored for comparison, and other control characters (for example BEL) are compared as code points and replaced by suitable representations for display. Normalize the resulting text comparison value to Unicode NFC before exact comparison; do not case-fold or apply compatibility normalization. Original Payload is stored unchanged; canonicalization applies to comparison only and is versioned with the identity rule. Search normalization is not reused.
- **Partial/deviating Transmissions (D-29, scope corrected by D-30):** Retain every validly submitted original Payload, including truncated/erroneous values and its optional Incomplete marker. Match only exact canonical identity in the current scope. A shorter/different canonical value does not join a fuller value through similarity, regardless of arrival order or marker; equal partial values may group exactly. Do not reconstruct or overwrite originals. Invalid transport shape remains rejected under C-01 and decoder reassembly stays on the Gateway. Absence of an Incomplete marker proves neither completeness nor correctness.

**Comparison extension boundary (D-30):** Keep canonical identity construction and candidate comparison separate from C-03 membership/merge decisions. The current comparison accepts compatible form/subtype and exactly equal canonical values; hashes only accelerate lookup, never replace equality checks. It must not depend on Unit matching, GUI representation or search normalization. A later comparator can propose non-exact candidates using retained originals, but needs a separately approved contract for temporal candidates, ambiguity, policy/versioning, correction and authorization before activation. No heuristic implementation, thresholds, scores, per-form activation, background reconsideration or split machinery is required now. Reserve distinguishable membership match kind `exact`; do not introduce speculative score/configuration fields or a plugin framework solely for future use. Previous text-on/default/prefix/50% discussions are withdrawn from current scope, and 85% was never confirmed.

**Permissions:** Protocol Payload and Transmission target/Address fields are not public metadata. All fields receive C-06 projection; unknown new fields receive no automatic grant. Project i18n never translates original Protocol Payload before comparison.

**Submitted fields per Protocol (draft until AP-04 freeze).** Prior POCSAG/EAS checks and their limits remain in the [source notes](../requirements-evidence.md#protocol-source-checks). FLEX was subsequently reviewed against ARIB RCR STD-43A, with explicit AP-04 findings and approval in [D-34](../authoritative-plan.md#ap-04-flex-decision). The [AP-04 clarification](#ap-04-flex-clarification) supplements the original Payload-form rules above; it is not retroactive protocol certification.

| --- | --- | --- | --- | --- |
| POCSAG | RIC (integer 0–2,097,151) plus Function 0–3 (often shown as A–D); bit/subaddress meaning is decided by the Address rule | `text` (alphanumeric), `numeric`, `tone-only` (Address only) | Form plus canonical value | Bit rate, Gateway Network identifier, Quality metrics, Incomplete marker |
| FLEX | Integer decimal radio address, not extended CAPCODE notation; short and long addresses in the same address space; no Function. Each Transmission carries the Protocol, optional Gateway Network identifier, Observation time, Payload with its Payload form, zero or more Transmission targets, and optional Quality metrics and Incomplete marker. `tone-only` has an empty Payload; ZVEI and EAS Transmissions have at least one Transmission target. SMTP-based and other Protocols need their own Protocol definition before use; they are not part of the initial set. The identity-rule version increases with every change of this table's identity columns or canonicalization.

## AP-04 FLEX Clarification

**D-34, 2026-10-25; owner DOM-02 with DOM-01; version 0.2-draft.** Gateway producers and ingest/Grouping/query consumers use this backend-owned mapping. Evidence: [AP-04 direct standard review](../execution/ap-04.md#e-06-direct-flex-specification-review), ARIB RCR STD-43A sections 3.8/3.9/3.10, chapter 4/5 and Appendix A. These facts and decisions do not select a decoder.

- Short numeric messages from Short Message Vector type `00` at non-Network addresses map to the existing `numeric` form and canonical numeric code sequence. The normal numeric preservation/comparison rules apply. A three-digit short message and an otherwise equal numeric message are not different merely because their vector encodings differ.
- Source-code variants `01` and `10` map to `flex-short-signal`, whose Payload value is the original integer Source code `0..7`. Canonical identity is this form plus that code. Message number and retrieval indication are preserved attributes, not identity. These reports do not match empty `tone-only`, `numeric` or `text`; different codes do not match each other. Invalid types/ranges fail validation rather than becoming empty tone-only.
- Pure Short Instruction/Network-control data used for group setup, system notification or Network-ID operation remains Gateway protocol handling, not an ordinary user-message Submission. It must not be fabricated into text/tone-only Payload. The existing opaque Secure-message handling is unchanged and implies neither encryption nor decryption.
- The target integer denotes the Appendix A decimal address portion. Full CAPCODE strings carrying frame/collapse/phase/roaming notation are not accepted in that field. Short/long addressing is not a different Unit/address namespace, and decimal values must be retained exactly, including values beyond a 32-bit unsigned integer.
- Appendix A Table A-1 distinguishes normal short addresses `1..1933312`, Temporary Addresses `2029568..2029583`, other special/reserved classes and long-address ranges beginning at `2101249`, with the defined table ending at `4297068542`. A single min/max check must not silently admit illegal/unused/reserved values as ordinary pager targets. Group and other special-address uses are distinguished by the protocol definition, not mapped to invented individual recipients.
- Temporary-group enrollment identifies individual addresses and the applicable temporary address/frame before the shared message. A Gateway with those assignments submits known concrete member addresses as targets in one finalized Transmission. Without known members, the existing fallback remains the temporary group address; no complete-membership assertion or server-side reconstruction is introduced. Common programmed group addresses do not reveal individual members merely by receiving the shared call.
- Fragment reconstruction remains entirely Gateway-owned. Finalized incomplete reception can be reported with the existing Incomplete marker; the server does not receive an RF fragment stream or join unrelated Submissions as decoder fragments.

Compatibility: this is a deliberate draft identity-rule amendment, not an additive field that old comparators may ignore. Producers/consumers must agree on the amended form mapping before implementation. Planned positive/negative cases are [F-42..F-44](reference-cases.md#ap-04-protocol-cases). Shared schema-version selection and a machine-readable schema remain subject to AP-04 freeze; no application or SDK artifact is claimed.

## Early Matcher Target Candidate

**Version/status:** original-target 1.0, frozen 2026-10-27 by explicit user approval under [D-60](../authoritative-plan.md#early-master-data-and-matcher-prerequisite-proposal). **Owner:** DOM-02, with DOM-01 retaining original evidence and DOM-04 consuming validated targets. **Scope:** only the target/protocol boundary needed by AP-08's standalone matcher; no Payload, comparison, Submission or Grouping implementation approval.

The authoritative original-target 1.0 Protocol/Address/Target serialization, validation and FLEX class/range handling are [the shared typed definitions](../../internal/protocols/targets.go), with [boundary and JSON tests](../../internal/protocols/targets_test.go). Accepted domains and special-address distinctions retain the table and D-34 above. Unsupported attributes, fractional/overflowing numeric Addresses and cross-Protocol forms are invalid, not ignored. ZVEI/EAS leading zeros are preserved, with no geographic expansion. No address-mode flag on a submitted POCSAG target overrides the matching rule's mode.

The internal typed target representation must preserve these distinctions without floating-point parsing. Validation/classification is owned by the shared Protocol definition, not duplicated in the matcher. Rule ranges must consist of supported addresses; merely validating two endpoints must not admit intervening reserved addresses or erase Protocol class distinctions. The authoritative FLEX class table is Appendix A Table A-1 of the official standard linked by the [direct source review](../execution/ap-04.md#e-06-direct-flex-specification-review), not an assumed continuous min/max interval.

DOM-04 receives an ordered validated target list and does not sort, deduplicate or rewrite it. Original-target reference/ownership/empty-list rules stay exclusively in [C-05](c-05-matching-correction.md#original-target-reference). [The AP-08 handover](../execution/source-ap-08.md#handover) binds these actual typed artifacts; it does not freeze or implement the remaining original Payload, Submission or Grouping schemas.

## Early Processing Source Projection Candidate

The [classified context builder](../../internal/processing/capture.go) supplies the approved [C-06 source-context memberships](c-06-identity-authorization.md#fixed-field-group-review-candidate) for trusted owner projections. It does not resolve Networks, authorize a source or replace the AP-06 original owner; current visibility masking precedes capture.

**Version/status:** processing-source 1.0, explicitly frozen 2026-11-01 as part of the user's `approve-processing-kernel-1.0` approval; execution start remains separate. No Submission/Payload-identity freeze or implementation follows. **Owners:** DOM-02 for Protocol/form/schema interpretation, DOM-01 for immutable evidence/reference, DOM-04 for current target context. DOM-08 receives a validated bounded projection, never foreign tables or unchecked raw JSON.

The internal projection has `transmissionId`, Protocol and declared form/subtype, original Observation instant, source revision, current resolved Network, Assignment/context revision, and ordered current target contexts referencing original positions. Source revision identifies immutable owner evidence/projection schema, not editable text. Order/duplicates and assigned/unassigned distinctions use D-60 types; current Unit/collection context uses the name-free internal port. No fabricated target for an empty original target list.

Projected values use [shared typed values](c-09-delivery.md#early-shared-typed-predicate-candidate), closed owner-provided declarations and classified dependencies. A dependency identifies source Transmission, field category and applicable Network/original-target context, not a cached permission decision. C-06 remains the sole authorization engine. Protocol/form metadata is context data, not automatically public.

The Protocol owner validates form/fields before projection. Text/numeric extraction sees the unchanged supplied Unicode string, not normalized comparison text or display-substituted controls. Tone-only has no text value; binary remains opaque bytes, never implicitly textual regex input. Structured ZVEI/EAS/FLEX-signal values are projected only through explicitly declared typed fields, retaining original meaning without geographic expansion or Unit-specific reinterpretation. An arbitrary `RawMessage` cannot establish validity by naming a Protocol/form.

T043's evaluator/fixtures consume the typed projection. Preview accepts a validated synthetic projection with server-checked declarations/context, or a stored reference resolved by its authenticated owner in a live transaction. Synthetic data is not authority for fetching stored sources/Units/Networks. Missing stored-source owner yields explicit dependency/authority unavailable, never an empty fixture/raw fallback.

The implemented internal handover shape is [the detached source capture and owner port](../../internal/processing/capture.go). This port requires a trusted producer's prior Protocol/form validation; it is deliberately not a public DTO allowing a caller to invent field declarations. Target declarations also describe targetless absence/classification without fabricating a target. [AP-12 E-09](../execution/source-ap-12.md#e-09-target-result-kernel-implementation-and-bounds) records fixture validation and its missing real-owner limitation. The [approved C-11 target-result binding](c-11-processing-presentation.md#target-result-binding-candidate) determines how captured contexts produce outputs; it does not transfer original-evidence ownership.

This handover establishes projection types/validation/ports, not original intake, decoder, full Payload transport, canonical identity or Message membership. AP-06 separately freezes/implements its originals and wires these ports; until then no production original-source route is claimed.
