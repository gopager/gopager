**Defined:** Stable internal Principal separate from credentials. Direct/multiple User group grants are additive; read scope A and write scope B remain distinct. API keys can only restrict further. Deleting a restricting scope object never makes a grant unrestricted. No default access for new Principals/guest; guest cannot be deleted; explicitly warn about public write grants.

Evaluate Network/Unit/Unit collection/account scopes and field rights centrally; search AND is separate. Current published target resolutions and Message contributions store Unit directly, including corrected history; pending/stale values do not authorize. Matching email establishes neither identity nor account linkage. New plugin/processing fields are not implicitly readable. Authorization age uses first permitted Unit-appearance evidence as specified below, consistently for details/Delivery/feed.

**Credentials/recovery:** Local password only with permission; setting/changing/recovery do not bypass its exclusion. Changes check old and confirmed new password. Administrators neither know nor set a user's new password; use short-lived one-time proof plus correct username. Do not disclose unknown accounts. Without secure Delivery, recovery creates a request. Only the authorized owner creates personal keys; technical-account keys require target permission. Rotation/revocation/last use remain traceable.

**Consistency/failures:** All output paths check current authoritative state. SQL predicates and field projection share AuthZ semantics; no filtering after already unauthorized pagination. Login/search/sending throttling must not disproportionately block shared locations solely by shared IP. Audit without secrets, rejection without others' details. Display-language selection changes no authorization outcomes.

## AP-02 Grants, Actions and Fields

Historical pre-D-69 schema, superseded for field ownership by [identity-fields1.0](#unscoped-field-permission-replacement-candidate): `subject` (Principal or flat User group), `actions` (explicit nonempty list), one `scope` (kind plus references or explicit all), `fields` for reads, optional `maxAgeSeconds` (absent = unlimited), stable ID/revision. A grant is an additive allow, not an ordered deny language. No mandatory compound/intersection scopes or Organization-specific grant dimension in v1. Organizations remain a correlated query filter; Unit/Unit collection scopes provide the required manageable access.

Scope-kind spellings are `all`, `network`, `unit`, `unitCollection`, `account`, `withoutUnit`; applicability/restrictions are defined in the action table below. Action suffix shorthand such as `rule.preview/activate/reprocess` expands to `rule.preview`, `rule.activate`, `rule.reprocess`, not an action containing slashes. The catalog is explicit, not a permission generator for every resource/suffix combination.

| Action catalog | Applicable scope / restriction |
| --- | --- |
| `message.read`, `message.detail`, `without-unit.read` | all/Network/Unit/Unit collection, evaluated on a concrete Transmission target/Message contribution; without-Unit only all/Network. Detail additionally needs read. |
| `unit.read/create/update/delete`, `organization.read/create/update/delete`, `unit-collection.read/create/update/delete`, `address-rule.read/create/update/delete`, `suppression.read/create/update/delete` | Unit or Network where meaningful; Organization/Unit collection mutations require all or their explicit manageable member scope and all affected uses. No delete through hidden cross-Network use. |
| `gateway.read/create/update/delete`, `network.read/create/update/delete`, `grouping.configure` | Network/all; Grouping configuration is installation-wide all only, separately audited. Gateway submits only through its own assigned Network credential. |
| `account.read/create/update/delete`, `account.delete-own`, `grant.manage` | Account/all; own profile/deletion does not imply managing others' grants. A permission manager can delegate only explicitly granted delegable actions/scopes; no privilege creation through Grant editing. |
| `password.local`, `recovery.request`, `recovery.issue`, `recovery.consume`, `session.manage-own` | Account/all as applicable; consume additionally proves username/proof. Own-session management cannot revoke other accounts. |
| `key.create-own`, `key.manage-own`, `key.manage-technical` | Own Account; explicitly scoped technical Account/all technical accounts for technical management. No creating another human's personal key. |
| `subscription.manage-own`, `subscription.manage-global`, `delivery.read/retry/redeliver` | Own Account or delegated technical Account; affected data/targets still require current permitted scope. Global administration is not global data read. |
| `rule.preview/activate/reprocess`, `presentation.manage`, `notice.manage` | Network/Unit/all for applicable processing scope; installation notices all. Saving drafts uses `rule.create/update`; reading/removing uses `rule.read/delete`. |
| `plugin.install`, `plugin.configure`, `plugin.internal-read`, `audit.read`, `operations.manage` | Install is local Operator authority only; configuration all or delegated instance; internal read additionally declares SDK operation/Field sets and requires an effective data grant. Audit Account/Network/all where meaningful; operations all. |

**Processing-instance read binding, D-100:** The current narrow kernel requires existing global `plugin.configure` for redacted administrative instance read/list operations, matching its existing configuration authority. No separate read action or instance scope is added. General delegated-instance configuration remains a later capability, not an implemented scope inferred from the catalog above. C-10 owns configuration redaction.

Field sets: `payload` (readable original/representative display), `address` (Address/Function), `unit` (Units/Organization/collection labels), `gateway` (Gateway/Transmission context/instants/markers), `quality`, `derived` (explicit Processing-result schemas) and named `extension.<plugin-id>.<field>`. Canonical comparison values are not a substitute GUI text. Message ID/View time are minimal result metadata; internal Message time is not automatically disclosed. Grant union remains within matching target/contribution context, not unrelated evidence. Hidden co-targets need their own rights; Message access does not expose all receipts.

An Access key contains allowed actions/scopes/fields and optional shorter age/lifetime restrictions; effective rights are owner-rights intersected with the key restriction. Its usage is attributed to the owner plus nonsecret key ID. No key body or custom scope grants rights the owner lacks. New Principals/Guest start with no grants; deletion of scope objects disables affected grants, never removes their restriction.

**Age:** Optional; default unlimited. Among matching read grants choose the largest permitted age, unlimited winning; intersect a restricting key age. Evaluate the first Unit appearance within its permitted scope using the minimum supporting Contribution age anchor (C-07), not global Message time or latest reception. `now - anchor <= maxAgeSeconds` is inclusive. Apply the same rule to feed, details, search and Delivery projections; no field-level clocks. A later repeat for the same Unit does not renew eligibility; a genuinely new Unit appearance has its own age without granting old/hidden evidence. No mandatory per-user age configuration/UI.

### Unscoped Field Permission Replacement Candidate

**Version/status:** identity-fields 1.0, explicitly frozen 2026-11-01 by the user (`unscoped_field_contract_freeze=approve-identity-fields-1.0`) under D-69/D-70; implementation start remains separate. **Owner:** DOM-05/integration; producers identity configuration/authority, consumers point authorization, native Ent filtering and source/field projection. Scope is only the required AP-06/AP-08/AP-12 identity prerequisite correction, not general account/Recovery/key issuance management.

Authoritative implemented record types are [FieldPermission](../../internal/authz/fields.go) and [Grant, Restrictions and Authority](../../internal/authz/grants.go); the [identity Ent schema](../../internal/persistence/ent/schema/identity.go) owns storage shape. FieldPermissions have no actions, data scope, Network/Unit/Gateway references or age restriction. Duplicate permission effects combine additively; effective groups are the union of the active Principal's direct and current group records. Absence grants no fields. Removing a permission/group membership revokes its effect at the current access revision. No ordered deny/override language or implicit administrator fields.

Scoped action/data grants remain independent and no longer carry active field permissions. `Authority` resolves both current action grants and current global field permissions under the same primary access lock/revision. An operation requesting fields must satisfy its action/data/age checks and the separate global field check. `message.detail` additionally requires the scoped `message.read` action/age and its own detail action/age, with requested groups checked globally once rather than scoped to either grant. Field permissions alone give no readable rows.

Restricting Access-key actions/scopes/age continue intersecting owner data rights. The key's existing explicit field allow-list intersects the owner's global effective groups and never adds rights; it has no per-scope field conditions. Key absence of a field still denies that field. No key issuance/lifetime/HTTP proof precedence changes.

Permission delegation checks both components separately: delegated action scopes cannot exceed the actor's delegable action rights; global field groups cannot exceed the actor's globally delegable field permissions. A scoped `grant.manage` permission is not sufficient by itself to mint global field access; the replacement management binding requires current installation-wide `grant.manage` authority for global field-permission changes, plus the relevant delegable field groups. No general remote permission-editor implementation follows from this prerequisite candidate.

Point authorization validates the global requested groups independently of target matching. Native Ent planning validates those same groups once and composes only scoped action/age/key predicates for row eligibility, eliminating the old per-field row-scope disjunctions. It still filters before paging/counting and preserves same-target read/detail/data correlation. Source/derived dependencies retain their eligible source references and required global field groups; they cannot expose otherwise forbidden evidence or turn hidden input into public output.

Persistence introduces owner-specific field-permission rows/indexes under existing Ent/privacy guards and the shared access revision. Creation/change/removal, audit and required access-change fact commit atomically. Bootstrap explicitly selected global groups become separate records within the existing bootstrap transaction; bootstrap still grants no unselected permissions. Existing metadata reads never expose confidential credentials. The existing platform/HTTP/Session/fact append APIs and namespaces remain unchanged.

**Fresh-development binding, resolved under D-70:** The user states that no deployed running instances exist and authorizes changing the unpublished model. Implement the fresh-installation schema and explicit split bootstrap; do not add a production legacy-field conversion, compatibility API or Operator reassignment workflow solely for nonexistent deployments. The earlier A/B transition alternatives are superseded as unnecessary preparation. Local development databases are not silently deleted/reset; unsupported old development schema/data receives an explicit incompatibility error where applicable, not guessed global field assignment.

Required conformance: scope A plus global Address permission permits Address fields only on otherwise allowed A evidence; scope A/B plus global Address permission makes Address fields equally available in both; absent global Address permission rejects Address projection/search; field permission alone authorizes no row; group union/removal and key intersection match between point/SQL decisions; detail never widens data/age; unsupported old development state is not silently promoted/deleted; fresh schema/bootstrap is atomic with required authority revision/audit/fact. Commands/HTTP/proxy behavior remains the approved transport tuple.

## HTTP Transport and Human Authentication

**D-52; version/status:** Application-wide HTTP support is approved; contract remains draft pending AP-04 owner review/freeze. **Owner:** DOM-05 for identity/authentication, with Operations/persistence owning application transport in [C-12](c-12-persistence-operations.md#application-http-transport). **Consumers:** all application routes, including AP-06 T022.

Every application function, including human login, Recovery, protected administrative routes and Session-backed use, must work over HTTP. GoPager does not require TLS, force an HTTP-to-HTTPS redirect or require a separate HTTP setting. Operators may terminate TLS at a reverse proxy; direct HTTP also remains supported. On direct HTTP, an on-path observer can read or alter passwords, Recovery proofs, bearer credentials, Session cookies, Payloads, metadata and responses, and may impersonate users. GoPager makes no confidentiality or server-authentication claim for HTTP. Under the explicitly approved D-52 clarification, Session cookies use `Secure` when the configured public application Origin is HTTPS and omit it when that Origin is HTTP; a proxy-to-GoPager HTTP hop does not determine the browser cookie attribute.

This rule supersedes any narrower C-06 transport rule below, including the draft TLS-only requirement for human credentials, `Secure` Session-cookie requirement and Gateway-only HTTP exception. Authorization, CSRF-token and Origin checks remain in force; they do not provide confidentiality for HTTP traffic.

The configured public application Origin is an absolute HTTP(S) scheme/host/optional-port without user information, query, fragment or non-root path. It is a common deployment value for either transport, not an HTTP opt-in. Cookie-authenticated state changes validate the actual browser Origin against it and require the Session-bound CSRF token. Login/Recovery browser endpoints also reject foreign Origins; no wildcard credentialed CORS is enabled. Untrusted `Forwarded`, `X-Forwarded-Proto`, `X-Forwarded-Host` or caller-supplied Host values cannot replace the configured Origin. API-key/Gateway requests still use their explicit Authorization credentials, not Cookie authentication inferred from a forwarding header.

### HTTP Credential Selection Addendum

**Version/status:** HTTP credential-selection 1.0, frozen 2026-10-26 by explicit [D-57 approval](../authoritative-plan.md#http-credential-selection-decision). **Owner:** DOM-05; producer/consumers and implementation scope remain those of the approved identity prerequisite.

An explicitly present Authorization header selects API-key bearer authentication even when a Session cookie is also present. Exactly one well-formed bearer credential is required. Invalid, empty, unsupported or duplicate Authorization values reject authentication; they never fall back to the Cookie or Guest. Only absence of Authorization permits Session-cookie selection; only absence of both permits explicitly anonymous Guest resolution. A bad or duplicate Session cookie likewise never becomes anonymous. Session-bound CSRF/Origin checks apply when Cookie authentication is selected, not to an ignored Cookie beside an explicit bearer credential.

### Local Identity Inputs

**D-71 internal producer adapter:** the explicitly approved [ResolvePrincipalAuthority](../../internal/identity/authority.go) supplies current validated owner authority to C-10's separately authorized execution-Principal binding in the caller's live primary transaction. It uses the same shared lock and current account/group/grant/global-field/scope checks, carries no credential/Session/CSRF proof, has no HTTP route and grants no caller-facing impersonation authority. Under D-54, a local username has preserved display spelling and a separate unique comparison key: NFC, full default Unicode casefold, then NFC. Use the same pinned `golang.org/x/text` implementation for creation, lookup, Recovery and throttling; do not use locale-specific casing or email matching. Validation requires a nonempty username of at most 128 Unicode scalars and 512 UTF-8 bytes, valid UTF-8, without control characters or leading/trailing Unicode whitespace. Technical accounts have the same stable Principal identity but never acquire an implicit human-login capability.

Password creation/change/Recovery use the same byte-preserving validator and local-password capability check.

Account creation, credential creation and bulk commands use the shared actor-bound command identity. Secret-bearing responses are displayed once; losing a response never makes the stored secret retrievable. Status lookup exposes only nonsecret references/state; retrying the same command cannot create another effective credential. Explicitly revoke/reissue when the one-time secret is lost.

### Shared Authorization Surface

`AuthorizeAction(context, transaction, authority, action, target) -> Decision` and `BuildAuthorizedReadScope(context, transaction, authority, action, requestedFields, now) -> AuthorizedScope` use the same current structured grants and Ent predicate composition. `Decision` has allowed/denied outcome and permitted nonsecret provenance; `AuthorizedScope` is an opaque domain-level constraint, not an Ent client/entity or SQL string. Missing, revoked or stale authority cannot turn into Guest or unrestricted internal authority. An explicitly anonymous request resolves the existing Guest subject with its actual grants.

The target identifies the concrete relevant Network, Unit/collection membership, Account or without-Unit context. Grants combine only within that target/contribution context. Apply owner-rights union before intersecting Access-key restrictions. Optional maximum age uses C-05 anchors; an absent maximum means unlimited, never zero. Unknown actions/fields/scopes are invalid, not implicitly allowed. A deleted restricting reference disables that grant. Explain decisions only within caller-readable context; a denied result does not expose another account, target or grant.

`ChangeGrants` / `ChangeUserGroupMembership` checks expected revision and current `grant.manage` authority, including the existing delegability restriction. It writes configuration, access revision, safe audit and required invalidation facts atomically. No action wildcard or built-in administrator bypass replaces the explicit catalog. Local bootstrap/rescue uses C-12 Operator authority, not a remote permission bypass.

Private operations load primary-authoritative credential/account/grants and relevant revisions in their transaction. Serialize protected mutations and credential revocation on the applicable authority rows; a revocation that commits before the authorization point prevents the action. Public DTO construction and each bounded private-output batch revalidate current authority; data already handed off is not recallable. Never cache an unrestricted Ent client, raw entity response or previous decision as sufficient authority after revision change. Authority/storage failure stops the operation with the C-07 code rather than stale success.

## AP-02 Credentials and Recovery

- Passwords: Argon2id with random per-password salt and encoded algorithm/parameters; minimum 12 Unicode scalars, maximum 1024 UTF-8 bytes, no truncation/normalization/composition rules. Initial candidate floor: 19 MiB memory, 2 iterations, parallelism 1, never silently downgraded; AP-03 must validate constrained-host cost/rate limits and AP-04 pins an approved configuration. Increase/rehash on valid login under versioned configuration.
- Session/key/Recovery-proof secrets: cryptographically random at least 256 bits, hashes only in authoritative storage, one-time secret display. Session cookies Secure/HttpOnly/SameSite=Lax, host-only; TLS is mandatory for public transport of human passwords, recovery proofs and reusable user bearer credentials. Cookie writes require CSRF token plus Origin validation; bearer keys use Authorization header, never URL. Sessions expire after 30 days absolute or 7 days inactivity, configurable shorter; password change invalidates other Sessions and outstanding Recovery proofs. Gateway Bearer credentials are the explicit D-45/D-47 exception and may be sent over HTTP.
- Common recovery flow: `RequestRecovery` creates the account-bound Recovery request with a uniform public accepted response, regardless of account existence. `IssueRecoveryProof` follows either authorized manager approval (manager passes the token to the User) or automatic dispatch through an admin-designated recovery-capable integration to a previously verified account-bound contact. Both paths use the same proof record, 30-minute lifetime, username requirement, one-time atomic consumption and local-password capability check. Never log the proof or expose it through ordinary Subscriptions/Delivery history.
  - D-52 and the public-Origin rule above supersede any stricter transport wording in this historical AP-02 draft paragraph. Effective behavior is: full HTTP support for the whole application, and Session-cookie `Secure` derived from the configured public Origin rather than upstream transport.
- A trusted email integration may supply recovery initially. SMS/push is possible only through an actually available suitable integration, not an AP-02 promise to implement extra targets. Missing/failed automatic transport leaves an explicit pending request for authorized manager handling; transport uncertainty is not proof that no token was sent. Local administrative rescue always remains possible, explicitly scoped/audited, issuing a short-lived recovery path rather than silently replacing an account or granting permanent bypass.
- Access key lifetime: instance default 90 days, operator-configurable including unlimited; explicit requested expiry shown before issuance. Self-rotation allowed within owner rights, new secret displayed once; optional old/new overlap at most 24 h, then old key revoked. Revocation/password policy changes immediately increment access revision. Store only nonsecret ID, owner, restrictions, created/expiry/revocation and last-use times.
- Proof consumption marks a nonsecret consumed receipt until expiry plus 24 h, then removes it; passwords/proof secrets never survive account deletion. Revoked credential receipts need no reusable bearer material.
- Default throttles (configurable, not capacity promises): login 10 attempts/minute per normalized account key plus 300/minute instance; recovery 3/hour per account plus 60/hour instance; proof consumption 10/minute per request; search 60/minute per Principal/key; outbound starts 60/minute per Subscriber and configured target/provider rate. Use bounded buckets and generic errors; unknown-account buckets behave the same. Shared IP is only a secondary abuse signal, never the sole identity. `RATE_LIMITED` includes safe retry delay.

## AP-06 Gateway Bearer Credentials

**D-45/D-47/D-48; version/status:** HTTP support, Bearer mechanism and lifecycle policy approved; credential issuance/wire/storage details remain draft until AP-04 freezes C-01/C-06. **Owner:** DOM-05 for authentication/authorization; DOM-01 owns Gateway submission and Network assignment. **Consumer:** AP-06 T022; Gateway adapter implementations remain outside AP-06.

Each Gateway has a Gateway-specific reusable Bearer credential, distinct from a Principal/API key. It authenticates exactly one Gateway and grants no rights beyond current Gateway Network assignments or the applicable C-06 action. An administrator authorized for `gateway.update` issues and revokes it for that Gateway using the Gateway's expected revision; `gateway.read` can inspect credential status. A credential consists of 32 cryptographically random bytes encoded as 43-character unpadded base64url; display it once and store only its SHA-256 hash with its nonsecret UUID credential ID, Gateway, creation/use and revocation state. Issuance returns the secret once; a lost response does not reveal or reissue it. The administrator can inspect the nonsecret ID/status, revoke that pending credential and issue another. Credential administration uses the normal protected administrative channel; D-45's HTTP exception applies to Gateway-authenticated requests, not human login or credential management. Requests carry the credential only in the HTTP `Authorization: Bearer <credential>` header, never in a URL or request body. Exactly one Authorization credential is accepted; duplicate or malformed Authorization headers are rejected. Never log or expose the credential in error details. Invalid credentials return the generic `LOGIN_REQUIRED` response without revealing whether the Gateway or credential exists.

The credential is reusable and is transmitted as a Bearer value on every request. HTTP therefore permits an on-path observer to obtain and reuse it until revocation; GoPager does not provide confidentiality or transport replay protection. C-01 Submission-ID idempotency still applies to repeated Submissions but is not a general replay defense. Direct HTTP also exposes Payloads and metadata and does not authenticate responses. Requests may use HTTPS; a TLS-terminating reverse proxy may provide transport confidentiality if its upstream path is also protected. GoPager accepts HTTP without a separate setting and does not redirect or claim it is confidential.

Credentials have no automatic expiry and remain valid until revoked. Rotation allows one pending replacement: both the current and replacement credentials work until the replacement's first successfully authenticated request. That request atomically promotes the replacement and revokes its predecessor before domain authorization; subsequent authentication using the old credential fails. A second replacement cannot be issued while one is pending. A revoked credential is rejected on the next authentication decision using current authoritative state. A request already authorized before a concurrent cutover may complete; cutover cannot recall in-flight work. Gateway authentication does not bypass current authorization, Network declarations or revision checks. Replay protection is not part of D-45/D-47/D-48.

**AP-07 credential-slice planning (D-112/D-119):** AP-07's exact Gateway credential/proof and administrative-authorization details are frozen in its own C-06 slice under D-119; a separate AP-04 contract package was not a prerequisite. The D-45/D-47/D-48 Gateway credential format/lifecycle is frozen only as consumed by this AP-07 slice; the rest of C-06 remains draft. This current status supersedes the AP-06 handover's then-current draft/freeze note, which records status at that time only.

### AP-07 Gateway Credential-Management HTTP Addendum

**Version/status:** AP-07 Gateway credential-management HTTP 1.1, approved under [D-121](../authoritative-plan.md#ap-07-gateway-credential-management-http-addendum). This supplements, but does not rewrite, the frozen Gateway HTTP Authorization 1.0 slice above. **Owner:** DOM-05; DOM-01 owns Gateway assignment and revision semantics.

Credential issue/revoke operations require an Administrative Principal with `gateway.update` coverage over every current Network assigned to the Gateway, or an `all`-scope grant. Status reads require `gateway.read` over every current assignment or `all`. All checks use authoritative current Gateway and Network state in the same transaction as the protected operation. The Gateway-specific credential remains distinct from Principal/API-key authority and authenticates only its Gateway.

Credential management uses the normal protected administrative HTTP channel, including existing human Session, CSRF, Origin and transport protections. The direct-HTTP exception for Gateway-authenticated requests does not apply to credential administration. Secret material is returned only by the initial successful issue response, never by status reads or command replays; only nonsecret credential ID and lifecycle status may be inspected. Existing D-47/D-48 format, one-pending-replacement rule, first-use cutover, revocation and no-automatic-expiry semantics remain unchanged.
