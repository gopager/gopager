Gateway contact, reported diagnostics and state-transition history must remain stored or exactly reconstructable so authorized administrators can distinguish which Gateways produced evidence for a Message and whether a Gateway had problems. State projection remains subject to C-06/C-07.

**Defined:** A Network has one domain Protocol; a Gateway may submit for multiple allowed Networks. An authorized unambiguous declaration precedes inference; reject unauthorized declarations rather than silently redirecting. An absent declaration (resolved by inference or the default Network) and an unauthorized declaration (rejected) are different outcomes. Simple single-Network Gateways need no artificial frequency ranges.

**Network resolution (user decision 2026-10-25; frozen for AP-07 under D-119, while remaining draft for other consumers):** A Gateway is assigned to one or more Networks. A Submission may declare its Network by a Gateway Network identifier: a Gateway-local identifier that the Gateway's configuration maps to exactly one of its assigned Networks. Only Networks assigned to the Gateway are ever used; there is no global built-in fallback Network. A Gateway has exactly one **default Network** for each Protocol it uses, including a Protocol with only one assigned Network under D-115; `ConfigureGatewayNetworks` rejects a configuration without it. The server resolves the Network of each Transmission in this order (user decision 2026-10-25):

1. **Declared:** a mapped Gateway Network identifier determines the Network. An identifier that is not mapped for this Gateway, or maps to a Network the Gateway is not assigned to, rejects the Submission (see failures); it is never silently redirected.
2. **Inferred, single:** without a declaration, if the Gateway is assigned to exactly one Network of the submitted Protocol, that Network applies.
3. **Inferred, by Address:** otherwise, among the Gateway's Networks of that Protocol, the Network in which at least one reported Address has an Address rule valid at the Observation time applies, if exactly one such Network exists.
4. **Default Network:** otherwise (no Network or more than one Network has a matching Address rule) the Gateway's default Network for that Protocol applies. If more than one Network matched, an Operational log entry is written and an Operational Domain event (ambiguous Network, default applied) is emitted, so administrators can fix the configuration or let the Gateway declare its Network.

The submitted declaration is immutable Transmission evidence; resolved Network and method (`declared`, `inferred-single`, `inferred-address`, `default`) are derived. Candidate Networks are recomputed, not stored as authoritative evidence. Current Gateway Network configuration and current Address rules determine the published resolution; rule domain validity is evaluated at the original Observation time. Do not require a historical immutable Gateway-configuration snapshot merely because D-29 retains original timestamps. Mapping/rule changes trigger C-05 Rematching without rewriting the declaration or retroactively treating the original accepted Submission as rejected. If current configuration no longer permits a safe resolution, invalidate the affected derivation and expose a pending/failed state to authorized managers, not a fabricated Network/Unit or changed original receipt. Initial unauthorized declarations remain rejected at intake.

Each Gateway owns transport and technical Protocol handling: frame/signal evaluation, Protocol integrity and fragment reassembly. Here "completed Transmission" means a finalized Gateway report in the C-02 schema, not a guarantee that reception recovered all information correctly. A report may contain partial/erroneous Payload and an optional Incomplete marker; retain that original under D-29. GoPager does not accept raw RF/audio frames or take over decoder/reassembly work. SMTP/non-radio adapters use the same finalized-report boundary.

The Gateway adapter does not perform Payload interpretation, map Addresses to GoPager Units, or perform Grouping of independent Transmissions. It submits the completed original Payload and the Transmission targets available from that Transmission. A Group call is submitted as one Transmission with multiple Transmission targets; this does not permit an adapter to merge separate Transmissions or decide that their Payloads are equal. GoPager performs the Payload-based comparison, resolves Address targets against current logical assignments, and links Transmissions into Messages, including across Gateways and Networks. Quality metrics are optional: if supplied, they must already be evaluated and include enough context to be meaningful; raw technical measurements and quality interpretation are not required of GoPager. An optional compact reference/delta submission format is a possible later bandwidth optimization, not part of this contract.

The Submission preserves original reported Payload, targets and context unchanged, even when reception was partial. Required transport/Protocol shape still must be valid; a damaged value valid for its declared form is not rejected merely for differing from a fuller reception. Every independent Transmission includes an offset-bearing Observation timestamp; compare/store its instant independently of Acceptance time. Missing or timezone-ambiguous Observation time is invalid; Acceptance time is never a fallback.

**Observation time format and plausibility (D-42 precision decision; AP-07-consuming behavior frozen under D-119, while remaining draft for other consumers):** The Observation time is an RFC 3339 date-time with a mandatory numeric UTC offset or `Z`. Gateways should preferably send whole-second values. Fractional seconds may be submitted, but the server discards all fractional digits without rounding before storing the Observation instant or using it for Network inference, Address-rule validity, Grouping or retry comparison. The supplied UTC offset is retained with the normalized whole-second instant; `.000` denotes the same instant as the corresponding whole-second value. This deliberately loses up to, but not including, one second of reported precision and can change Grouping or Address-rule boundary results; see [F-47](reference-cases.md#ap-04-observation-precision-case). The D-42 policy supersedes the earlier user decision to preserve and compare nonzero fractional seconds at their supplied precision. Observation times in the past are accepted without limit. An Observation time later than the server time plus a configurable clock-skew tolerance is accepted and processed normally, including Grouping; the Transmission is marked `observation-time-implausible`, an Operational log entry is written, and an Operational Domain event is emitted so that administrators can subscribe Deliveries to it. The default clock-skew tolerance is 15 minutes. This does not automatically require recording raw radio signals. The Gateway adapter supplies an operation identity for each independent Transmission. A transport retry of the same operation creates no new server Transmission; an independent Transmission does, even if its Payload is identical to another Transmission's. **Idempotency (user decision 2026-10-25, clarified by D-42; AP-07-consuming behavior frozen under D-119, while remaining draft for other consumers):** Gateway plus Submission ID identifies an operation. Compare submitted content after normalizing Observation time by truncating its fractional digits and retaining its UTC offset. Thus, otherwise identical requests with the same offset and different fractional digits that truncate to the same second return the existing receipt and Transmission. Different normalized time, offset or other content under the same Submission ID is rejected as a conflict and never updates the accepted Transmission. Retries do not create new Observation times or advance a Grouping window. The server retains a Submission ID as long as the Transmission it created is retained. A retry that arrives after its Transmission was deleted by retention is accepted as a new Transmission; the user accepted this residual risk on 2026-10-25 because retries normally end long before retention deletes data (F-23).

**Time/transaction:** Acceptance follows the recorded intake transaction; its receipt/state boundary is specified below. An uncertain commit is not a definite failure. Queries/resubmissions respect idempotency and current Gateway permissions. Derived/publication completion is separate from recorded intake; AP-03 validates synchronous execution as an optimization, not a different semantic boundary.

**Rejected Submissions (user decision 2026-10-25):** A Submission is rejected as a whole, with a stable error code and no partial acceptance, if it is malformed: missing Observation time or one without offset, unknown Protocol, Payload that is invalid for the Payload form declared by the Protocol definition, unmapped or unauthorized Gateway Network identifier, a Protocol for which the Gateway is assigned to no Network, or a Submission ID conflict. A rejected Submission creates no Transmission. Each rejection writes an Operational log entry and emits an Operational Domain event (Gateway, Submission ID, error code, time; no Payload content) so administrators can subscribe Deliveries to it.

**Failure/cancellation:** Invalid/incomplete submission shape, unauthorized Gateway/Network, conflicts, storage shortage/write failure, and uncertain write authority are visible without exposing other Gateways/Networks. Protocol-frame, checksum, signal-decoding, and fragment-reassembly errors belong to the Gateway adapter. No silent deletion to free space. Cancellation after a possible commit cannot guarantee absence.

**Gateway state:** Never seen, active, degraded, deliberately stopped, and contact lost remain distinguishable. Transmission and heartbeat have separate times. Missing contact proves no specific crash cause; removed history does not disprove previous Transmission.

**AP-02 handover completed:** Common schemas specify JSON, identifiers, limits and contact timeouts. Receipt fields: `submissionId`, `transmissionId`, `acceptanceTime`, `processingStatus`, and `messageId` only if derived and authorized. Intake commit yields `accepted` with `processingStatus: pending`; it never implies publication or completed Parsing. `completed` means Grouping, current target resolutions and Message contributions and selected Workflows have finished; `failed` is inspectable/retriable internally, not a silently successful projection. AP-03 may validate a synchronous fast path under the same states; it cannot publish half-processed data. Commit durability/precision/backend strategy remains AP-03, not an executed AP-02 experiment.

**Rejection when storage is unavailable:** C-01's required Operational log/Domain event accompanies a durable rejection when storage permits. If the store itself is unavailable, return storage/authority error and emit a redacted process diagnostic; do not claim the Operational Domain event was committed or invent successful rejection persistence. Authentication failures do not disclose a foreign Gateway/Network. This makes the rejection invariant implementable during disk/primary failure.

## AP-05 Intake-commit Boundary

**Version/status:** intake-commit 1.0, frozen for AP-05 under D-35 on 2026-10-26; all Submission wire/schema/Protocol/Observation-time choices above remain draft. **Owner:** DOM-01 with integration. **Producer:** later authenticated intake repository; **consumer:** AP-05 transaction adapter and later C-08 producer adapters. Vocabulary: glossary G-1.0.

Intake persistence joins [C-12's transaction capability](c-12-persistence-operations.md#transaction-and-repository-participation). Future receipt/original evidence and required durable follow-up work must commit together; successful receipt means the recorded intake stage only. No receipt/`accepted` response is published before successful commit. Known rollback leaves no partial intake/outbox state; possible commit returns `COMMIT_UNCERTAIN` for same-operation lookup under current Gateway authority. The platform never generates a new Submission identity or reruns the callback to hide uncertainty.

AP-05 tests this boundary using explicitly synthetic repository participants, not production Transmission tables or an ingest API. Cases [F-46c/F-46d](reference-cases.md#ap-05-foundation-cases) bind atomicity and uncertainty. This partial freeze does not settle Observation precision, generate OpenAPI, implement Gateway authentication or transfer DOM-01 schema ownership.

## AP-07 HTTP Surface

**Version/status:** AP-07 HTTP Surface 1.0, frozen under [D-119](../authoritative-plan.md#ap-07-contract-freeze-proposal); the rest of the C-01 Submission/API remains draft. **Owner:** DOM-01; DOM-05 owns Gateway proof and administrative authorization under C-06; integration owns composition and shared commit. Product boundaries and routes are approved under [D-104..D-109](../authoritative-plan.md#ap-07-gateway-http-submission-boundary-decision); complete-replacement behavior and request representation are approved under [D-110](../authoritative-plan.md#ap-07-gateway-network-replacement-semantics-decision) and [D-115](../authoritative-plan.md#ap-07-gateway-network-replacement-request-decision); Gateway state-fact and success-response decisions are [D-116..D-118](../authoritative-plan.md#ap-07-gateway-state-fact-boundary) and [D-120](../authoritative-plan.md#ap-07-recovered-report-idempotency).

| Operation | HTTP boundary | Identity and effect |
| --- | --- | --- |
| `SubmitTransmission` | `POST /api/v1/transmissions` | Gateway-authenticated; derive Gateway identity from C-06 proof, never from a caller-supplied Gateway ID. Accept the completed C-02 Transmission and return the C-01 acceptance receipt/state. |
| `ReportGatewayState` | `POST /api/v1/gateway/state` | Gateway-authenticated; derive Gateway identity from C-06 proof. Report heartbeat, degraded status, explicit recovery, or termination separately from Transmission acceptance. |
| `ConfigureGatewayNetworks` | `PUT /api/v1/gateways/{id}/networks` | Administrative-Principal authenticated; replace the complete allowed-Network configuration under required `expectedRevision`. Reject an empty or invalid set without mutation; a stale revision is a conflict. No PATCH operation is included. |

Submission uses the common AP-02 JSON schema, limits, and receipt fields above; its accepted response means intake only, not completed Grouping, target resolution, or Processing publication. `SubmitTransmission` uses the C-01 receipt fields above and the C-07 status mapping: accepted/pending is 202, completed receipt is 200. `ReportGatewayState` returns 204 after commit. `ConfigureGatewayNetworks` returns 200 with `{schemaVersion:1, revision:string}` containing the committed Gateway revision. Failures use the shared C-07 redacted error envelope and status mapping. Gateway identity/proof and administrative authorization are bound by C-06; this HTTP error binding adds no alternate envelope or status system.

**Gateway-state report binding (D-113/D-114/D-116/D-117/D-120):** The closed request is `{schemaVersion:1, operation:"heartbeat"|"degraded"|"recovered"|"terminated", reasonCode?:string, detail?:string}`; unknown fields are invalid. Only `degraded` accepts these diagnostic fields and requires `reasonCode` (opaque ASCII identifier, maximum 64 bytes); `detail` is optional UTF-8, maximum 512 bytes. Other operations reject those fields. The server records authenticated contact time and the report; the values are diagnostic only and do not drive authorization or automation. Heartbeat records contact but does not silently clear degraded status; authenticated new contact ends contact-lost or stopped state as specified in shared conventions. `recovered` is an idempotent request to set active and records contact; if already active, it emits no state-change fact. Explicit termination records the stopped state. `gateway.state-changed` is appended only when the effective state changes, including changes caused by an authenticated Submission; a contact-only heartbeat or any same-state report does not emit it. Successful reports return 204 after commit. The operation must not accept caller-asserted `active` or `contact-lost`; those are server-derived.

**Gateway Network replacement request binding (D-110/D-111/D-115/D-118):** The closed body is `{schemaVersion:1, expectedRevision:string, networks:[...]}`; unknown fields are invalid. `expectedRevision` is a positive decimal signed-64-bit revision string. `networks` has 1..1024 entries, each `{gatewayNetworkIdentifier:string, networkId:UUID-string, default:boolean}`. Local identifiers are nonempty, at most 128 UTF-8 bytes and unique; Network IDs are unique; referenced Networks must exist and be assignable. Reject an empty or otherwise invalid set without mutation. For each Protocol represented, exactly one entry is marked as default, including when only one Network is assigned. Authorization requires `gateway.update` coverage for the union of current and proposed Network assignments, or `all` scope. A stale revision returns a revision conflict. Successful replacement returns `{schemaVersion:1, revision:string}` with the new Gateway revision. No PATCH is included.

**HTTP error binding:** All three operations use the common C-07 error envelope and status mappings. Missing/invalid credentials use `LOGIN_REQUIRED`; absent or hidden Gateways use `NOT_FOUND`; a valid Principal lacking the required action/scope uses `FORBIDDEN`; malformed bodies, invalid protocol data, or an unassignable proposed Network set use `INVALID_INPUT`; reuse of a Submission ID with changed normalized content uses `IDEMPOTENCY_CONFLICT`; stale configuration uses `REVISION_CONFLICT`; configured size excess uses `RESOURCE_LIMIT`. Storage, write-authority and uncertain-commit failures use the corresponding C-07 platform codes. Error parameters do not expose hidden Gateway/Network identifiers, Payload, credentials or private causes.


## AP-07 Gateway Credential-Management HTTP Addendum

**Version/status:** AP-07 Gateway credential-management HTTP 1.1, approved under [D-121](../authoritative-plan.md#ap-07-gateway-credential-management-http-addendum). This is additive to the frozen AP-07 HTTP Surface 1.0 above; those three routes and their semantics are unchanged. **Owner:** DOM-01 for routes and Gateway revisions; DOM-05 owns credential authorization and lifecycle.

| Operation | HTTP boundary | Identity and effect |
| --- | --- | --- |
| `IssueGatewayCredential` | `POST /api/v1/gateways/{id}/credentials` | Administrative Principal; issue an initial Gateway credential or one pending replacement under `expectedRevision`. |
| `ReadGatewayCredentialStatus` | `GET /api/v1/gateways/{id}/credentials` | Administrative Principal; return nonsecret status for the Gateway's credentials. |
| `RevokeGatewayCredential` | `DELETE /api/v1/gateways/{id}/credentials/{credentialId}` | Administrative Principal; revoke the identified credential under `expectedRevision`. |

The issue request is the closed JSON object `{schemaVersion:1, commandId:UUID, expectedRevision:string}`. First success returns `201 Created` with `{schemaVersion:1, credentialId:string, secret:string, revision:string}`. The secret is returned only in that first response. Repeating the same command returns nonsecret credential status and revision without the secret; reusing the command ID with changed input conflicts. An issue without a current credential creates the current credential; otherwise it creates the sole pending replacement. A second pending replacement conflicts. Existing D-48 first-successful-authentication cutover and revocation behavior applies.

The status operation returns `200 OK` with credential IDs, lifecycle status and permitted timestamps only; it never returns secret material or hashes. The pending credential ID is included so an administrator can inspect/revoke a pending replacement after losing the one-time secret response.

The revoke request is the closed JSON object `{schemaVersion:1, commandId:UUID, expectedRevision:string}` and returns `200 OK` with `{schemaVersion:1, revision:string}`. `expectedRevision` is a positive decimal revision string. Issuance/revocation require `gateway.update` coverage of all current Gateway Network assignments or `all`; status reads require `gateway.read` coverage of those assignments or `all`. All operations use the common C-07 redacted error envelope and status mapping. They use the normal protected administrative HTTP channel; the Gateway direct-HTTP exception does not apply.
