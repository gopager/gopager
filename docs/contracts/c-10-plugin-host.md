**Version/status:** 0.1-draft. **Owner:** Plugin host; DOM-07 owns Delivery/subscription semantics, integration owns SDK contract. **Producers/consumers:** Operator supplies artifacts; host checks/activates; modules produce/handle explicit Domain events or provide allowed targets.

Draft interfaces: `InspectModule(artifact) -> compatibility`; `ActivateModule(moduleRef, configurationRevision) -> lifecycleStatus`; `InvokeCapability(invocationContext, projectedInput) -> boundedResult`; `DisableModule(moduleRef) -> status`; `DeclareExtensionFields(manifest) -> validated definitions`. Manifest/SDK shape below is documentary, not an approved compiled ABI.

**Defined:** Separate Wasm artifacts from operator sources or local provision; Wazero embedded in Lite. Only operators install/update code. Web administrators configure permitted capabilities; users own allowed subscriptions. Lifecycle, update/rollback and incompatible/disabled/active/failed states are specified below. No marketplace, native legacy ABI, or arbitrary-language guarantee. English documentation and stable machine codes do not prevent a language-neutral SDK.

**Trust clarification (D-130, 2026-11-05):** Operator-installed plugins are fully trusted. The target capability includes direct host, device and network access, for example GPIO, displays, printers, building automation, MQTT and KNX. D-67's pure WASI command is only the first implemented subset for installed Processing steps; it is not a trust boundary or a limit for other plugins. The runtime model that provides this access is open (see the [architecture re-evaluation](../architecture.md#native-plugin-alternative-review)).

**Trust boundary (D-24):** Operator-installed plugins are trusted code. Explicitly approved host capabilities may include general network/SMTP/MQTT, filesystem and host/container command execution; no claim that Wasm confines a malicious plugin given such access. All SDK operations on Core entities, including other Units, must be declared in the Plugin manifest and pass current C-06 authorization. Host-level access can technically bypass SDK isolation (for example by reading a mounted database); the trust contract prohibits undeclared Core access but cannot guarantee enforcement against malicious privileged code. Operators must not grant such access to code they do not trust.

**AP-04 delivery amendment (D-33):** The initial first-party targets are separate Pushover and Webhook plugins; Telegram and email are later under the [scope decision](../authoritative-plan.md#ap-04-scope-decision). Initial Webhook capabilities are owned by [C-09](c-09-delivery.md#initial-target-capabilities). The retained future email boundary below does not require an initial SMTP implementation: an HTTP-only host API would not automatically support later email, which needs controlled SMTP or an explicitly selected mail provider path. For configurable webhooks/hosts, internal-target protection, DNS/redirect/TLS behavior, and secret forwarding belong to the security contract, not a blanket Network grant.

**Configuration exposure (D-33 clarification, 2026-10-26):** The [manifest configuration-field contract](#manifest-configuration-fields) is mandatory for SDK/API configuration, not optional UI metadata. C-09 owns the [configuration-authority boundary](c-09-delivery.md#configuration-authority), Pushover split and before-attempt checks.

**Transaction/failures:** Plugin failures cannot change another domain's data/grants or bypass attempt recording. Wasm adds isolation but is no complete security guarantee. The lifecycle below and C-09 define disable/update during invocation and uncertain provider results.

## Native Alternative Review Boundary

**Status:** approved documentary review under [D-65](../authoritative-plan.md#native-plugin-alternative-review), not a revised/frozen plugin ABI or implementation selection. The user also accepts separately supplied native-library-style plugins as an alternative to examine. [The architecture comparison](../architecture.md#native-plugin-alternative-review) distinguishes Go plugins, native C-ABI libraries, a bundled native child host and executable RPC plugins from the existing separate Wasm format.

If a native option is later selected, required artifacts/runtimes/dependencies ship under D-63, and the manifest/compatibility/configuration/Principal/capability/lifecycle/error boundaries below still apply. Loading native initialization is execution, not harmless metadata inspection. Direct loading shares Core memory/failure state and is not automatically bounded by a cancellable Go context. Neither native support, an arbitrary-language ABI, nor a replacement for the existing Wasm choice follows from this review. Full AP-11 implementation remains outside the T043 prerequisite scope.

## Early Installed Processing Invocation Candidate

**Version/status:** installed-processing 1.0, explicitly frozen 2026-11-01 as part of the user's `approve-processing-kernel-1.0` approval; execution start remains separate. D-67 selects the narrow pure WASI-command subset; D-66 separately selects restricted CEL-Go for shared predicates. **Owners:** plugin host/integration for invocation, DOM-08 for typed Workflow use. D-62 selects only the separate Core regex adapter.

Proposed initial boundary: separately supplied prebuilt WASI command plus version-1 closed manifest, executed in the selected Wazero tuple. Invocation uses bounded version-1 UTF-8 JSON on standard input/output, not a custom raw-memory callback/allocation ABI. WASI memory access validation is runtime-owned; Core still checks input encoding, closed schema/types/finite numbers, result length and context completion before accepting a result. Command start/exit/import semantics must match the approved runtime; no deployment-time compiler or dependency installation.

The concrete implemented manifest, artifact pin, recursive configuration policy and loader forms are owned by [the installed artifact definitions](../../internal/processing/artifacts.go). Unknown required capabilities/imports block invocation. Inspection reads metadata/compiles permitted imports without running initialization with live data/Secrets. The initial boolean-only preview limitation is preserved in [AP-12 E-21](../execution/source-ap-12.md#e-21-dedicated-preview-binding-gap); the approved optional separate binding and actual supplied preview invocation are verified in [E-22](../execution/source-ap-12.md#e-22-approved-dedicated-preview-invocation).

The concrete implemented input/output envelopes, pins, safe failure vocabulary and wire validation are owned by [the command boundary](../../internal/processing/installed.go); [Workflow invocation ports](../../internal/processing/installed_workflow.go) require separate current instance/Principal/source authorization and reject input substitution. No grants, credential secrets, foreign tables or unrestricted source. Mixed success/failure is invalid. Nonzero guest exit/trap/timeout/memory/malformed/oversized output is explicit failure; private stderr never becomes a public error or unredacted production log. [AP-12 E-10..E-13](../execution/source-ap-12.md#e-10-approved-bounded-artifact-loader) record actual partial evidence; the production administrative/current-authority/lifecycle adapters remain incomplete.

The host-only invocation context in those ports carries the actual [captured source reference](../../internal/processing/capture.go) and optional original body target independently of mapped field values. The participant must not infer that target from input values, a dependency union or a callback counter. [AP-12 E-19/E-20](../execution/source-ap-12.md#e-19-explicit-invocation-context-and-scoped-evaluation) verify this binding with identical actual guest inputs; no guest wire change or production current-owner completion is inferred.

The first adapter supports declared pure processing modules without external/OS capabilities or additional Core reads, using projected input from the current execution-Principal boundary. Modules needing later capabilities remain explicitly unavailable, not silently downgraded or counted as supported. Store-neutral invocation/authority/configuration ports retain extension points for AP-11; this subset does not remove D-24 host capabilities or complete AP-11.

Preview never executes effectful/undeclared-capability code. A separate declared pure-preview implementation may run with synthetic/authorized data under the same bounds; otherwise `capability-unavailable`. Stored samples/input require fresh execution-Principal grants/source-owner projection separately from the editor's action grant. Missing source/configuration/Secret/authority owner fails explicitly. No speculative Secret store: unresolved Secret references block activation/invocation.

Operator provisions artifact/manifest through the local persistent artifact-directory model. Administrative instance configuration is separately revisioned; Workflow activation validates capability/configuration/Principal binding. Digest/configuration pins are immutable during invocation. Disable/version switch prevents new old-version starts and cancels current calls best-effort. Missing artifact is dependency/capability unavailable, not a builtin stub.

**AP-06 startup/read additions, D-100/D-101:** Redacted administrative instance reads/listing use the existing global `plugin.configure` action under [C-06's narrow binding](c-06-identity-authorization.md). Local artifact provisioning is selected through explicit optional `--processing-artifact-root`, with no default path, downloads or runtime installation/compiler. An invalid configured root fails explicitly; omission leaves installed capabilities unavailable without disabling built-in processing. Existing rooted-path, size, digest, manifest, current-authority and joined-lifetime checks remain mandatory. Configuration views preserve the manifest redaction rules below; these additions do not supply delegated instance scopes, general installation or personal/Secret settings.

The narrow administrative revision representation is owned by [Processing instance types](../../internal/processing/instance.go), its [bounded local inspector](../../internal/processing/instance_artifacts.go), [current-proof command coordinator](../../internal/processing/management/instance.go), [native immutable snapshots/current pointer](../../internal/persistence/ent/processingstore/instance.go) and [additive schema migration](../../internal/persistence/migrations/00007_processing_instances.sql). This does not implement a general installer or personal/Secret configuration owner. [C-11's D-81 interpretation](c-11-processing-presentation.md#early-workflow-kernel-candidate) owns result-schema versus inherited visibility requirements.

[The current execution/lifetime adapter](../../internal/processing/instance_execution.go) now owns per-run main/preview preparation, fresh enabled instance/execution-Principal/global-field checks, required source-owner checks, committed-change cancellation and drained artifact cleanup. [The editor adapter](../../internal/processing/execution/preview.go) resolves the separate actual preview proof. [E-36](../execution/source-ap-12.md#e-36-current-installed-execution-and-per-run-artifact-lifetime) distinguishes actual PostgreSQL/supplied guest checks from still-required trusted activation/preview, production source and root/runner/HTTP composition. Callers must evaluate with the run context, join dependent work, close the run, then close shared host/root during shutdown; no unbounded cross-run artifact cache is introduced.

Shared 64 MiB memory, 1 MiB input, 256 KiB output and 30 s installed-call deadline apply. Core regex instead shares C-11's 1 s total built-in budget; installed capability does not turn every built-in step into a fresh 30 s allowance. Native alternatives remain D-65 candidates, not supported through disguised ABI compatibility.

This command-only candidate differs from the retained general guest-memory/host-function SDK draft below. ## Installed Artifact Load Bound Review

**Status:** fixed 32 MiB load extension explicitly approved for implementation under [D-73](../authoritative-plan.md#installed-processing-artifact-load-bound), preserving the prior installed-processing 1.0 history. **Owner:** plugin host/integration. Existing 1 MiB invocation JSON, 256 KiB output and 64 MiB guest linear-memory limits do not bound a provisioned Wasm binary before decoding/machine-code translation.

Apply one fixed product limit of **32 MiB per supplied `.wasm` artifact**, including any separate pure-preview artifact. Inspect/load must reject a larger or nonregular artifact before compilation, enforce the boundary while reading as protection against concurrent growth, validate the pinned digest on the exact bytes compiled, and use the existing bounded manifest decoder. Operator-rooted path handling must not permit reading outside the configured persistent artifact directory. Missing/mismatched/oversized artifacts remain explicit capability failures; do not truncate, download replacements, compile source, silently select an old version or treat the Core regex guest as the installed capability.

This is a binary-load byte bound, not a guarantee of total compiler/host RAM, preparation latency or supported language/toolchain. The actually supplied Core Go/WASI guest is 3,879,470 bytes ([AP-12 E-09](../execution/source-ap-12.md#e-09-target-result-kernel-implementation-and-bounds)); this shows the invocation's 1 MiB JSON cap cannot substitute for a Wasm artifact cap, not that every useful module fits 32 MiB. A fixed cap avoids a new runtime setting; a later need for larger modules requires an explicit reviewed bound change. Other invocation limits/capabilities/Principal/configuration policies and AP-11 scope remain unchanged. No arbitrary artifact is loaded under this proposed rule before approval.

## Manifest Configuration Fields

**Owner:** Plugin host/integration; AP-04 D-33 draft amendment, not a frozen machine-readable manifest/SDK artifact. Every configurable property must declare its type/validation, required/default behavior, explicit Secret classification, and `configurationScope`:

| `configurationScope` | Storage/configuration binding | Who may configure |
| --- | --- | --- |
| `admin` | Administrative plugin instance | Authorized administrator/Operator under C-06 `plugin.configure`; never ordinary personal Subscription authority. |
| `user` | Owning User within a configured plugin instance | That User, with current permission to use the instance and manage their personal configuration; never another User's configuration or an administrative override. |

The classification applies to every configurable value, including nested properties and collection elements. Container replacement, defaults and configuration merges must preserve it; mixed-scope containers cannot be replaced through a personal write to bypass an administrative child. Omission, unknown scope, conflicting declarations or an unclassified open-ended property invalidate the manifest at inspection/activation. There is no inferred user-editable default. Plugins without personal settings declare no `user` properties.

SDK/API reads and writes use the validated manifest version and enforce this classification server-side for all configuration paths. Configuration views expose only permitted fields and redacted Secret status. Requests containing unknown or unauthorized fields are rejected explicitly and atomically without persisting the permitted subset; hiding a field in the UI or silently ignoring a forbidden field is insufficient. Manifest declarations describe supported configuration, not new grants or permission to make C-09 administrative settings user-editable.

Invocation resolves the administrative configuration and only the applicable User's personal configuration under the existing invocation Principal/Secret rules. Identical field names or nested paths do not allow personal values to shadow administrative values. Manifest updates revalidate configuration and its scopes before activation; an incompatible scope change is a visible configuration failure, not silent promotion of personal input to administrative authority. Existing invocations retain their pinned version under the lifecycle rules.

[F-45](reference-cases.md#ap-04-plugin-configuration-cases) specifies planned positive/negative examples. AP-12 defines the generated manifest schema/SDK configuration types, authoritative paths and compatibility version before implementation.

## AP-02 Installation, Manifest and Invocation

- Operator provides prebuilt `.wasm` artifact plus manifest through a persistent directory/volume, image layer, or an operator-managed artifact source. No Core rebuild, compiler, npm/pip install or automatic remote code download at plugin installation/container startup. Docker updates preserve mounted artifacts/configuration. Runtime machine-code translation/cache of an already-built Wasm binary is not source compilation or an image build step; no persistent compiled cache is mandatory.
- Manifest requires plugin ID/version, artifact digest, manifest/SDK major/minor compatibility, offered Delivery/processing/Domain event capabilities, typed configuration/input/result schemas, Secret fields, Extension field definitions, required Core SDK operations/data Field sets, requested host capabilities and resource expectations. Unknown required capabilities or incompatible major versions block activation; additive optional fields may be ignored only as schema permits. Inspect never executes plugin initialization with active credentials.
- Lifecycle: installed -> validated -> configured -> active; incompatible/disabled/failed distinguishable. Configuration is revisioned and checked before activation. Install/update is Operator-only; web administrators can configure only delegated capabilities, Users only permitted targets/Subscriptions. Host/container execution is an explicit high-trust capability, not silently inferred from email support.
- Invocation envelope identifies plugin artifact digest, SDK version, capability, job/attempt, effective Principal, configuration and resolved Secret version, deadline/cancellation, typed input and correlation reference. Result is bounded typed output plus accepted/transient/permanent/uncertain status; no raw exception/SQL/credential details in public outcomes. Plugin may query other Units only through declared approved SDK operations under its explicit data Principal, not by inheriting the installer.
- SDK draft uses versioned UTF-8 JSON records and bounded length-delimited guest-memory buffers, host-owned invocation handles, explicit guest allocation/release, and one result ownership transfer. Caller copies a validated result before releasing memory; reject invalid ranges/overflow/UTF-8 and result schema violations. Host functions expose declared Core reads/publication and approved external/OS capabilities. This general draft is not the fixed pure installed-processing ABI. Exact selected signatures/runtime/toolchains are AP-12's bounded planning and validation using available AP-03 evidence; no unfinished AP-03 result, new AP-04 sign-off or arbitrary-language guarantee is required.
- Standard HTTP/SMTP helpers and optional connection/stream/command capabilities let compatible existing libraries own protocol logic. Core need not implement Telegram/SMTP protocol engines twice. Every mediated I/O has deadline/cancellation and size limits; plugin command execution still requires its declared Operator-approved capability. [D-63's managed-child boundary](c-12-persistence-operations.md#managed-child-process-clarification) permits application-managed subprocesses without an exact Core process-count restriction. Required application/plugin-host runtime dependencies must be supplied, not installed separately by the Operator. This topology clarification does not grant a plugin command/network/filesystem or Core-data capability.
- Update validates a new artifact/configuration without mutating running invocations. Existing invocations keep their digest/configuration/Secret version; no new old-version starts after activation switch. Disable stops new starts, cancels outstanding work best-effort, records uncertain effects honestly. Rollback reactivates a still-compatible preserved artifact/configuration; never undo external effects or silently downgrade incompatible state. Missing old artifact blocks its pending work visibly.

## AP-02 Secrets and External Transport

Core Secret store either encrypts local secrets using authenticated encryption with a separately provisioned master key/key ID, or resolves versioned external references. Kubernetes-mounted Secret files/environment and external-provider adapters are valid delivery paths; environment rotation requires process/configuration refresh, mounted file/provider rotation creates a new resolved configuration revision. No requirement to copy external values to SQL or bake them into images.

Manifest-declared per-instance Secrets may be supplied in plaintext only to that trusted plugin invocation; opaque handles are optional convenience, not a mandatory second security system. Other plugins/normal views receive neither values nor unauthorized references. Rotation pins the resolved value/version for the invocation, then drops it when finished; missing/expired Secret produces a visible configuration failure. Standard logs/errors redact secrets; there is no guarantee against a deliberately malicious trusted plugin printing or exporting them.

Core-owned configurable HTTP/webhook/SMTP transport validates URL/host/port, DNS results actually connected, TLS certificate/hostname and redirects. Default core transports reject loopback/private/link-local/cloud-metadata destinations and redirects; an authorized Operator may explicitly permit intended internal SMTP/MQTT/webhook infrastructure and external endpoints. Redirects, if deliberately enabled, revalidate destination and do not forward credentials to a different authority. A trusted plugin granted broad network/command capability may implement its own policy; that is explicit trust, not a falsely advertised Core SSRF protection.

The deferred email plugin supports configured SMTP with TLS/authentication and controlled status mapping; header/Address fields reject CR/LF injection, no shell construction from Payload. Standard public transport requires TLS; intentionally configured private infrastructure exceptions are explicit Operator policy, not silent downgrade. Initial target timing follows [D-33](../authoritative-plan.md#ap-04-scope-decision), not these retained future email requirements. Libraries are allowed if compilable/compatible; feasibility must be demonstrated rather than installing a second runtime unasked.
