## Multi-target Workflow Binding Review

**Status:** proposed clarification only, not part of the frozen workflow-kernel 1.0 subset and not an adopted execution policy. **Owner:** DOM-08/integration, with DOM-02/DOM-04 source-context and C-09 predicate consumers. Approval is tracked by [D-72](../authoritative-plan.md#multi-target-workflow-context-binding).

The frozen source projection retains ordered original-target contexts; transmission-level selection evaluates relevant contexts separately and selects at most one run per Workflow. Steps, branch conditions and final mappings may nevertheless refer to `target`. If two different original-target contexts match, their target-specific values can differ. The current binding does not specify which context those later references resolve against. Predicate-level correlation does not determine a post-selection winner.

Options requiring explicit owner resolution:

- **A, reject ambiguous target reads (recommended):** source-only processing still runs once after a match. An actually executed step/condition/final mapping that reads `target` requires an unambiguous selected context; several selected contexts produce an explained failed result rather than choosing one. Nonexecuted branch bodies do not cause this failure. Empty original target lists retain their existing absence/no-fabrication rules.
- **B, explicit first-match policy:** later target reads use the first matching context in immutable original-target order. Retain selection/classification dependencies as required by C-09. Other matching recipients remain original evidence, but do not supply that run's target-specific values. This is an intentional order-based processing policy, not a Unit/quality preference.
- **C, per-target outputs within one run:** evaluate target-dependent processing separately for matching contexts and return explicitly target-bound output sets under the Workflow namespace. Keep one durable Workflow run and do not split original Transmission/Message membership. This requires a revised result shape, aggregate-budget checks and corresponding consumer binding, not an implicit list loop or silent replacement of the frozen scalar output form.

Until resolved, do not implement post-selection target lookup or choose an implicit winner. Existing source, predicate, regex, installed-runtime and store-neutral work not depending on this choice remains permitted. No field permission scope or data-access rule changes through this clarification.

### Target-result Binding Candidate

**Version/status:** workflow-target-results 1.1, explicitly frozen and implementation-approved by `approve-target-results-1.1-and-implement` under D-72. The unchanged workflow-kernel 1.0 remains the historical freeze. This subset replaces only its ambiguous post-selection target binding and corresponding result container. It does not open presentation/Delivery implementation. The heading is retained for stable links.

**Evaluation cardinality:** Determine target dependence statically from all declared references in the immutable definition, including selector, all branch bodies, input mappings and final outputs. If none references `target`, evaluate once and retain ordinary Workflow-wide `fields`. Otherwise, evaluate the selector independently against every original target context, retaining immutable original positions/order and scope eligibility. Execute the body separately for each definitely selected context. A reference anywhere marks the definition target-dependent even if that branch is not taken; this predictable conservative rule avoids an additional dependency-graph optimization or configurable mode.

Each context is the existing original target plus its current resolved Unit/collection context, not a new iteration per collection or a cross-product of Units/addresses. Unassigned original targets remain real contexts; missing resolved fields retain declared optional absence. If the original target list is empty, do not fabricate one: evaluate once against the source with target fields readable-absent according to the owner declarations, and use Workflow-wide `fields` on success. A hidden target operand remains hidden, not absent. An indeterminate selector is unavailable dependency and cannot produce a complete successful result. Definite false selects no body. No selected contexts means not-selected, not an empty successful target-result set.

**Result container:** Keep one durable run/result identity for `(Transmission, Workflow, definition version, source/context revisions)`. A selected completed result has exactly one of:

- `fields`: the existing closed typed classified field map for one source-only or genuinely targetless evaluation; no `targetResults`.
- `targetResults`: a nonempty ordered list of `{targetPosition, fields}` for selected original target contexts; no top-level `fields`. Positions are unique references into that Transmission's original target list, never generated target IDs or list indexes reinterpreted as Unit IDs. Each entry uses the same Workflow's declared output schema. Different Workflows retain independent namespaces.

Management/preview status can explain not-selected, unavailable or failed contexts safely, but an incomplete list is never a successful completed result. Any selected context's failure fails the whole replacement result; no partial target-result publication. Preview reports the same shape/selection/failures without persistence. Private partial computation is not ready evidence.

**Classification/projection:** Each entry inherits all selector dependencies used to determine the selected context set, including hidden/short-circuited operands, plus its own executed branch/data/configuration/installed-output dependencies and declared `derived` field requirement. Do not copy another context's intermediate values. The shared selection dependency union is deliberately conservative; it can prevent projection when another selection dependency is no longer authorized. Keep current source/data-context eligibility separate from global field permissions. A downstream consumer explicitly selects an authorized target entry or processes entries individually; no flattening to an arbitrary first value, implicit merge or permission-bypassing fallback. A target result is not a new Transmission, Message, Contribution or grant.

**Budgets/publication:** Existing one-second accumulated built-in budget, 1 MiB aggregate input/intermediate/selection capture and 256 KiB complete-result boundary apply across the entire run, not freshly per target. Each installed invocation still has its existing 30-second limit; a target-dependent installed step can invoke once per selected context, so total sequential installed waiting can multiply by targets and configured steps. The existing finite original-target/step/input limits bound this work; no new parallel fan-out, total installed deadline or hidden truncation is introduced. If a valid input cannot finish within existing limits, fail explicitly and retain prior published evidence.

Multiple matching Workflows evaluate independently on the same immutable input and current derived context. Namespace isolation removes scheduling-order dependence; one Workflow cannot silently consume another's result. Presentation/Subscription mappings explicitly select a namespace/field. No duplicate or ambiguous unqualified field lookup. Processing fan-out is once per `(Transmission, Workflow, definition version, relevant input revision)` with C-08 idempotency/fencing; a retry does not duplicate a result/fact.

Extraction uses Go RE2-compatible regular expressions, without backreferences/lookbehind or runtime-specific backtracking. Pattern validation rejects unsupported syntax; named captures map explicitly to declared typed fields. No match is an explained absent optional value, not an execution failure; invalid required conversion/schema, resource exhaustion or plugin failure is an explicit failed result. Shared limits apply (128 steps, nesting 32, 1000 collection elements, 4096-byte pattern, 1 MiB input, 1 s built-in budget). C-10's 30 s bound applies to each installed code invocation; the finite step count also bounds the number of invocations. No unbounded loops, recursion or implicit external Delivery step.

Classification propagates from every input used to compute a field, including branch/selector dependencies, not just copied strings. A derived field requires its declared `derived` permission and the necessary source-field/context rights; extraction or a boolean condition does not declassify hidden text. Administrators cannot make a hidden field public by renaming it. A user-initiated preview needs `rule.preview` and read permission for all stored sample data; a synthetic sample is request data, not permission to fetch hidden Messages.

Core-owned built-in ingest derivation is internal processing, not a user grant or outbound capability. Installed code receives only its declared authorized input and current configured execution Principal; any further SDK read or external/OS access obeys C-10. Activation validates that capability/scope binding; it never captures the editor's temporary admin rights. Missing execution authority is an explicit failed/pending state, not an unrestricted worker fallback.

## Ingest Publication, Activation and Reprocessing

**Failed-work retry action binding 1.0:** approved under [D-78](../authoritative-plan.md#processing-failed-work-retry-action-binding). Explicit retry of a failed, still-unpublished current candidate requires scoped `rule.reprocess` and expected candidate revision, not `rule.update`, `rule.read`, inferred administrator rights or a new `rule.retry`. Validate current source eligibility and active configuration separately. Preserve cumulative/automatic attempt history; one authorized manual attempt does not reset an automatic cycle. This operation is distinct from historical Reprocess below and does not start a historical sweep or change historical replay/reaction policy.

1. Capture active Workflow versions and relevant current context for the accepted Transmission. No matching Workflow means the barrier is complete, not failed. Each selected Workflow must complete before its new evidence/results contribute to normal GUI/search/Delivery publication.
2. Original acceptance and internal facts can commit while Processing is pending. Managers see safe processing status; normal views do not receive the new unprocessed state. A failed Workflow leaves that state failed/pending publication, with authorized retry, not a silently successful raw-text substitute.
3. Compute without a long SQL transaction; publish results, ready target/contribution state and `processing.completed` facts with current revisions and C-08 fencing. Changed relevant input/configuration supersedes stale work. A pending new reception must not remove previously valid published evidence from an existing Message; select representatives only from ready readable supports.
4. `ActivateRuleVersion`/`SelectPreviousVersion` atomically change the active pointer with revision/audit. New inputs use it; pending work on the old pointer is superseded/reselected before publication. Already published results stay source/version-bound until explicit reprocessing; no automatic historical sweep or regrouping.
5. `Reprocess` requires `rule.reprocess`, explicit permitted source scope and chosen version. It uses current access/target state and preserves original Payload/membership. Replacement results publish atomically after success; invalidated source authority is never kept visible merely because a prior result exists. Historical external reactions are suppressed by default through C-08 `replayMode`; redelivery is C-09's separately confirmed operation.

Preview runs the same validator/evaluator against the supplied draft/sample and returns typed fields, selected branches, absent-field explanations and safe step errors. It neither saves/activates nor writes live results, events or Deliveries. External/OS-effecting installed steps are not invoked in preview: return an explicit capability-unavailable explanation unless a declared pure preview implementation exists. Never quietly execute live integration code.

## Presentation and Configuration

Presentation template: ID/revision, immutable definition version, applicable permitted scope, typed field bindings and output kind (GUI card or Delivery text/structured input). ## Text-key Mapping and Remaining Technical Evidence

C-07 owns the complete API error-code/fallback table. C-11 owns `status.<status>`, `validation.<constraint>`, `processing.<reason>` and component/action/accessibility keys. Registry entries require an English base string, typed named parameters and plural forms when count-dependent; CI in AP-15 checks every referenced built-in key/parameter against the catalog.
